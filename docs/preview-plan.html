Detailed implementation plan · F-30–F-36 · F-75 · 6 Sep 2026

A preview for every file.

A resizable pane on the right that renders whatever is selected — Markdown as a document, source as highlighted code across sixty-plus languages, images, PDFs, CSV as a grid — and keeps rendering it as you arrow down a directory, without ever reading a whole file or dropping a frame.

Owner
ferret-preview + ferret-ui
Phase
3 — depends on 1
Targets
macOS · Windows
Primary gate
Zero dropped frames arrow-keying
Decision summary

Executive verdict

Almost every renderer this feature needs is already compiled into the tree and switched off. gpui-component ships a Markdown document view, a Rope-backed virtualised code editor, a tree-sitter highlighter with a publicly extensible language registry, and a table; gpui decodes fifteen image formats and SVG; ferret-vfs’s read already takes a byte budget. The work is not writing renderers. The work is a classifier, a byte budget, one background pipeline, and the two or three places where the stock behaviour is actively wrong for a file manager.

Recommended baselineTurn on gpui-component’s tree-sitter-languages feature for 35 grammars; register roughly 30 more through the public LanguageRegistry for 65+; render Markdown with TextView, code with a read-only Editor, images with our own capped decode into a RenderImage, tabular data with table, and everything else — PDF, Keynote, video, HEIC, RAW, Office — through the operating system’s own thumbnail service behind one ferret-platform trait.
PV-D01

One registry, one Preview value. Classification and reading happen once, on a background thread, and produce a plain data value. The Render impl only reads it. This is gate 7 (“no per-frame work may be O(the directory)”) applied to a pane whose input is O(the file).

PV-D02

ferret-preview is GPUI-free; the pane lives in ferret-ui. Only ferret-ui may depend on gpui-component, and every renderer worth reusing is inside it. So the crate seam falls between what to show — sniffing, budgets, decoding, parsing, caching, all testable without opening a window — and how to draw it.

PV-D03

Nothing reads a whole file. Every provider is handed Vfs::read(path, budget), whose cap is already documented as non-optional. Budgets are per kind and live in ferret-preview/src/config.rs. A file past its budget previews its head with an explicit “first 2 MB of 4.1 GB” banner — never a spinner that never ends, never a blank pane.

PV-D04

Code preview and edit mode are the same component. gpui-component’s Editor with readonly(true) gives virtualised line layout, selection, in-pane find, line numbers, folding and tree-sitter highlighting. F-36 then flips one boolean instead of shipping a second text renderer. Upstream states the editor is built for “large text up to about 50K lines”, so the line cap in PV-D03 is not a preference — it is that ceiling, enforced before we hand text over.

PV-D05

Extend the highlighter; do not replace it. LanguageRegistry::register(name, &LanguageConfig) is public and takes a tree_sitter::Language plus query strings, so additional grammar crates drop straight in and are picked up by the editor and by Markdown’s fenced code blocks with no second theme mapping. This answers Q-02.

PV-D06

Identifying a language and highlighting it are different jobs. A table of ~240 extensions resolves a language name; 65+ of those names have a grammar behind them. An .applescript file previews as monospaced text labelled AppleScript, not as “unsupported binary”. Coverage of the header is total; coverage of colour is finite and honest.

PV-D07

The OS renders what Rust will not. Quick Look on macOS and IShellItemImageFactory on Windows already produce a high-resolution bitmap for PDF, Keynote, Sketch, video, HEIC, RAW and Office documents — the same picture Finder and Explorer show. One ThumbnailProvider trait in ferret-platform, shaped exactly like the existing IconProvider and bound by the same rule: never called on the render path.

PV-D08

PDF ships on both platforms in v1; multi-page is a cargo feature. PV-D07 gives a real first-page render on Windows with no bundled C++ blob, which is what made Q-01 hard. Scrollable multi-page PDF goes behind an off-by-default pdf feature using pdfium-render, which binds its library at run time — so an absent library degrades to the single-page render instead of failing the build.

PV-D09

Decode images ourselves; never hand img() a user’s path. GPUI’s asset loader does a blocking whole-file fs::read and a full-resolution decode. That is correct for the app’s own bundled assets and wrong for a 200-megapixel TIFF someone arrow-keyed past. Probe the header for dimensions, refuse past a pixel cap, decode with limits off-thread, downscale to the pane, and hand GPUI a finished RenderImage.

PV-D10

The preview never touches the network. GPUI resolves a non-file image URI by fetching it over HTTP. A README in a downloaded folder must not be able to make this machine call out — that is a tracking pixel with a file manager attached. Markdown image URLs are rewritten to absolute file:// beneath the document’s own directory or dropped to alt text; no other scheme loads.

PV-D11

One generation, debounced, cancel-by-drop. The same contract the listing and Power Search already use. Arrow-keying twenty rows starts one read, not twenty; every result carries its generation and a stale one is discarded defensively.

PV-D12

A remote preview is the same code with a smaller budget. Vfs::read already spans backends, so SFTP needs no provider of its own — it needs quarter budgets, an explicit “loading over the network” state, and capabilities_for(path) deciding whether the Edit button exists at all.

PV-D13

Edit saves atomically or refuses. Temp file in the same directory, flush, rename; line endings, final newline and permissions preserved; a mtime-or-size change since load blocks the save and says so. This needs a genuinely new Vfs method — the trait has no write today — and it is the one place in this plan where R-06 (data loss) is in play.

Traceability

Source, scope, and non-goals

The reference screenshot is a product reference, not an instruction. docs/plan.html stays authoritative: F-30 the pane, F-31 Markdown, F-32 highlighted code, F-33 images and thumbnails, F-34 PDF, F-35 CSV grid, F-36 in-place editing, plus F-75 space-to-preview. The base shell’s gates — virtualisation, focus, both themes, both platforms, run it, no O(n) per frame — apply unchanged.

Explicit non-goals

  • Not an editor. No LSP, no multi-file, no project, no diagnostics, no format-on-save. F-36 is “fix a typo in a config file without leaving the file manager”, and the moment it grows a second file it has become the wrong product.
  • Not a viewer for everything. Where neither Rust nor the OS can render a type, the pane shows metadata and an Open with… affordance. That is a finished state, not a failure state.
  • No transcoding. Video and audio get a poster frame and metadata; playback is out of scope for phase 3 and probably forever.
  • No archive browsing. A .zip previews as its manifest at most. Mounting archives as folders is a different feature and belongs with the VFS backends.
  • No thumbnails in list view. F-33’s thumbnails are for icon view. A 200,000-row list must not sprout 200,000 decode jobs.
Product experience

Two rows: a header that is identical for every file type, and a body that is entirely the provider’s. Keeping the header type-independent is what makes arrow-keying feel like one surface rather than seven.

Architecture

Three crates, one seam

The layering rule decides this before taste does: no service crate may depend on ferret-ui, and only ferret-ui may depend on gpui-component. Every renderer worth having is inside gpui-component. So the seam is data in, elements out.

1 · ferret-vfsBytes, budgeted

read(path, budget) exists and is already capped. F-36 adds write_atomic. Nothing else changes.

2 · ferret-previewWhat to show

GPUI-free. Sniffing, classification, decoding, CSV parsing, thumbnail cache. Returns a Preview.

3 · ferret-platformWhat the OS can show

ThumbnailProvider: Quick Look and the shell thumbnail service, returning the existing IconBitmap.

4 · ferret-uiHow to draw it

preview/: the pane, the divider, the header, and one render arm per Preview variant. Owns the language registry wiring.

The value the pipeline produces

// crates/ferret-preview/src/preview.rs
pub enum Preview {
    /// F-31. Source plus the directory it lives in, which is what makes
    /// relative image links resolvable — and, per PV-D10, resolvable only
    /// downward from there.
    Markdown { source: String, base: VfsPath, truncated: Truncation },

    /// F-32. `language` is a registry name ("rust", "nix"), never an
    /// extension. `Plain` is a language, not an absence of one.
    Code { text: String, language: SmolStr, truncated: Truncation },

    /// F-33. Already decoded, already downscaled, in the BGRA layout
    /// `RenderImage` wants. `natural` is the size before scaling, so the
    /// footer can be honest about it.
    Image { bitmap: Bitmap, natural: (u32, u32), frames: FrameCount },

    /// F-34 and everything the OS knows how to draw. `by` records which
    /// path produced it, because "Quick Look" and "pdfium" fail differently.
    Rendered { bitmap: Bitmap, pages: Option, by: RenderedBy },

    /// F-35. Header row detected, delimiter sniffed, rows virtualised.
    Table { header: Option, rows: Vec, delimiter: u8, truncated: Truncation },

    /// The floor. Hex plus printable ASCII for the head of the file.
    Binary { head: Vec, size: u64 },

    Directory { entries: Option },
    Multiple { count: usize, bytes: u64, kinds: SmallVec<[(Kind, usize); 4]> },
    Unsupported { kind: Kind, reason: Unsupported },
}

Two properties of this enum are load-bearing. It is Send and owns everything it points at, so it crosses from a background task to the view without borrowing anything that might have been dropped. And it carries no GPUI type — Bitmap is width, height and a BGRA Vec<u8>, the same shape ferret_platform::IconBitmap already validates at the unsafe boundary — which is what keeps the crate’s tests running without a window.

Why the grammars live in ferret-ui and the names live in ferret-previewLanguageRegistry is a gpui-component type, so the tree-sitter-* crates have to be ferret-ui dependencies. The extension-to-name table has no such constraint and belongs with classification. The two halves are kept honest by one test in ferret-ui: every name ferret_preview::languages can emit must either resolve in the registry or appear in an explicit IDENTIFIED_BUT_UNHIGHLIGHTED list. A grammar added without a name, or a name added without a decision about its grammar, fails that test.
Classification

Deciding what a file is

Extension first because it is free and usually right; content second because it is the only thing that is reliably right. A .txt that is actually a 900 MB core dump must not reach the text renderer, and a Makefile with no extension at all must.

  1. Name table. Exact filenames before extensions: Makefile, Dockerfile, Cargo.lock, .gitignore, CMakeLists.txt, go.sum, Justfile, .env. This is the case a pure extension map gets wrong every time, and it covers a lot of what sits in a repository root.
  2. Extension table. ~240 entries mapping to a Kind and, for text kinds, a language name. Built once as a static phf-shaped match — a plain match on a lowercased SmolStr, which the icon layer already established as the right representation for an extension.
  3. Magic bytes. The first SNIFF_BYTES (8 KiB) decide format for anything the name did not settle, and override the name for images and archives: PNG, JPEG, GIF, WebP, TIFF, BMP, ICO, AVIF, QOI, PDF (%PDF-), Zip, Gzip, ELF, Mach-O, PE, and the UTF-8/16/32 BOMs.
  4. Binary test. A NUL byte in the sniff window, or invalid UTF-8 that is not a truncated final code point, means binary. This is the same heuristic grep-searcher uses, which matters because Power Search and the preview should agree about what is text.
  5. Size gate. Applied last, per kind, before any full read is attempted.
The sniff is a second read, and that is fineReading 8 KiB and then reading 2 MiB looks wasteful until you price the alternative: reading 2 MiB of a 4 GB video to discover it is a video. The sniff is one read(path, SNIFF_BYTES); the head it returns is reused as the first 8 KiB of the text read where the kind turns out to be textual, so the redundant work is bounded by 8 KiB and only on files we were going to read anyway.

Symlinks are resolved for classification and reported in the header — a symlink to a 4 GB file previews the target under the target’s budget, and the header says where it points. A broken symlink is a Gone-adjacent state with the dangling target named, not a silent empty pane. A symlink loop is bounded by Vfs::canonicalize, which already exists for the per-folder preference key.

The renderers

The providers, one at a time

F-31 Markdown — TextView

gpui-component’s TextView parses Markdown into a document tree and renders headings, lists, tables as real tables, block quotes, task lists, links, inline code and fenced code blocks — the fences highlighted through the same LanguageRegistry the code provider uses, so a Rust block in a README and a .rs file get identical colours for free.

Three things need doing on top:

  • Hold the state entity. TextViewState::set_text parses synchronously only up to 4 KiB and hands anything larger to a background task with a revision check. So the pane owns one Entity<TextViewState> for its lifetime and calls set_text on selection change. Constructing a new state per frame would re-parse the document on every frame and is exactly the per-frame O(n) work gate 7 forbids.
  • Rewrite image URLs (PV-D10). Upstream turns a document image URL into an ImageSource without granting filesystem access, which means a relative ![](img/x.png) resolves against nothing useful and an https:// URL resolves against the network. Ferret rewrites relative paths to absolute file:// beneath base, rejects anything that escapes base after normalisation, and replaces every other scheme with its alt text.
  • Link clicks. on_link_click routes a relative link to the file pane (select the target, or navigate if it is a directory) and an external link to the platform’s opener with the URL shown in a confirm. Never navigate the preview itself — the preview follows the selection, and a preview that could navigate on its own would fight the list.

MDX and HTML-in-Markdown are parsed but rendered as their source text inside a code block rather than executed; TextView::html exists but pointing it at arbitrary repository content is a strictly larger attack surface for no product gain.

F-32 Code — read-only Editor

EditorState::new(window, cx).language(name).line_number(false).soft_wrap(false), rendered through Editor::new(&state).readonly(true). Its element lays out only the visible line range, so a 20,000-line file costs the same per frame as a 20-line one.

The pane owns one Entity<EditorState> and calls set_value plus set_highlighter when the selection changes, for the same reason as Markdown. Scroll position resets; the language changes with the file; the read-only flag is the only difference between this and F-36.

Line numbers default off — the reference screenshot has none and a preview is for reading, not for citing — and are a persisted toggle in the overflow menu. Soft wrap defaults off for code and on for plain text and logs, which is the split that matches how people actually read those two things.

F-33 Images — our decode, GPUI’s draw

gpui::img() already handles AVIF, JPEG, PNG, GIF, WebP, TIFF, TGA, DDS, BMP, ICO, HDR, EXR, the PNM family, QOI and SVG, with animated GIF and animated WebP decoded to frame sequences. The formats are not the problem. The path is: GPUI’s loader does a blocking whole-file read and a full-resolution decode, which is right for a bundled 24 px icon and catastrophic for a photographer’s directory.

So ferret-preview::image owns the pipeline and GPUI only draws the result:

  1. Probe the header for dimensions without decoding. Past IMAGE_SOURCE_PIXEL_CAP the answer is TooLarge and no allocation happens at all.
  2. Read under the kind’s byte budget, decode off-thread with the decoder’s own allocation limits set.
  3. Downscale to the pane’s long edge at the window’s scale factor, capped at 4096 px, with a triangle filter — bilinear is visibly soft on downscales this large and Lanczos costs more than the difference is worth at preview size.
  4. Convert to BGRA and hand ferret-ui a Bitmap, which becomes one RenderImage.

Animation. Animated GIF and WebP are decoded to frames and played only in the docked pane and the F-75 overlay, never in icon-view thumbnails — a directory of forty animated GIFs must not become forty running animations. A frame count past ANIMATION_FRAME_CAP falls back to the first frame with a footer note.

SVG. Rendered through GPUI’s own svg_renderer at the pane’s size, so it stays sharp on resize rather than being rasterised once. Bounded by the same source-pixel cap on its viewBox.

HEIC and RAW. The image crate decodes neither, and they are two of the most common things in a real Pictures folder. Both go to PV-D07’s OS thumbnail path, which handles them natively on both platforms — an iPhone photo previews without Ferret linking libheif at all.

Thumbnails. Icon view asks ferret-preview::thumbs, which is a disk cache under the user’s cache directory keyed by a hash of canonical path, mtime, size and target pixel size. Size in the key is the part that is easy to omit and matters: a file edited without its mtime changing is rare, but a file replaced with one of a different length is not. Entries are 128 px WebP, evicted by age past THUMB_CACHE_AGE and by total bytes past THUMB_CACHE_BYTES, oldest first. Generation is bounded to visible tiles plus a small lookahead, on ferret_vfs::pool, never on a fourth thread pool.

F-35 CSV and TSV — table

Delimiter sniffed from the first 64 KiB by scoring comma, tab, semicolon and pipe on consistency of field count across the first 20 lines — the frequency-only heuristic gets European semicolon-delimited exports wrong often enough to matter. Header detection: the first row is a header if every one of its fields is non-numeric and at least one subsequent row has a numeric field in the same column.

Parsed with the csv crate, because RFC 4180 quoting — embedded delimiters, embedded newlines, doubled quotes — is precisely the kind of thing that looks like twenty lines of hand-rolled code and is wrong on real data. Rows stream into a bounded buffer and render through gpui-component’s virtualised table, so the plan’s “a 500 MB export still opens” means the first screen paints from the first few kilobytes and scrolling pulls more.

Column sorting is offered only within what has been loaded, and says so, rather than pretending to sort a file it has not read. Malformed rows render with their fields as parsed and a marker, never dropped silently — a preview that hides the broken row is worse than useless for the person trying to find it.

F-30 Plain text, logs, and the binary floor

Text with no language resolves to the Plain language and renders in the same editor with soft wrap on. Line endings are detected and reported in the header (LF / CRLF / mixed) because that is load-bearing information the moment F-36 is involved. A UTF-16 or UTF-8 BOM is decoded and noted; invalid sequences render as U+FFFD rather than refusing the file.

Binary is the floor and is a real view, not an apology: 16 bytes per row, offset gutter, hex, printable ASCII column, for the first HEX_BUDGET bytes. It is what makes “what actually is this file” answerable without leaving the app.

F-75 Space-to-preview

The same Preview value rendered into a full-window overlay mounted on Root’s dialog layer. Deliberately not deferring to macOS Quick Look’s own panel: sharing the provider means the two surfaces cannot disagree, and the overlay works identically on Windows where there is no Quick Look panel to defer to. The OS thumbnail service is still used underneath for types we cannot render — it is a data source, not a UI.

Because the value is already computed for the docked pane, Space on an already-previewed selection opens instantly with no read at all. When the pane is closed, the overlay runs the same pipeline on demand.

Q-02, answered

Sixty-plus languages without a second highlighter

gpui-component ships 35 grammars behind its tree-sitter-languages feature — which Ferret currently does not enable, so today’s editor has no highlighting at all. Turning it on is step one. Getting from 35 to 65+ is the interesting part, and the mechanism already exists: LanguageRegistry::register is public, takes a tree_sitter::Language and query strings, and is consulted by the editor and by Markdown fences alike.

The capture-name detail that decides whether this looks rightgpui-component resolves a tree-sitter capture to a style through 41 named slots, and falls back by dotted prefix — keyword.modifier resolves to keyword. Upstream grammar crates ship nvim-flavoured queries full of names like @variable.parameter and @function.method, and that fallback is exactly what makes them usable unmodified. Where a grammar’s query is genuinely poor, the fix is a hand-written highlights.scm in our own tree — which is what gpui-component itself does for twelve of its languages — not a different highlighter.

Why not syntect

syntect with two-face would reach 250 languages in one dependency. It is the wrong trade here for three reasons, in order of weight. It would be a second highlighter: the editor and the Markdown fences are already driven by tree-sitter, so syntect output would need its own theme mapping and the same file could get two different colourings depending on where it appeared. Its Sublime-syntax engine is regex-per-line, which is a poor fit for a component that lays out only the visible range. And the marginal languages it adds past our extended set are ones nobody browses in a file manager — the long tail is real but it is a tail.

The cost, stated plainly

Thirty additional generated-C grammars is roughly a minute of extra cold build and somewhere in the region of 15–25 MB of binary before strip. That is a real cost paid by every contributor on every clean build, and R-07 already names build friction as a live risk. So the extended set sits behind a default-on languages-extended feature on ferret-ui: on for anyone who builds normally, and --no-default-features away for someone iterating on the file pane who does not care about Gleam. The built-in 35 are never optional — a code preview with no colour is a broken feature, not a fast build.

Both options were framed as the only two, and there is a third that is better than either: ask the operating system, which is already rendering these documents for its own file manager.

MuPDF was considered and set aside: it is AGPL, and while AGPLv3 and GPLv3 are explicitly compatible, taking an AGPL dependency changes the obligations of everyone who redistributes Ferret and that is not a decision a preview pane gets to make.

Contract

Performance contract

Phase 3’s acceptance in docs/plan.html is “arrow-keying down a directory of mixed file types renders each preview without a dropped frame”. That sentence is the whole contract, and it is satisfied by four rules.

  1. Debounce, then one generation. A selection change bumps preview_generation and schedules work at PREVIEW_DEBOUNCE (80 ms). Holding ↓ through forty rows produces one read. In-flight work is dropped by dropping its task — the cancel-by-drop pattern the listing already uses — and any result whose generation is stale is discarded on arrival regardless.
  2. Nothing O(the file) on the main thread. Reading, sniffing, decoding, downscaling and CSV parsing all run on ferret_vfs::pool or through smol::unblock. Markdown and tree-sitter parsing are the two exceptions and they are not ours: both components already background their own parse with a revision check, which is why the pane holds their state entities rather than rebuilding them.
  3. The render path reads, and only reads. Render for the preview pane matches on a Preview and builds elements. It does not clone the text, re-derive a language, re-scan for line endings or rebuild a bitmap. just budget is the mechanical check, and the preview pane joins the allocation-budget test with its own case: arrow through ten files of ten kinds and assert the per-frame allocation count is flat.
  4. Budgets are hard, and stated. Every read is capped; every cap has a footer line when it bites. There is no path through this feature that reads an unbounded number of bytes, and no path that decodes an unbounded number of pixels.

Safety

Safety and privacy

A preview pane renders files the user did not write, did not choose and may have just downloaded. That is a different threat model from an editor opening a project, and three things follow from it.

  • No network, ever (PV-D10). The single most likely quiet failure in this whole feature is a Markdown file with ![](https://tracker.example/pixel.png) silently confirming to a third party that this machine opened this file. GPUI will happily fetch it. Every non-file scheme is dropped to alt text, and a test asserts that with a URL that would fail loudly if it were fetched.
  • No path escapes. A rewritten relative image URL is normalised and rejected if it leaves the document’s directory. ![](../../../.ssh/id_rsa) renders as alt text. The check is on the normalised path, not the literal string, because a/../../b is the version that gets through a string check.
  • Every decoder gets limits. Decompression bombs are the standard attack on exactly this surface — a 40 KB PNG that decodes to 60 GB. The pixel cap is checked from the header before allocation, and the decoder’s own Limits are set as the backstop for formats where the header lies.
  • The OS renders out-of-process where it can. Quick Look generation runs outside our address space, so a malformed PDF crashes Apple’s helper and returns an error, not a crash. On Windows the shell thumbnail provider is in-process; the mitigation is that it runs on a worker thread and its failure is caught, but this is an honest asymmetry worth recording.
  • Nothing the preview reads is ever written back. Except through F-36, which is explicit, confirmed and atomic.
Mounts

Remote mounts

Because FerretState.fs is a Router, a preview on an SFTP mount is the same code path with different latency. Four things change, and all four are already named as rules in the repository guide.

  • Budgets scale down. REMOTE_BUDGET_SCALE is ¼. A 2 MiB text budget over a 200 ms-RTT link is several seconds of waiting for something the user was arrow-keying past; 512 KiB is a preview.
  • The loading state is not optional. Locally the 120 ms threshold means the skeleton rarely appears. Remotely it always will, and it says “Reading over the connection” rather than showing a generic spinner, because the user needs to know which kind of slow this is.
  • Ask capabilities_for(path), never capabilities(). The Edit button’s existence is a property of the backend the file is on. A read-only mount shows no Edit button rather than an Edit button that fails on save.
  • There is no watcher. A remote preview does not refresh itself when the file changes on the server, and the mount answers from a five-second cache. A manual refresh in the overflow menu calls Vfs::invalidate first — the same rule every other remote-facing surface follows.
  • The OS thumbnail path is local-only. Quick Look and the shell take a filesystem path. A remote PDF either downloads under budget (and gets the pdfium path if that feature is on) or shows metadata and Open with…, which for a mount means downloading it deliberately. It does not silently pull 40 MB over SSH because someone moved the selection.
F-36

Edit mode

The smallest feature in this plan with the largest downside. R-06 names data loss as the worst thing this product can do, and in-place save is the one place the preview pane can do it.

The Vfs gains one method. The trait has read but no write, so this is genuinely new surface:

/// Replace a file's contents, atomically.
///
/// Writes a temporary file in the *same directory* — a different filesystem
/// makes the final step a copy, which is exactly what atomicity rules out —
/// flushes it, then renames over the target. A reader either sees the old
/// bytes or the new ones, never a truncated file, and a crash mid-write
/// leaves the original intact.
///
/// `expect` is the identity the caller last saw. A mismatch is refused
/// rather than resolved: the file changed under the editor, and only the
/// person looking at both versions can say what should win.
async fn write_atomic(
    &self,
    path: &VfsPath,
    contents: &[u8],
    expect: FileIdentity,
) -> Result<()>;

Around that:

  • Preserved on save: the file's existing line endings (a CRLF file stays CRLF even though the editor works in LF), the presence or absence of a trailing newline, the BOM if there was one, and Unix permission bits. Ownership where the platform allows it.
  • Refused: binary files; files that were truncated by the budget, because saving a truncated buffer would destroy the tail; and any file whose mtime or size changed since load.
  • Confirmed: navigating away with unsaved changes. The selection change is blocked, not queued — a preview that silently discards an edit because the user pressed ↓ is the data-loss failure in miniature.
  • Windows: rename over an existing file needs ReplaceFile or a delete-then-rename; the naïve fs::rename fails if the target exists. This is one of the platform differences that must be handled in LocalFs, not discovered in the field.
  • Remote: SFTP has no atomic replace primitive that is universally available. The mount writes to a part file and renames, which is the same approach the transfer code already takes, and the capability is declared honestly if a server refuses.

Tests for this are the highest-value tests in the feature, against temp directories: CRLF round-trip, no-trailing-newline round-trip, BOM round-trip, permission preservation, concurrent-modification refusal, and a byte-identical round-trip of a file that was opened and saved without being edited.

Sequence

Build sequence

Ordered so each step leaves the app runnable and each gate is passed at the point where it is cheapest. Steps 1–3 are the ones that decide whether the feature is any good; everything after is additive.

01

The pane, with no file reading at all

Right-hand split, drag-resizable divider reusing render_sidebar_divider’s shape, toolbar toggle, persisted width in a new settings.preview block, collapse-before-sidebar at the minimum window width. Renders only the Empty, Multiple and Directory states.

Done when the pane opens, closes, resizes, remembers its width across a restart, and looks right in both themes with the terminal both open and closed.

02

ferret-preview: classification and budgets

New crate, GPUI-free. The name and extension tables, magic-byte sniffing, the binary heuristic, size gating, budgeted reads, line-ending and BOM detection, and the Preview enum. Tests against temp directories cover every branch — this is the crate where the repository guide says tests are worth the most.

Done when cargo test -p ferret-preview passes with no window opened, and classification is correct for a fixture directory containing a Makefile, a mislabelled .txt binary, a UTF-16 file, a 4 GB sparse log and a broken symlink.

03

Text and code, unhighlighted — and the performance gate

The pipeline end to end: debounce, generation, background read, Preview into the pane, read-only Editor. No colour yet.

Done when arrow-keying the length of the 200,000-entry fixture with the pane open drops no frames and issues a handful of reads rather than one per row. If this step is not clean, nothing later fixes it.

04

Highlighting: the built-in 35

Enable tree-sitter-languages on the workspace gpui-component dependency. Map the theme’s 41 syntax slots in ferret.json for light and dark. Wire the language name from classification into EditorState.

Done when a Rust, a Python, a TypeScript and a YAML file each render correctly in both themes, and the palette is Ferret’s rather than the library default.

05

Sixty-plus: the extended grammars and the identification table

The ~30 registrations behind languages-extended, the ~240-entry name table, and the invariant test tying them together.

Done when a Dockerfile, a .tf, a .nix and a .vue highlight; an .applescript renders as labelled plain text; and building with --no-default-features still highlights all 35 built-ins.

06

Markdown

TextView with a held state entity, the image-URL rewrite, the scheme block, and link routing.

Done when this repository’s own README.md renders with working tables and highlighted fences, a relative image resolves, an https:// image does not load, and a ../../ image does not escape.

07

Images, then thumbnails

Header probe, capped decode, downscale, RenderImage. Then the disk cache and icon-view tiles, bounded to visible-plus-lookahead on ferret_vfs::pool.

Done when a 9504 × 6336 RAW-adjacent TIFF previews without a memory spike, an animated GIF plays in the pane and not in the tiles, and scrolling an icon view of 500 photographs drops no frames on a second visit.

08

ThumbnailProvider: PDF and the long tail

The trait in ferret-platform, Quick Look first because it is the simpler of the two, then IShellItemImageFactory with COM confined to its worker thread.

Done when a PDF, a Keynote deck, an MP4 and an iPhone HEIC each preview on macOS; a PDF, a .docx and an MP4 each preview on Windows; and a type neither service knows falls through to Unsupported with Open with… rather than a blank pane.

09

CSV and TSV grid

Delimiter scoring, header detection, streaming rows into the virtualised table, loaded-range-only sorting.

Done when a semicolon-delimited export with quoted embedded newlines renders correctly, and a 500 MB CSV paints its first screen in the same time as a 5 KB one.

10

Edit mode

Vfs::write_atomic with the Windows replace path, the Edit button gated on capabilities_for, dirty state, conflict refusal, navigation guard.

Done when a CRLF config file with no trailing newline round-trips byte-identically apart from the intended change, on both platforms, and a file modified externally mid-edit refuses to save with a message that says what happened.

11

Space-to-preview (F-75)

The overlay on Root’s dialog layer, reusing the computed Preview.

Done when Space opens instantly on an already-previewed file, works with the pane closed, and does not fire while a text field has focus.

12

Optional: multi-page PDF

pdfium-render behind the off-by-default pdf feature, binding at run time, degrading to step 8’s single page when the library is absent.

Done when a 400-page PDF scrolls and the same build with the library removed still shows page one.

Questions this plan closes

Q-01

Closed. PDF ships on both platforms in v1 as a first-page render through the OS thumbnail service — no bundled pdfium, no macOS-only compromise. Scrollable multi-page is an off-by-default feature that binds its library at run time.

Q-02

Closed. The built-in 35 always; ~30 more registered through the public registry behind a default-on feature; ~150 further extensions identified but not highlighted. Runtime-loadable grammars are not worth the complexity — the registry already makes compile-time registration a one-line addition per language.

Questions left open

PV-Q01

Should the preview follow the selection or the cursor in a multi-select? Following the cursor is more useful and more surprising. Decide when step 1 meets a real multi-select.

PV-Q02

Does edit mode survive navigating away, as an unsaved buffer per tab, or is it strictly modal to one selection? Modal is safer and is what step 10 builds; per-tab buffers are a real convenience and a real chance to lose work.

PV-Q03

Do we ever want in-process HEIC (libheif-rs)? Only if a Linux backend returns, since PV-D07 has no answer there. Deferred with D-19.
