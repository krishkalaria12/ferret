§1

What this is

The build document for Phase 2, in the same relationship to plan.html that ui-base.html had to Phase 1.

plan.html catalogues the terminal as three feature entries and two paragraphs. That was enough to schedule it and nowhere near enough to build it. This document is the missing half: which VT engine, why, how the threads are arranged, what "sync" actually means when a process is running, what ships in the box for four different shells, and the order to build it in so the app still runs at the end of every day.

In scope: F-10 (the panel), F-11 (directory sync, both directions), F-12 (terminal themes and independent text size), plus one small platform feature — "Open in Terminal" (D-29), which ships early and independently because it is also the bottom rung of the fallback ladder in §2.

Not in scope: F-13, the SSH terminal that follows a remote mount — it depends on F-21 and belongs to Phase 7. Nothing here should make F-13 harder, and §4 keeps the seam it will need, but no remote code gets written now.

The bar

A terminal that runs ls is a log view. The acceptance test is vim, htop and tmux — three programs that between them exercise the alternate screen, mouse reporting, resize, 256-colour and true-colour SGR, cursor shapes, and bracketed paste. If those three are right, almost everything is right. See §11.

What Phase 1 already gives us

The base shell is finished and its 122 tests pass, so this phase starts from a real application rather than a scaffold. Three pieces of it are load-bearing here:

  • crates/ferret-ui/themes/groknight.json already carries a terminal block with all sixteen ANSI slots plus foreground, background and cursor. F-12's data format exists; only the loader is missing.
  • ferret-settings owns the settings schema and keymap, including appearance.ui_font_size. The terminal's font size is a sibling field, not a new mechanism.
  • The browser owns per-tab state and a current directory that already changes on navigation. Forward sync hooks that, it does not invent it.
§2

The engine decision

The one choice in this phase that is expensive to reverse.

A terminal panel is three layers, and only the middle one is a real choice:

PTYspawn a shell, read and write bytes, resize
→
VT engineparse escapes, keep the grid, encode input
→
Rendererpaint the grid with GPUI

Ferret writes the first and third layers whichever engine it picks. Only the middle is a library decision.

Ruling out an out-of-process terminal

The first option to consider and dismiss: do not emulate anything, and drive a terminal that already exists. It cannot deliver F-10. Terminal.app, iTerm2, kitty and Windows Terminal are applications, not embeddable views — there is no supported API to host one inside another process's window, and the child-window reparenting tricks that appear to work break focus, IME, GPU compositing and window dragging, on both platforms. Every editor with a built-in terminal — VS Code, Zed, JetBrains, Sublime — writes its own emulator on top of a PTY for exactly this reason.

This also rules out the more interesting version of the idea: kitty-rc, a Rust client for kitty's remote-control protocol. It is worth naming explicitly so it does not get proposed again, because at a glance it looks like a terminal library and is not one.

Why kitty-rc is not a fallback

It is the wrong layer. kitty-rc is a client that sends JSON commands to a running kitty instance over a socket — LaunchCommand, FocusTabCommand, SetFontSizeCommand. It parses no escape sequences and owns no grid, so it cannot stand in for the middle box in the diagram above. What it could do is drive an external kitty window: open one in the current folder and re-cd it as you navigate, which is a real approximation of F-11. But it delivers none of F-10 — no docked panel, nothing inside Ferret's window — and it works only for users who have kitty installed and allow_remote_control enabled. That is a narrower audience and a weaker result than the escape hatch below, which needs nothing installed at all.

What we do take from the system is the shell, which is a different question and is settled in D-24 below.

The two real candidates

plan.html assumed alacritty_terminal, on the reasonable grounds that Zed uses it and Zed is the closest working example of a terminal on GPUI. That assumption predates libghostty-vt having usable Rust bindings. It is now worth re-opening, and the comparison does not come out where the plan expected.

D-22 The VT engine is libghostty-vt, pinned to an exact version.

Version 0.2.1 (18 July 2026) is the floor. Pin it exactly in Cargo.toml — =0.2.1, not a caret range — and bump it as a deliberate, tested change, the same rule the workspace already applies to gpui and gpui-component.

Because OSC 7 decides it. F-11's reverse direction — the terminal changes directory and the file pane follows — is half of the signature feature, and on Windows OSC 7 is the only way to get it: there is no /proc and no proc_pidinfo. Choosing Alacritty means either forking vte or running our own escape-sequence scanner over the raw PTY stream, correctly, across chunk boundaries, forever. That is a worse thing to own than a pinned dependency. The conformance and reflow advantages are real but secondary; they are the reason this is an easy decision rather than a close one.

What this costs, stated plainly

A Zig toolchain enters Ferret's build. That cuts against the spirit of D-13, which turned on runtime_shaders specifically so contributors would not need full Xcode. It is the strongest argument against this decision and it is not dismissed — it is paid for by D-23, and it is why step 1 of §10 is a build spike on both platforms before any other terminal code is written.

D-23 The C API is isolated behind one internal module, and snapshots are owned Rust data.

Everything in ferret-terminal outside engine/ talks to a small internal surface — feed bytes, take a snapshot, encode a key, resize — and never touches a libghostty-vt type. Grid data crosses that boundary as owned Rust values, copied out; no borrowed pointer into engine memory is ever held past the call that produced it.

Because two independent reasons converge on the same shape. The dependency is pre-1.0, so its API will move under us and we want one file to fix rather than a crate to re-write. And the types are !Send + !Sync, so a snapshot that borrowed engine memory could not be sent to the UI thread at all — copying is not defensive style here, it is the only thing that compiles. This is also the seam that makes the Alacritty fallback a week's work rather than a rewrite, if the Windows or Zig risks in §12 land badly. It is one module boundary, not a plugin system: resist any urge to grow it into a trait with one implementation.

D-24 Ferret spawns the user's own login shell, with no configuration of its own.

macOS: $SHELL, falling back to the user's getpwuid shell, then /bin/zsh. Windows: PowerShell 7 (pwsh.exe) if on PATH, else Windows PowerShell, else cmd.exe. Started as a login shell so the user's real profile, aliases, prompt and PATH apply. A terminal.shell settings override exists for people who want something else, but it is empty by default.

Because a file manager's terminal that is not the user's own shell is a toy. Anyone who would use this feature has a configured shell and expects it. The override exists because Windows users switching between pwsh, cmd and Git Bash is normal, not exotic.

D-25 The PTY layer is portable-pty.

One API over forkpty on macOS and ConPTY on Windows, with try_clone_reader() and take_writer() giving independent read and write handles.

Because it is the crate WezTerm ships on and the one Paneflow drives libghostty-vt with on Windows, so the exact combination is in production somewhere. Writing our own ConPTY binding to save a dependency would be trading a week for a rounding error, and ConPTY's sharp edges — startup ordering, resize, draining output at exit, killing descendants — are precisely the parts we would get wrong.

The fallback ladder

D-22 carries real risk (R-09, R-10, R-11), so it is worth writing down in advance what we do if it fails, and at which point we would decide. Each rung costs more product than the one above it, and each is reachable from the step in §10 where the failure would actually surface.

What the ladder is not

It is not a licence to build all three. Rung 1 is the plan; D-23's module boundary is the only structural concession made to rungs 2 and 3, and it earns its place on the !Send constraint alone. Do not write an engine trait with one implementation against a fallback that will probably never be taken.

Matching the reference

Iruka labels this header Terminal rather than showing a path, and puts a filled Sync control at the right end — that shape is worth keeping, and Ferret follows it. Two deliberate departures. The shell's directory appears next to the label only when it differs from the pane's, because the rest of the time it duplicates the path bar and the one moment you need it is when the two have come apart. And the injected line is cd -- '…' rather than cd "…": single quotes stop the shell expanding $ and backticks in a filename, and -- stops a directory named -P being read as a flag. The reference's form breaks on both. Only the functional layout is being reimplemented here — no artwork, icon or string is taken from it.

When the shell exits

The grid freezes with its last contents, dims by 40%, and a single line appears under it: [process exited with status 1 — press ⏎ to restart]. The panel does not close itself. A shell that died taking its scrollback with it is how you lose the error message you were about to read.

§4

Crate architecture

One new crate, and the rule that keeps it testable without a window.

Per the ownership rule in AGENTS.md, the new crate exists because the code that belongs in it now exists. ferret-terminal owns the PTY, the engine and the session; ferret-ui owns the panel view and the renderer.

The layering rule, applied

  • ferret-terminal must not depend on ferret-ui, on gpui, or on gpui-component. It is a service crate like ferret-vfs, and it must be testable without opening a window — feed it bytes, assert on the snapshot. ferret-vfs and ferret-settings hold that line today with 50 window-free tests; this crate holds it too.
  • It may depend on ferret-settings for the terminal palette and font size, and on ferret-vfs for VfsPath — the sync policy needs to know a local path from a remote one, which is exactly the distinction VfsPath exists to draw.
  • Only ferret-ui may draw. The renderer lives there because it is a GPUI Element and nothing else in the workspace is allowed to be.
The seam Phase 7 will need

F-13 opens an SSH session that follows a remote mount. It differs from a local session in exactly one place: what pty.rs spawns — ssh host rather than the login shell. Keep the spawn decision in shell.rs behind a single function returning a command, and Phase 7 adds a branch to it rather than a second session type. Do not build that branch now.

§5

The data path

Three threads, two channels, and the !Send constraint that arranges them.

Because every libghostty-vt type is !Send + !Sync, the Terminal must be created on one thread and stay there for its whole life. That is not a limitation to work around — it produces the design you would want anyway: a shell's output is a serial byte stream, and parsing it on a dedicated thread keeps the UI thread free during a flood.

GPUI main thread

  • Owns TerminalPanel and the latest snapshot.
  • Paints. Never parses.
  • Sends Input, Resize, Scroll, Cd down the request channel.
  • Receives SessionEvent and calls cx.notify().
ferret-ui::terminal

Engine thread — one per session

  • Creates and owns the Terminal. Never moves it.
  • Blocking-reads the PTY, feeds bytes to the parser.
  • Encodes keys and mouse events — encoding needs mode state, so it must happen here.
  • Builds owned snapshots and throttles them to one per frame.
  • Surfaces OSC 7, OSC 133, title and bell as events.
ferret-terminal::session

Foreground poller

  • One shared timer thread for all sessions, not one each.
  • Answers "is the shell at a prompt?" when there is no shell integration.
  • Polls at 250 ms, and only while a cd is queued.
ferret-terminal::foreground

Shape of the loop

Illustrative, not a signature — libghostty-vt's exact API is pre-1.0 and should be read from the docs at the pinned version:

// on the engine thread; `term` never leaves it
let mut term = Terminal::new(opts)?;
let mut buf = [0u8; 64 * 1024];

loop {
    select! {
        // PTY output: parse it, but do not snapshot per chunk
        n = reader.read(&mut buf) => {
            term.process(&buf[..n]);
            dirty = true;
        }
        // UI requests: encoding needs `term`'s mode state, so it happens here
        req = requests.recv() => match req {
            Input(key)   => writer.write_all(&term.encode_key(key))?,
            Resize(c, r) => { term.resize(c, r); pty.resize(c, r)?; dirty = true; }
            Cd(path)     => if sync.may_inject(&term) { writer.write_all(...)?; },
        }
    }

    // Throttle: at most one snapshot per frame, however fast the flood.
    if dirty && last_emit.elapsed() >= FRAME {
        events.send(SessionEvent::Frame(term.snapshot()))?;   // owned copy, D-23
        last_emit = Instant::now();
        dirty = false;
    }
}
The throttle is not an optimisation

It is the difference between working and not. yes, cat of a large file, or a verbose build all produce output far faster than 60 frames a second. A snapshot per read chunk saturates the channel, and the UI thread spends every frame painting states no human will see. Emit at most one per frame and drop the intermediate grids — they were never visible. Paneflow hit the same wall and fixed it the same way.

What a snapshot contains

libghostty-vt gives us most of this already: RenderState is its own viewport snapshot, walked with row and cell iterators. Our snapshot is the owned copy we make while walking it — D-23's rule — because a RenderState is !Send and cannot cross to the UI thread. Scrollback, wrapping and reflow are the engine's job, not ours; we never keep a second copy of the grid.

Owned, Send, and cheap enough to build every frame. A 200×60 viewport is 12,000 cells; at roughly 16 bytes each that is under 200 KB, and the allocation is reused between frames rather than freshly allocated.

Snapshot fields
FieldWhy the UI needs it
rows: Vec<Row>Visible viewport only, never the whole scrollback. Each cell carries its grapheme, fg, bg and attribute bits.
cursorPosition, shape, visibility, blink. Drawn only when the panel has focus — same focus rule as the file pane's selection in ui-base.html §8.

Rendering rule

Shape per run of identical style, not per cell. A monospace grid has a uniform advance, so x positions are arithmetic and a run of 80 same-styled cells is one ShapedLine. Shaping per cell is the mistake that makes a terminal feel slow, and it is the terminal's equivalent of the virtualisation gate from Phase 1 — cheap now, unrecoverable later.

§6

Directory sync

F-11. The signature feature, and the one with a way to lose someone's work.

The behaviour being guaranteed

You navigate in the file pane. The terminal is already there. No keystroke, no focus change, no waiting. That sentence is the product, and everything in this section exists to make it true without the failure mode that would discredit it — a cd landing in the middle of a running program. The safety rules below are not hedges against the feature working; in the ordinary case — a shell sitting at a prompt, which is what a shell is doing almost all of the time — every one of them passes at once and the cd goes out in the same frame as the navigation.

Two directions, with very different risk. Terminal → UI is safe: we read a path and navigate a pane. UI → terminal writes into someone's shell, and a write at the wrong moment corrupts a command they were typing or, worse, lands in a running program's stdin.

Forward: the pane moves, the shell follows

The rule is a single conjunction. Inject only when all of these hold:

Forward-sync preconditions
ConditionHow we knowIf unknown
Sync is on Per-tab toggle. —
Not on the alternate screen From the snapshot — mode 1049. Catches vim, htop, less, tmux. Never unknown; the engine always knows. This is the cheapest and most valuable of the checks.
The shell is at a prompt Tier 1 — normally. OSC 133 prompt marks from the integration D-30 injects: exact, and present on both platforms without the user doing anything.
Tier 2 — when injection failed. macOS: tcgetpgrp(fd) equals the shell's pid. Windows: the shell process has no child processes (Toolhelp32 snapshot).		 Hold the cd, show the toggle amber, retry on the next poll.
The input line is empty Tier 1 only. OSC 133's B mark gives the column where input starts; compare it to the cursor column. Unknowable at Tier 2. See R-12 — but D-30 makes Tier 2 the rare case rather than the Windows default.
The terminal has been idle
Tier 2 only		 No output and no keystroke for one second (D-26). Tier 1 does not wait at all. OSC 133 has already told us the prompt is up and the input line is empty, so there is nothing an idle timer would add — it would only make the feature feel slow. The wait is a Tier 2 substitute for knowledge we normally have.

When they hold, write one line:  cd -- '/quoted/path'\n. Note the leading space — with HISTCONTROL=ignorespace (bash) or setopt HIST_IGNORE_SPACE (zsh) it keeps Ferret's own cd lines out of the user's history. Because D-30 injects, we set that ourselves at spawn rather than hoping the user has it; at Tier 2 those lines are visible in history, which is untidy but not harmful. Never override a HISTCONTROL the user has already set to something else — append to it.

Only the newest queued directory is ever sent, coalesced over 120 ms. Someone arrow-keying down a folder tree generates a navigation per keystroke; the queue holds one entry and replaces it, so the shell receives one cd when they stop, not forty. 120 ms is under the threshold where a UI feels like it is responding to you rather than catching up with you, and it is the only delay in the Tier 1 path.

Why this is not a race

The order is fixed and it matters. The pane navigates first and repaints; the cd is queued from that same update. If the shell is busy the queue simply holds — the pane does not wait for the shell, ever. A file manager that blocked navigation on a terminal would be a worse file manager than the one Phase 1 already shipped, and no amount of sync is worth that trade.

D-26 At Tier 2, a cd that cannot be proven safe is held, not guessed at.

When the integration did not load — the cases in §7 — Ferret can tell that no child process is running but cannot tell whether the user has half-typed a command. In that state the cd stays queued and the toggle sits amber until the terminal has been idle for a full second, roughly four times the Tier 1 window. If a keystroke arrives during that window the timer restarts.

Because injecting into a shell we cannot read is how you append cd to somebody's half-written rm. Waiting a second costs nothing — nobody is watching the terminal at the moment they navigate a folder — and a keystroke inside the window is the one signal we do get that a human is mid-thought. An earlier draft of this decision disabled forward sync on Windows entirely; D-30 makes that unnecessary, because Tier 1 is now the normal case on both platforms.

Reverse: the shell moves, the pane follows

The shell emits ESC ] 7 ; file://host/path ST on every directory change. libghostty-vt's osc module parses it; osc.rs validates it before anything acts on it:

  1. Host must be empty, localhost, or this machine's hostname. Anything else is a remote path we have no business opening — Phase 7 revisits this for SFTP mounts.
  2. Percent-decode, then reject any path that is not absolute.
  3. stat it. A path that does not exist or is not a directory is dropped silently — a shell can report a directory it deleted a moment ago.
  4. If it equals the pane's current directory, drop it. This is the common case, and it is what closes the feedback loop.
  5. Otherwise navigate the pane, without adding to the tab's back/forward history — the user did not press anything, so a shell cd should not fill up their history stack.

macOS fallback. With no shell integration, poll the foreground process's cwd with proc_pidinfo(PROC_PIDVNODEPATHINFO) on the idle timer. It is how Alacritty and Zed do it, it needs no setup, and it is why macOS gets working sync with nothing installed. There is no Windows equivalent; that asymmetry is the whole reason §7 exists.

Loop prevention

Forward sync writes a cd; the shell obeys and emits OSC 7; that OSC 7 would navigate the pane to where it already is. Step 4 above absorbs it. Belt and braces: each injected cd carries a generation number, and an OSC 7 matching the pending target is consumed rather than acted on. Both mechanisms are cheap; keep both, because step 4 alone breaks if the user navigates twice in quick succession.

Quoting

quote.rs is pure, has no dependencies, and gets the most tests in the crate — the fixture from Phase 1 already generates the names that break naive quoting: 255-character names, NFD, emoji, and anything with a quote in it.

Path quoting by shell
ShellRuleExample
bash / zsh / fishWrap in single quotes; replace each ' with '\''.it's → 'it'\''s'
PowerShellWrap in single quotes; double each '. Use -LiteralPath so globbing characters are inert.it's → 'it''s'
cmd.exeDouble quotes, and refuse any path containing " — cmd has no escape for it.—

Never interpolate a path into a command string without going through this module. The -- in cd -- is not decoration either: it stops a directory named -P from being read as a flag.

§7

Shell integration

What upgrades sync from good to exact — and, because Ferret spawns the shell itself, something the user never has to install.

The integration is two escape sequences emitted by the shell: OSC 7 on every directory change, and OSC 133 marks around the prompt (A before it, B at the start of user input, C when a command starts, D with its exit status). Together they give §6 exact answers to both of its hard questions — is the shell at a prompt, and has the user typed anything.

D-30 Shell integration is injected at spawn, not installed to disk.

D-24 already has Ferret choosing the shell binary and building its command line, which means it also owns argv and the environment. That is enough to load the integration for the session without touching a single file the user owns.

Injection mechanism per shell
ShellHow it loadsNotes
zshZDOTDIR → our dirOur .zshrc sources the integration, restores the user's ZDOTDIR, then sources their real files.
bash--rcfile / ENVPreserve the user's own --rcfile if one was configured, and source it from ours.
fishXDG_DATA_DIRS prependfish auto-loads <dir>/fish/vendor_conf.d/*.fish.
PowerShell-NoExit -Command ". <script>"Runs before the user's $PROFILE, which loads normally afterwards.

Because this is what the two implementations most worth copying both do. Ghostty injects automatically for bash, zsh, fish, elvish and nushell; VS Code injects for the same family and gates it behind one setting. Neither edits a user's rc file, and the reasons are good ones: nothing to install means the feature works on first launch, nothing to uninstall means removing Ferret removes Ferret, and nothing persistent means a crash mid-write cannot corrupt a shell profile. The earlier draft of this document had Ferret appending a marked block to ~/.zshrc; that is the worse design, and the only reason to reach for it is the fallback below.

We are already depending on Ghostty, whose integration scripts are MIT and therefore GPL-3.0 compatible. Adapt those rather than writing four from scratch — they are battle-tested against real prompt frameworks — renaming the GHOSTTY_ environment variables to FERRET_ so the two can coexist on one machine. PowerShell is the exception: Ghostty has no Windows support and ships no script for it, so that one we write, modelled on VS Code's.

When injection does not take

Three known cases, all of which degrade to Tier 2 rather than breaking:

  • macOS /bin/bash is version 3.2 and does not support the injection path. Anyone using Apple's stock bash rather than a Homebrew one gets Tier 2.
  • ZDOTDIR set in /etc/zshenv overrides ours, because system-wide zsh config wins. Rare, but it is the documented failure mode Ghostty hit.
  • A shell we ship no script for — nushell, elvish, cmd.exe, or anything set via the terminal.shell override.

D-27 A persistent install exists, but only as the fallback for those three cases.

When Ferret detects that injection did not take — the integration sets a sentinel variable, and its absence after the first prompt is the signal — the degraded sync control offers Load integration permanently. That appends a guarded block:

# >>> ferret shell integration >>>
[ -f "$HOME/.config/ferret/ferret.bash" ] && . "$HOME/.config/ferret/ferret.bash"
# <<< ferret shell integration <<<

Idempotent, and an uninstall removes exactly the marked block. The body lives in its own file so upgrading never touches the rc again.

Because the fallback has to exist — Tier 2 on stock macOS bash is a real configuration and we should be able to fix it rather than shrug. But it is now a repair for a detected problem rather than the normal path, which is a much easier thing to justify writing to someone's home directory for. Marked blocks are the convention every tool that does this uses (conda, nvm, Starship). Ferret never writes to a shell profile without the user clicking a button that says so.

D-31 TERM is xterm-256color, not xterm-ghostty.

Overridable via terminal.term for anyone who has installed the Ghostty terminfo entry and wants the extra capabilities advertised.

Because TERM travels. The moment someone sshes out of the panel, that value is what the remote host looks up — and xterm-ghostty is not in any stock terminfo database, which produces 'xterm-ghostty': unknown terminal type and a broken remote session. It is the single most reported friction point Ghostty has, with a small industry of blog posts about working around it. Ferret should not inherit a known papercut for capabilities most users will never exercise. This matters more here than in a standalone terminal, because F-13 in Phase 7 makes SSH a first-class path rather than something the user happens to type.

Whatever loads it, the script must be safe in a non-interactive shell — one that writes escape codes into an scp session breaks it. Every script guards on interactivity first.

F-12, which is mostly already built.

Colour resolution

  1. A cell with an explicit true-colour SGR uses it verbatim.
  2. An indexed colour 0–15 resolves through the palette's sixteen slots.
  3. 16–255 resolves through the standard xterm cube — computed, not stored.
  4. Default fg/bg come from the palette's foreground and background.

The panel background is the palette's, not cx.theme()'s. A terminal that repaints its background when the app theme flips has lost its own identity, and a Groknight-dark grid inside a light window is a legitimate thing to want.

The light-theme gap

Groknight is a dark palette and Ferret ships light and dark. F-12 needs a second palette before this phase closes, in the same JSON shape, defaulting when the app theme is light and the user has not pinned one. Both themes are first class — that gate from AGENTS.md applies here exactly as it did to the shell.

§9

Interaction contract

Every binding needs a Windows equivalent — the same gate Phase 1 held.

The governing principle: inside a focused terminal, keys belong to the terminal. A file manager that swallows CtrlC before the shell sees it is broken. Only the bindings below are intercepted; everything else is encoded and written to the PTY.

Intercepted bindings
ActionmacOSWindowsNote
Toggle panel⌘JCtrl JGlobal; works from the file pane too. Mirrored by a toolbar button at the right end of the title bar, which renders in the toolbar's active state while the panel is open — as the reference does.
Focus panel / return to pane⌃`Ctrl `Toggles focus between the two.
Copy⌘CCtrl Shift CWindows must use Shift — plain CtrlC is SIGINT and stays SIGINT.
Paste⌘VCtrl Shift VBracketed paste when the shell has asked for it.

Font size⌘+ / ⌘− / ⌘0Ctrl+ / Ctrl− / Ctrl0Terminal only; the interface does not scale with it.

Scroll page⇧PgUp / PgDnShift PgUp / PgDnPassed through when on the alternate screen, where the program owns them.

Mouse

  • When the program has enabled mouse reporting and Shift is not held, encode and forward. Shift is the universal escape hatch for selecting text over a program that wants the mouse; every terminal implements it and users expect it.
  • Drag selects; double-click selects a word; triple-click selects a line. Selection is in grid coordinates so reflow does not scramble it.
  • ⌘/Ctrl-click on a detected URL opens it. Detection runs over the snapshot, and OSC 8 hyperlinks take priority over pattern matching when present.
  • Scroll wheel moves scrollback; on the alternate screen it is translated to arrow keys, which is what makes the wheel work in less and man.

Focus

The panel is a focus region alongside the sidebar, path bar and file pane, and joins the Tab ring defined in ui-base.html §8. The cursor is drawn solid when focused and hollow when not — the same idea as --app-selected versus --app-selected-idle in the file pane. Opening the panel with ⌘J focuses it; closing it returns focus to the pane.

Drag and drop

Dropping a file from the pane onto the terminal inserts its quoted path at the cursor — through quote.rs, the same as sync. It does not execute anything. This is a small feature that makes the two halves feel like one application, and it costs almost nothing once quoting exists.

§11

Gates & budgets

What has to be true, and the numbers that say so.

Gates

  1. Build on both platforms before anything else. Step 1 exists to make D-22 falsifiable in a day. Every later step assumes it passed.
  2. Runs, not cells. As soon as pixels appear, confirm shaping scales with style runs. This is Phase 2's virtualisation gate.
  3. Never inject blind. No code path writes to the PTY on the app's behalf without passing the §6 preconditions. Injecting into a running program is this phase's equivalent of Phase 1's trash-before-delete rule.
  4. But do inject. The mirror of the rule above, and the easier one to lose sight of while writing the safety code. At a prompt with an empty input line, the cd goes out — no idle timer, no extra confirmation, no waiting for focus. A sync that is technically safe and practically never fires has failed at the thing Phase 2 exists to do.
  5. Keys belong to the terminal. Only §9's list is intercepted.
  6. Both themes, both platforms. Unchanged from Phase 1.
  7. Run it. cargo check proves nothing about a PTY.

The one that decides the phase

Open the panel, click through six folders in the sidebar and the listing at normal speed, and read the terminal. There should be six prompts, each in the folder you were looking at, arriving as fast as you clicked — and you should not have touched the terminal once. If that feels instant, F-11 works. Questions

All four are now answered. They are kept here with their reasoning rather than deleted, because the next person to disagree deserves to see what was weighed.

Q-05 · Q-10 How many sessions, and scoped to what? answered

D-28 — exactly one session per window, following the active tab. Not one per tab.

Because per-tab looked right until it was costed. Ten tabs would mean ten shells, ten scrollback buffers, and — the part that actually decides it — closing a tab would kill a shell that might have a build running in it. A file manager whose tab close button can destroy a running job is a bad file manager. Per-window has none of that: the terminal is a property of the window, the active tab's directory is what it follows, and switching tabs is just another navigation, handled by the same §6 safety rules that handle navigating inside one. It composes with the amber held state for free — if a build is running in tab A and you switch to tab B, the shell stays where it is, the header keeps showing A's directory, and the cd lands when the build finishes. Dolphin, the closest prior art with a decade of use behind it, is per-window too. The rest of the original answer stands: anyone who wants four shells has tmux, and tmux works here because this is a real terminal.

Q-09 Zig in CI, or vendored static archives? answered

D-32 — build from source; Zig is a CI and release-build dependency. No prebuilt archives in the repository. The contributor cost is paid down instead by feature-gating: ferret-terminal sits behind a cargo feature, so cargo check, cargo test and every other crate's workflow stay pure-Rust for anyone not working on the terminal. Document the exact Zig version, the pinned Ghostty commit, and GHOSTTY_ZIG_SYSTEM_DIR for network-free builds.

Because a committed .a or .lib is a blob nobody can verify against the source commit it claims to come from, in a GPL-3.0 repository where auditability is part of the point. It also has to be regenerated for three targets on every bump, by whoever happens to have the toolchain, which is how vendored binaries silently drift from their sources. Installing Zig in CI is one workflow step. The real cost was always the contributor who just wants to fix a sidebar bug, and the feature gate removes that cost entirely rather than trading it for an unverifiable artefact. Revisit only if contributor friction turns out to be real and measured.

Q-11 When do we prompt for shell integration? dissolved

Never, in the normal case. D-30 injects the integration at spawn, so there is nothing to install and nothing to ask about. The prompt survives only as the repair path in D-27, offered when Ferret has detected that injection did not take.

Because the question was a false choice created by the earlier design. Once the shell is spawned by us, asking permission to edit a file we no longer need to edit is a dialog with no purpose. The best answer to "when should we interrupt the user about this" is usually to find the design where you do not have to.
