Detailed implementation plan · F-13 · F-20–F-23 · 3 Sep 2026

One click to connect. Drag to transfer.

Saved SSH connections in the sidebar, an SFTP mount that browses like a local folder, and a guided “Send to” transfer from the context menu — built in-process with russh, with no kernel mount, no second SSH configuration to maintain, and no frame ever blocked on a round trip.

Decision summary

Executive verdict

Build product Phase 7 as one GPUI-free service crate, ferret-remote, holding four things: saved connection records, live SSH sessions, an SFTP Vfs backend, and a transfer queue. The browser reaches all of it through the Vfs trait it already uses, so remote folders arrive as folders rather than as a bolted-on transfer client. Interactive SSH keeps shelling out to the system ssh binary; only file browsing is in-process.

Recommended baselinerussh 0.63 + russh-sftp 2.4 for transport, authentication and the SFTP subsystem; keyring 4.2 for the OS keychain; ssh2-config 0.8 to import hosts from ~/.ssh/config; the system ssh binary for interactive shells; a two-thread Tokio runtime confined to the remote crate. All Apache-2.0 or MIT — compatible with distributing Ferret under GPL-3.0.
R-D01

ferret-remote owns everything remote and knows nothing about GPUI. Connection records, session lifecycle, host-key policy, the SFTP backend and transfers live behind one crate boundary, matching how ferret-git, ferret-search and ferret-terminal are split today. The UI depends on it; it depends on ferret-vfs only.

R-D02

A router in ferret-vfs becomes FerretState.fs. Today that field is a concrete LocalFs, copied into every task that lists, watches, probes or mutates. A Router that itself implements Vfs and dispatches per VfsPath keeps all of those call sites intact and is the single change that makes a mount browsable. Local paths keep a direct LocalFs call — no dynamic dispatch is added to the hot listing path.

R-D03

One Tokio runtime, two worker threads, owned by ferret-remote. russh is Tokio-based and Ferret is smol + GPUI executors; the bridge is explicit rather than accidental. The runtime is created on first connect, never used for CPU work, and never grows with the core count — Ferret already runs three pools and the fourth must not size itself like the others (AGENTS.md, “one walker per job”).

R-D04

Listings stream from the raw SFTP handle, not from a collected iterator. opendir followed by repeated readdir yields one SSH_FXP_NAME response per round trip, and each response becomes exactly one DirEntryBatch. Attributes ride along with the names, so the backend declares metadata_in_listing: true and a 10,000-entry remote directory needs no second pass.

R-D05

“Send to” transfers over SFTP on the already-authenticated session — not scp(1), not the legacy SCP wire protocol. OpenSSH 9.0 itself switched scp to use SFTP by default; the old protocol is deprecated, gives no usable progress granularity, and a subprocess would authenticate a second time. The user-facing name stays “Send to…”, the transport is SFTP.

R-D06

MountId is persisted per connection record, not handed out per launch. VfsPath::preference_key() formats remote paths as {mount}:{path}, so a counter reset at startup would silently attach one server’s per-folder view preferences to a different server after a restart. The id is allocated once, stored in the connection record, and never reused.

R-D07

Connections live in their own connections.json; secrets live in the OS keychain; neither ever holds the other’s data. The settings file stays a small, hand-editable document (D-12/D-21) and gains only the handful of remote tunables that code actually reads (D-41). Passwords and key passphrases are never written to any file Ferret owns.

R-D08

Host keys are verified on every connection against the user’s own known_hosts. An unknown host raises an explicit fingerprint dialog before anything is sent; a changed host key is refused outright with no “continue anyway” button in the first release. Ferret must never be the SSH client that made key checking optional.

R-D09

Interactive SSH shells out to the system ssh (D-07), and directory sync is off by default for remote sessions. The remote shell dialect is unknown, so the only line Ferret will ever inject is the POSIX cd -- '…' form, behind the existing alternate-screen and idle guards.

R-D10

Capabilities are negotiated, never assumed. atomic_rename is declared only when the server advertises posix-rename@openssh.com; watch is always false, because SFTP has no change notification and polling a remote directory on a timer is a cost the user did not ask for.

R-D11

Remote maps use a seeded hasher. The workspace uses foldhash precisely because folder indices key on names read from the user’s own disk. Directory entries from a remote server are attacker-choosable input; anything keyed on them takes std’s SipHash instead. This is written down in Cargo.toml already — this is the feature that triggers it.

R-D12

Root-enabled mounts (F-23) ship last, or not at all in this phase. Everything else is reversible; that one hands a GUI unrestricted write access to a remote machine. It stays behind a typed confirmation, a permanent visual marker, and a refusal to restore from session state.

Included beyond the reference

  • Import from ~/.ssh/config, so nobody retypes hosts that already exist (explicit F-20 behaviour).
  • Host-key fingerprint confirmation and a refusal path for changed keys.
  • Connection state that survives navigation: mounts stay warm, and a dropped link reconnects once before it complains.
  • Capability badges — remote folders honestly show what they cannot do (no trash, no watcher, no content search) rather than failing at the end of a gesture.
  • Transfers in both directions. The reference shows local→remote; a remote mount makes remote→local a drag, and refusing it would be arbitrary.

Non-goals for first delivery

  • No kernel-level mount (D-06). Other applications cannot see a Ferret mount, and “Open With” on a remote file is deferred until a download-open-upload cycle is designed properly.
  • No SSH configuration reimplementation. Jump hosts, Match blocks, certificate authorities and MFA prompts belong to the user’s own ssh; where the in-process client cannot honour one, Ferret says so instead of half-supporting it.
  • No port forwarding, no remote command palette, no rsync-style delta sync, no S3/WebDAV (F-24/F-25 are Phase 8).
  • No remote content search in this phase. Filename search over a mount is capability-gated per PS-Q05; content search stays local until a remote grep path is designed.
  • No password-only convenience shortcuts: no “save password” checkbox that writes to disk, no host-key bypass flag, no agent-forwarding by default.

Send to · the guided transfer

Right-click a selection → Send to → a submenu of saved connections, built in pane/menu.rs beside Cut/Copy. Choosing one opens a small destination sheet: the connection, a remote directory field pre-filled with the last destination used for that host, a Browse button that lists the remote tree, and the conflict policy for the transfer (Skip · Replace · Keep both). Dropping a local selection onto a connected sidebar row is the same operation with the destination pre-answered — the sidebar already accepts DraggedPaths drops, so this is a new destination kind rather than a new gesture.

Direction is symmetric.Dragging out of a remote pane to a local folder is a download; dragging in is an upload; dragging between two mounts is refused in v1 with a clear reason (it would need a server-to-server relay through the client, which is a different performance story and belongs with F-05 dual pane).

The runtime bridge

russh is built on Tokio; Ferret runs GPUI’s executors and smol. This is the single most important boundary in the crate, because getting it wrong shows up as a deadlock under load rather than as a compile error.

  • One runtime. A OnceLock<Runtime> in runtime.rs, built with worker_threads(2) and enable_io + enable_time only. Two threads, fixed: this work is latency-bound, not CPU-bound, and sizing it to the core count would put a fourth core-count-sized pool next to ferret_vfs::pool, smol’s blocking pool and GPUI’s executor.
  • One direction of ownership. Session objects live inside the runtime. The rest of Ferret holds only a handle that sends requests; no russh type ever crosses the crate boundary (the same rule ferret-terminal applies to its VT engine, D-23).
  • Request/response uses futures::channel::oneshot. An async fn in the Vfs impl spawns the work onto the runtime with Handle::spawn and awaits the oneshot on whichever executor called it. No block_on anywhere, ever — that is what would freeze a frame.
  • Streams use a bounded async-channel. read_dir returns a stream fed by a runtime task, with capacity LISTING_BUFFER. Cancel-by-drop falls out for free: the receiver drops, the next send fails, the task returns, and the SFTP handle is closed. That is the Vfs cancellation contract satisfied by construction rather than by a token somebody has to remember to check.
  • Shutdown. Disconnecting a mount drops its session handle; the runtime task closes the channel and the connection. Quitting drops the runtime after the config flush, with a short bounded wait so an in-flight transfer can abort cleanly.
Verify this before building on it.Tokio is already in Cargo.lock at 1.53 through zed-reqwest, so the dependency is an edge to something already compiled rather than a new stack — but the features Ferret needs (rt-multi-thread, net, io-util, time) are additive across the graph, and Cargo unions them. Confirm the resulting binary size and startup cost before R-2 closes; a lazily created runtime must cost nothing until the first connection.

Session model

One connection record can be mounted once. A mount owns: the TCP connection, the authenticated SSH session, one SFTP channel, the attribute cache, and the reconnect state machine.

TransitionTriggerBehaviour
Idle → DiallingSidebar click, drag-drop onto the row, or a navigation to a path with that MountIdTCP connect with a bounded timeout; host-key check before any authentication attempt.
Dialling → AuthenticatingHost key acceptedAgent identities first, then the configured key, then keyboard-interactive/password if the server offers them. Each attempt is reported so a failure names the method that failed.
Authenticating → MountedAuthResult successOpen the SFTP subsystem, read the server’s extension list, canonicalize . to get the home directory, publish Capabilities, register in the router.
Mounted → DegradedKeepalive miss, channel EOF, or an I/O error on any requestIn-flight requests fail with a disconnect error naming the mount; one automatic re-dial after a short backoff; the UI banner appears only if that fails.
Degraded → MountedRe-dial succeedsCaches are dropped wholesale — a reconnect proves nothing about what changed on the other side. Open listings refresh; the user keeps their selection and scroll position.
Any → UnmountedDisconnect, record deleted, or quitTabs inside the mount show an unmounted state with a Reconnect action rather than closing themselves.

Keepalive: a server-side SSH_MSG_IGNORE-class keepalive every 30 seconds with a 3-miss timeout, so a laptop that slept for an hour discovers a dead link on wake rather than on the user’s next click. Machine sleep is the common case, not the exotic one.

The one structural change

The routing change

Everything else in this plan is additive. This part touches existing code, so it is specified precisely.

Today FerretState.fs is a LocalFs — a zero-sized Copy type — read out of the global and moved into background tasks in folder/listing.rs (listing, watching, probing), folder/expansion.rs (subtree listing and metadata batches) and browser/mutations.rs (create, rename, copy, remove). Replacing the field’s type with a Router that is itself Vfs keeps every one of those call sites compiling and gives them remote support in the same change.

// crates/ferret-vfs/src/router.rs
#[derive(Clone, Default)]
pub struct Router {
    local: LocalFs,
    mounts: Arc<ArcSwap<HashMap<MountId, Arc<dyn Vfs>>>>,   // read-mostly; swapped on mount/unmount
}

impl Router {
    pub fn mount(&self, id: MountId, backend: Arc<dyn Vfs>);
    pub fn unmount(&self, id: MountId);
    pub fn backend(&self, path: &VfsPath) -> Option<BackendRef<'_>>;
}

#[async_trait]
impl Vfs for Router {
    fn read_dir(&self, dir: &VfsPath, detail: ListingDetail) -> ReadDirStream {
        match dir {
            VfsPath::Local(_) => self.local.read_dir(dir, detail),          // no dyn dispatch
            VfsPath::Remote { mount, .. } => match self.lookup(*mount) {
                Some(fs) => fs.read_dir(dir, detail),
                None => once(Err(VfsError::NotMounted { mount: *mount })),
            },
        }
    }
    // rename/copy additionally require both sides to resolve to the same backend
}

Rules the router enforces

  • Local is not slowed down. The Local arm calls LocalFs directly. The ArcSwap load happens only on the remote arm, so the 200,000-entry listing benchmark is unaffected — and cargo xtask bench must confirm that, not assume it.
  • Two-path operations must agree. rename and copy take a source and a destination; if they resolve to different backends the router returns a new VfsError::CrossBackend naming both sides, and the UI routes the gesture to the transfer queue instead. Silently copying byte-by-byte through the Vfs trait would be a hidden network transfer with no progress and no cancel.
  • Capabilities are the mount’s, not the router’s. Router::capabilities() answers for local disk; the pane asks the backend for the folder it is actually showing. That is a small change at the two call sites that read capabilities today (folder/listing.rs and the sort profile).
  • An unmounted id is an ordinary error, not a panic. Session restore, a stale tab and a deleted record all produce paths whose mount no longer exists.

Backend contract

SFTP backend contract

The Vfs trait was designed for this moment: async throughout so a slow call is a slow call rather than a frozen window, listings that stream so a large remote directory paints immediately, and capabilities declared up front so the UI can disable rather than fail (D-17). What follows is what each method actually does over SFTP v3.

Caching, and why it is small

  • Attribute cache: (MountId, path) → Metadata, short TTL (default 5 s), invalidated by any mutation Ferret performs on that path or its parent. It exists to stop the column view and the path bar from re-stat-ing what the listing just delivered — not to pretend the server is local.
  • Listing cache: the most recent N directories per mount (default 16), used for back/forward navigation and column-view ancestors. Dropped wholesale on reconnect, on Refresh, and on any mutation inside that directory.
  • What is never cached: file contents. Previews re-read; there is no shadow copy of the remote tree on disk in this phase.
  • Column view is the pressure test. It opens several directories at once; over a high-latency link that is several concurrent opendir sequences. Cap concurrent listings per mount (default 3) and let the cache absorb the rest, or the mode becomes unusable at 150 ms RTT.

Error mapping

RemoteError is the crate’s own thiserror enum, and every variant names its subject. At the trait boundary it maps into VfsError, which needs two new variants — both carrying enough to be shown to a person unedited:

VfsError::NotMounted   { mount: MountId }                 // "That server isn't connected."
VfsError::CrossBackend { from: VfsPath, to: VfsPath }     // routed to the transfer queue instead

SSH_FX_NO_SUCH_FILE        -> VfsError::NotFound
SSH_FX_PERMISSION_DENIED   -> VfsError::PermissionDenied
SSH_FX_FILE_ALREADY_EXISTS -> VfsError::AlreadyExists
SSH_FX_NO_SUCH_PATH/…      -> VfsError::Io { action, path, source }   // verb + path preserved
disconnect / auth loss     -> VfsError::Io with a message naming the host, then a mount-level banner
Do not reuse CrossVolume for a remote destination.Its text says the item “has to be copied rather than moved”, which is true for two local volumes and misleading for a server: the copy is a network transfer that can take an hour. That is why CrossBackend is its own variant.
F-22

Send to · transfers

F-22 depends on F-60, the operations queue, which does not exist yet. Rather than block Phase 7 on Phase 6, this plan ships a deliberately small queue inside ferret-remote with the interfaces F-60 will need, and states plainly that it is temporary.

A stated deviation from D-09.“All bulk mutation goes through the operations queue” exists so no feature grows its own private copy loop. The interim queue here is one job type (transfer), one progress shape and one cancel path, deliberately shaped so that when ferret-ops lands it absorbs this as a job kind and this module is deleted rather than adapted. If F-60 is built first, skip this entirely — that is the better order if both are in scope.

What a transfer does

  1. Plan. Walk the local selection with jwalk (D-34: bulk file work, no ignore semantics) to a file list with sizes. A remote source walks over SFTP with the same concurrency cap as a listing. The plan is shown before anything is sent: n files, total bytes, destination.
  2. Resolve conflicts up front. One lstat per destination path, pipelined. The chosen policy — Skip, Replace, Keep both — applies to the whole job, decided before the first byte moves, not per file mid-flight.
  3. Create directories, then stream files. Uploads open the destination as name.ferret-part, write pipelined 32 KB chunks with a window of 16 outstanding requests, fsync if the server advertises fsync@openssh.com, then rename into place. A cancelled or failed transfer leaves the part file, which the next attempt overwrites — never a truncated file under the real name.
  4. Preserve what can be preserved. Modification time via setstat; the executable bit; nothing else. Ownership is not attempted.
  5. Report. Per-file and total progress, throughput, ETA, and a final summary listing anything skipped and why. Errors on one file do not abandon the job unless the user asks.

Rules

  • Two concurrent files per mount by default, each with its own pipelined window. More connections do not make one link faster and do make the server’s logs worse.
  • Never write outside the destination directory. When downloading, every remote name is validated before it is joined onto a local path: no separators, no .., no absolute component, no Windows reserved name (CON, NUL, COM1), no trailing dot or space. A malicious or broken server must not be able to place a file anywhere it likes on the user’s disk.
  • Symlinks are copied as links, not followed, unless the user asks — following turns a link loop into an infinite transfer.
  • Cancel is immediate and observable: dropping the job closes the file handles and the in-flight requests stop within one round trip.
  • The queue survives navigation and does not hold the window thread. Its state lives beside the mount, not on a view.
F-13

The SSH terminal that follows the mount

D-07 is unchanged: interactive sessions run the user’s own ssh. Jump hosts, MFA, agent forwarding config, Match blocks and password prompts then work exactly as they do in their terminal, because it is their ssh.

  • Spawn. TerminalSession::spawn currently builds a shell command with a local cwd. It gains a sibling that takes an explicit program and argument list, so the PTY, engine, reader thread and snapshot machinery are shared and only the command differs. The command is exactly what the dialog’s copy button shows.
  • Landing directory. ssh -t host -- cd '<dir>' && exec "$SHELL" -l lands in the browsed folder. If that fails, the session still opens at the remote home — a shell that opened in the wrong directory is far better than one that did not open.
  • Sync. terminal_synced_to and terminal_pending_sync widen from PathBuf to VfsPath. A remote sync only ever emits the POSIX form cd -- '…' — leading space, single-quote escaping, -- guard — because the remote shell dialect is genuinely unknown. ShellKind::detect classifies a local executable path and must not be asked about a remote host.
  • Safety. The existing guards hold unchanged: nothing is injected while the alternate screen is active, and only after an idle window. A remote session adds one more: sync defaults to off, because injecting text into a session the user may have su-ed or opened an editor in deserves an explicit opt-in.
  • Availability. The network button is disabled with a reason when ssh is not on PATH. On Windows that is a real case — OpenSSH Client is an optional feature — so the message points at how to install it rather than saying “failed”.
Non-negotiable

Security model

This is the feature where a mistake costs someone their server, not their afternoon. Every item here is a requirement, not a preference.

Host keys

  • Every connection verifies the server key against the user’s known_hosts (~/.ssh/known_hosts, and %USERPROFILE%\.ssh\known_hosts on Windows) via russh::keys::known_hosts. Hashed entries are supported by that module and must keep working.
  • Unknown host: a dialog showing host, port, key algorithm and the SHA256 fingerprint in the same format OpenSSH prints, so it can be compared against what the administrator published. Accepting writes the entry with learn_known_hosts_path. Default focus is Cancel.
  • Changed key: refuse. Show the stored fingerprint, the offered one, and the file and line to inspect. No override control ships in v1; the user can edit their own known_hosts if they genuinely rekeyed, which is the same friction OpenSSH imposes and for the same reason.
  • Verification happens before any authentication attempt, so a password or an agent signature is never offered to an unverified host.

Credentials

  • Agent first. SSH_AUTH_SOCK on macOS; the \\.\pipe\openssh-ssh-agent named pipe on Windows. Agent support on Windows is the item most likely to need a fallback — confirm it in R-1 and, if it is not usable, fall back to key files and say so in the UI rather than silently failing.
  • Key files. The record’s explicit path, else the standard identities. Encrypted keys prompt for the passphrase at connect time. “Remember” is opt-in and stores the passphrase in the OS keychain (keyring 4.2: Keychain on macOS, Credential Manager on Windows) under a service name that names Ferret and the connection.
  • Passwords are prompted per connection and never written anywhere by default. If “remember” is checked, keychain only.
  • Never in a file Ferret writes. Not settings.json, not connections.json, not a log line, not an error message. The record stores a reference to a keychain item, never a secret.
  • Never in a panic. Debug is implemented by hand for anything holding a secret so a backtrace cannot print one.

Treating the server as untrusted input

  • Directory entry names are validated before they become paths (see Transfers) — and before they become map keys, which is where R-D11’s seeded hasher applies.
  • Names are UTF-8-checked; invalid sequences are shown with replacement characters and the raw bytes preserved for the protocol, never round-tripped lossily into a request.
  • Attribute blocks are bounds-checked: a size or timestamp far outside a sane range is displayed as unknown, not used to size an allocation.
  • Response sizes are capped. A server that answers a 4 KB read with 400 MB gets its channel closed.

Root mounts (F-23)

Kept exactly as the product plan describes, and last in the sequence: an unmistakable typed confirmation, a permanent marker on the mount and in the path bar, no automatic enablement from restored state, and documentation that says plainly it needs passwordless sudo for the SFTP subsystem on the remote host. If the schedule slips, this is the item to drop — F-20 through F-22 are complete without it.

Gated build order

Delivery sequence

Each stage leaves the workspace runnable and each gate is checkable by reading a diff or running a command. Do not advance past a failing gate.

R-0

Router and mount identity

Add ferret_vfs::Router, the NotMounted and CrossBackend variants, and persistent MountId allocation. Switch FerretState.fs to the router with no backends registered. Gate: just test and cargo xtask bench show no local regression; just budget unchanged; a test proves a remote preference key is stable across a simulated restart.

R-1

Crate skeleton, runtime bridge, connect

Create ferret-remote with its errors.rs/config.rs, the single Tokio runtime, the session state machine, host-key verification and agent/key authentication. No UI. Gate: an integration test connects to a containerised sshd, refuses an unknown host, refuses a changed key, and drops the runtime cleanly; nothing calls block_on.

R-2

SFTP backend: read-only

read_dir streaming from the raw handle, metadata, probe, exists, canonicalize, read, negotiated capabilities, the attribute and listing caches. Gate: a 10,000-entry remote directory streams its first batch in under 3 RTT and never materialises before yielding; capability negotiation is asserted against a server without posix-rename.

R-3

Connections: store, dialog, sidebar (F-20)

connections.json, keychain access, ~/.ssh/config import, the New Connection dialog under Root, the Connections sidebar group with its five states, and the live ssh … command line. Gate: both themes at default and minimum window size; keyboard-only creation and editing; the generated command is byte-identical to what F-13 will spawn; deleting the app’s config directory loses no secrets and breaks nothing.

R-4

Browse a mount end to end (F-21)

Click-to-connect, navigation, path bar and breadcrumb for remote paths, capability-driven menu disabling, the unmounted and reconnecting tab states, per-folder view preferences keyed correctly. Gate: browse a real server over an 80 ms link for ten minutes without a frame drop or a blocked window; sleep the machine and confirm the mount detects and recovers.

R-5

Remote mutations

Create folder/file, rename, delete-permanently with its own confirmation, copy within a mount where the server supports it. Cache invalidation on every path. Gate: every mutation refreshes exactly the affected rows without a full re-list; “Move to Trash” is absent rather than failing; a permission error names the path and the operation.

R-6

Send to · transfers (F-22)

The interim queue, the context-menu submenu, the destination sheet, sidebar-row drop, both directions, part-file atomicity, conflict policy, progress and cancel, name sanitisation on download. Gate: a cancelled 1 GB upload leaves no file under its final name; a hostile-name test suite cannot write outside the destination; throughput meets the budget.

R-7

SSH terminal (F-13)

The command-spawning session variant, the terminal header button, VfsPath-based sync with the POSIX-only injection rule and sync defaulting to off, missing-ssh detection on Windows. Gate: nothing is ever injected into an alternate-screen session; the spawned command matches the dialog’s copy button; the panel degrades with a reason when ssh is absent.

R-8

Root mounts, hardening, docs (F-23)

Acceptance

Verification checklist

Automated

  • Unit: path validation (separators, .., absolute, reserved Windows names, trailing dot/space), SFTP status → VfsError mapping, attribute → Metadata conversion including implausible values, capability negotiation from an extension list, connection record round trip, ~/.ssh/config import including unknown keywords and Include, the generated ssh command line, MountId allocation and preference-key stability.
  • Integration against a containerised sshd: connect, unknown host accept and refuse, changed host key refusal, agent and key auth, encrypted key with and without passphrase, listing at every directory shape, unreadable directory, symlink loop, invalid-UTF-8 names, mutation round trips, transfer in both directions, cancellation mid-file, part-file recovery, disconnect mid-listing and mid-transfer, reconnect.
  • Router: local dispatch unchanged, unmounted id errors, cross-backend rename and copy refused with both paths named, capabilities answered per mount.
  • Cancellation and lifetime: dropping a listing stream closes the handle within one round trip; dropping a mount ends its tasks; no task outlives the runtime; no block_on in the crate (a grep test is fine and is the kind that keeps being true).
  • Hostile-server suite: malformed packets, oversized responses, names with separators, a readdir that never ends, a server that accepts and then stops responding.
  • Performance: the budgets above, checked in as a runnable target with machine-readable output, plus the existing cargo xtask bench and just budget as regression guards.

Manual, on both targets

  • Create, edit, duplicate and delete a connection by keyboard alone; verify light and dark at 1180×760 and at the minimum window size.
  • Connect to a real server; browse a large directory; sort by every column; switch to column and icon views; rename and delete; confirm nothing blocks.
  • Pull the network cable mid-listing and mid-transfer; sleep and wake the machine; confirm the recovery path and that selection and scroll survive.
  • Send a folder of mixed files to a server and back again; compare checksums; confirm timestamps and the executable bit.
  • Open the SSH terminal, navigate the pane, confirm the session follows only when sync is enabled and never during a full-screen program.
  • Quit with a transfer running; confirm it aborts cleanly and the config flush still happens.
Feature-level done conditionA saved connection mounts in one click; a remote folder browses, sorts, renames and deletes like a local one over a high-latency link with no frame ever blocked; “Send to” moves a directory of files in either direction with real progress and a clean cancel; the SSH terminal lands in the folder being browsed; and no secret, host key or hostile filename can leave the boundary this plan draws around it.
Honest uncertainty

Risks and open questions

R-Q01 · Is Windows SSH-agent support usable through russh?

The agent client is written for Unix sockets; Windows uses a named pipe. Resolve in R-1 by testing against the OpenSSH agent service. If it does not work, key files cover the common case, the UI says agent authentication is unavailable on Windows, and this becomes a tracked follow-up — not a silent difference between platforms.

R-Q02 · What happens to ProxyJump and Match blocks?

Interactive SSH honours them for free (it is the user’s ssh). The in-process browser does not. Recommendation: import ProxyJump into the record, and in v1 mark such a connection “terminal only” with the reason stated, rather than half-implementing a jump host. A direct-tcpip channel through an intermediate session is the correct implementation later, and russh’s connect_stream is the hook for it.

R-Q03 · Should a mount be restored at startup?

Recommendation: restore the tab and its path, but do not dial until the user acts. A file manager that opens three password prompts on launch trains people to type passwords without reading the dialog. Root mounts never restore at all (R-D12).

R-Q04 · How does search behave on a mount?

PS-Q05 left this open. Recommendation for this phase: the scope badge says “filename only, live” and the walk runs over SFTP with a hard depth and result cap; content search is disabled with a reason. A remote grep over an exec channel is a real option and is a separate decision with its own security surface.

R-Q05 · Where does the interim transfer queue live if F-60 lands mid-phase?

Recommendation: build R-6 against the job/progress/cancel shape ferret-ops will need, so absorbing it is a move rather than a rewrite. If F-60 is already in flight when R-6 starts, skip R-6’s queue entirely.

Primary risks

  • Latency leaking into the frame. The single failure that would make this feature feel broken. Mitigated by the zero-network-calls-on-render gate, by capabilities that disable rather than fail, and by testing at 80 ms rather than on loopback.
  • Runtime bridge deadlock. Two executors and a channel between them is where a hang hides. Mitigated by one direction of ownership, no block_on, bounded channels everywhere, and a test that drops mounts under load.
  • Silent security downgrade. A “continue anyway” button, a remembered password in a JSON file, or a fingerprint dialog nobody reads. Mitigated by R-D08, by keychain-only secrets, and by defaulting destructive dialogs to Cancel.
  • Hostile or broken server responses. Path traversal on download, unbounded allocations, hash-collision floods. Mitigated by validation before any join, response caps, and R-D11.
  • Scope creep into a full SSH client. Port forwarding, jump hosts, tunnels and remote execution are each a feature. The line: Ferret browses and transfers files, and hands everything interactive to ssh.
  • Dependency surface. russh is well maintained but young relative to OpenSSH, and a crypto library is a serious dependency. Pin deliberately, watch advisories, and keep cargo deny in the release gate.
  • Two ways to reach one server. The in-process client and the user’s ssh can disagree — different key, different host, different jump. Mitigated by generating the terminal command from the same record the browser dialled with, and by showing it in the dialog so a divergence is visible rather than mysterious.
