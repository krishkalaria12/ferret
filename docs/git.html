§1

What this is

The build document for §4.6 of plan.html, in the same relationship to it that terminal.html has to §4.2.

The plan catalogues git as four feature entries and eleven lines of behaviour. That was enough to schedule the work. It does not say which of git's twelve status formats to parse, what happens to a badge when a directory is untracked and collapsed, what a push does when the credential helper wants a passphrase and there is no terminal attached, or how a status map for a hundred thousand changed files avoids becoming a per-frame scan. This document is that half.

In scope: F-50 (branch, counts and ahead/behind in the status bar), F-51 (per-file status in the listing, including a rolled-up indicator on directories), F-52 (the commit dialog), F-53 (pull and push, with git's own errors surfaced unedited).

Not in scope, deliberately: per-hunk staging, a diff viewer, a log or history browser, branch creation, merge conflict resolution, rebase, stash management, submodule recursion, and anything else that would make Ferret a git client rather than a file manager that knows about git. The line is the one plan.html draws at F-52: the commit dialog is deliberately blunt, and everything past it belongs in the terminal panel that is already docked six pixels below it.

The feature is the status bar, not a panel

"Git panel" is a convenient name and a misleading one. Nothing new docks, nothing new resizes, and no region of ui-base.html §4 changes size. What ships is a segment at the right of the existing 24 px status bar, a modal dialog, and a badge inside the Name cell the listing already draws. If any part of this design starts asking for its own dock, it has left the scope above.

What Phase 1 and 2 already give us

  • A status bar (browser/render.rs) with a left slot in use and a right slot empty.
  • A per-directory notify watcher with a 150 ms debounce and a Desynced recovery contract (ferret_vfs::watch) — which is the refresh trigger this feature needs and does not have to invent.
  • A background executor, and the discipline that nothing filesystem-shaped runs on the window thread.
  • Arc<ArcSwap<T>> as the established shape for read-every-row-every-frame state, from ColumnLayout.
  • A docked terminal in the same directory, which is the escape hatch for everything this feature deliberately cannot do.
§2

The engine decision

plan.html settled this as D-04. This section is why it survives contact with the implementation, and what it costs.

OptionWhat it givesWhy not
git2 (libgit2) In-process status, no subprocess, structured errors. A C toolchain and a vendored build on both targets. And the decisive one: it does not speak to the user's credential helper, SSH agent, 2FA or signing config. A push that works in their terminal and fails in Ferret is worse than no push.
gix (gitoxide) Pure Rust, no C toolchain, genuinely fast status. Same credential problem, plus an API still moving under us. It would also mean Ferret's idea of "changed" could drift from what git status prints in the panel below — two sources of truth, six pixels apart.
the git binary Credential helpers, SSH agents, 2FA, signing, hooks, includeIf, core.fsmonitor, the untracked cache and every future git feature, all for free and all identical to what the terminal panel shows. A runtime dependency on git being installed, a process spawn per query, and a wire format to parse. All three are addressed below.
D-43 git is optional at runtime, and its absence is silent.

A missing git is not an error condition — most folders are not repositories and most users of a file manager are not developers. The probe runs once per process, is cached, and on failure the entire feature simply never renders. No banner, no toast, no settings key that has to be turned off. The one place it is mentioned is the tooltip on a repository whose status could not be read.

D-44 Every invocation is non-interactive, and says so to git.

Ferret spawns git with no controlling terminal. Left alone, a credential prompt or an SSH passphrase request would block the child forever and the operation would hang with no output. Every spawn therefore sets GIT_TERMINAL_PROMPT=0, GIT_OPTIONAL_LOCKS=0 for read-only queries, GIT_EDITOR=true and GIT_PAGER=cat, and carries a timeout. When git needs a human, it fails fast and Ferret shows its message unedited — which is honest, and which points at the terminal panel where the human can answer.

D-45 One query, one process. Never a process per row, per file or per frame.

--porcelain=v2 --branch answers branch, upstream, ahead, behind, staged, unstaged, untracked and conflicted in a single invocation. This is the rule that keeps the feature from becoming the "easiest place in the whole app to destroy scrolling performance" that plan.html warns about under F-51.

§3

Panel anatomy

Two surfaces: a segment in the status bar, and one modal dialog.

The status bar segment

It occupies the right end of the existing h24 status bar, is absent entirely outside a repository, and never changes the bar's height. Left to right:

branch chip
Branch glyph plus the branch name, or the short OID in a detached HEAD. Truncates at 160 px. Tooltip carries the full name, the upstream, and the repository root.
new
change count
A filled dot and a number: how many files differ from HEAD, staged and unstaged together, plus untracked roots. Absent when the tree is clean.
new
ahead / behind
↑n and ↓n, each shown only when non-zero, and neither shown at all without an upstream.
new
Pull
Ghost button. Disabled while any git action is in flight.
new
Push
Ghost button. Present only when there is an upstream and something to push.
new
Commit…
Ghost button, ellipsis because it opens a dialog. Disabled when there is nothing to commit.
new

Every number in the segment uses theme::tabular_numerals(), for the same reason §7 of ui-base.html gives for the Size column: these counts change under a watcher without the user doing anything, and proportional figures make the buttons beside them jump sideways when 9 becomes 10.

The segment must never be the reason the status bar reflows

The left slot holds "7 items · 1 selected — 22 KB" and the two share one row. The git segment is flex_shrink_0 and the item count truncates before it does, because the item count is re-derivable by looking at the list and the branch name is not.

The commit dialog

A 460 px modal on the window's Root layer, which is the only place a dialog renders (the bootstrap contract in AGENTS.md). Content, top to bottom:

  • A title row: a filled circular check glyph in the accent, Commit Changes, and the repository's directory name beneath it in muted text.
  • Message — a Textarea, five rows, autofocused, with the library's focus ring. Empty by default; Ferret does not pre-fill commit messages.
  • A checkbox: Stage all changes first (git add -A), checked by default, and disabled with an explanatory tooltip when everything is already staged.
  • A footer: Cancel (outline) and Commit (primary). Commit is disabled while the message is blank or a commit is in flight.

⌘↵ / Ctrl↵ commits from inside the message field; Esc cancels. Plain ↵ inserts a newline — this is a commit message, and the body matters.

D-46 The dialog is a view entity, not a closure.

window.open_dialog takes an Fn builder that runs on every frame the dialog is up. Holding the message text or the checkbox state in that closure would mean rebuilding the input every frame and losing the caret. The dialog therefore owns an Entity<CommitDialog> created before it opens; the builder's only job is to mount that entity as a child.

§4

Crate architecture

One new service crate, GPUI-free and testable without a window.

crates/ferret-git/
├── src/lib.rs        // public surface: Repository, RepoStatus, FileStatus, ops
├── src/errors.rs     // GitError + Result<T, E = GitError> (AGENTS.md)
├── src/config.rs     // timeouts, output caps, the badge cut-off
├── src/command.rs    // the ONLY module that spawns a process. D-44 lives here.
├── src/discover.rs   // rev-parse --show-toplevel --absolute-git-dir
├── src/status.rs     // RepoStatus + the porcelain v2 parser (pure, over bytes)
└── src/ops.rs        // stage_all, commit, pull, push — each returns git's own text

crates/ferret-ui/src/browser/
├── git.rs            // GitPanel: discovery, refresh scheduling, the snapshot handle
├── git_status_bar.rs // the status-bar segment (F-50) and its buttons (F-53)
└── commit_dialog.rs  // CommitDialog entity (F-52)

The layering rule, applied

  • ferret-git depends on ferret-vfs (for VfsPath, because "is this a local path?" is exactly the question discovery has to ask first) and on thiserror, smol_str and foldhash. It does not depend on gpui, gpui-component or ferret-ui.
  • Its parser is a pure function from &[u8] to RepoStatus. That is what makes the format's sharp edges — renames, quoted paths, missing branch.ab, detached HEAD, an unborn branch — testable from a byte literal with no repository and no window, which is where nearly all of this crate's tests live.
  • Anything that spawns a process goes through command.rs. One module owns the environment scrubbing in D-44, so a future operation cannot forget it.
D-47 Absolute paths cross the crate boundary; repo-relative paths never leave the parser.

git speaks in slash-separated paths relative to the work tree. The listing speaks in VfsPath. Converting per row per frame would be an allocation and a join in the hot path; converting once, off-thread, while the status is being built, is free. The snapshot that reaches the UI is keyed by PathBuf so a row can be looked up with &Path and no allocation at all.

§5

The data path

Where the work happens, what crosses to the window thread, and what wakes it up.

Window thread

  • Owns GitPanel: the current repository, the in-flight generation, and the snapshot handle.
  • Reads the snapshot with one atomic load per cell. Never spawns git.
  • Renders the segment, opens the dialog, shows notifications.
ferret-ui::browser::git

Background executor

  • Discovery: one git rev-parse per navigation into an unknown tree.
  • Status: one git status per refresh, parsed to a RepoStatus.
  • Builds the absolute-path map and the dirty-directory set (D-47) before handing anything over.
ferret-git

The .git watcher

  • One non-recursive ferret_vfs::Watch on the resolved git directory.
  • index, HEAD, FETCH_HEAD, MERGE_HEAD and packed-refs are all direct children — so commit, checkout, fetch and pull all land here.
  • Costs one subscription, and no polling at all.
ferret-vfs::watch

The refresh triggers, and only these

  1. 1 Navigation. The active tab changed folder. If the new folder is inside the same work tree, the snapshot is kept and a refresh is queued; if not, the snapshot is cleared first so a stale branch name cannot be shown for a folder it does not describe.
  2. 2 The folder watcher fired. The user, or anything else, wrote a file in the directory on screen.
  3. 3 The .git watcher fired. Somebody committed, checked out, fetched or staged — from Ferret, from the terminal panel, or from another application.
  4. 4 An action finished. Commit, pull and push each refresh on completion regardless of outcome; a failed pull may still have moved refs.
  5. 5 The window regained focus. Covers the case where the repository changed while Ferret was not running its watchers' event loop.

There is no timer. A poll is the thing that makes a git integration a background CPU cost on an idle machine, and every event above is either free or already being delivered.

D-48 Refreshes are debounced, coalesced and generation-guarded.

A git add -A in the terminal can produce a dozen watcher events in 200 ms, and git status on a large repository is not free. Requests coalesce into one pending refresh behind a 220 ms debounce; at most one status process exists at a time, and a request arriving while one is running sets a re-run flag rather than starting a second. Every result carries the generation it was requested at and is dropped if the browser has navigated since — the same rule Folder already uses for listings.

Handing the snapshot over

GitSnapshot is immutable and shared as Arc<ArcSwap<GitSnapshot>>, cloned into every FilePane the browser builds. A read is an atomic load; a write is one pointer swap on the window thread. This is the same mechanism ColumnLayout uses and for the same reason: it is read once per cell per frame and written rarely.

§6

Reading porcelain v2

The exact command, the grammar, and the five things that make a naïve parser wrong.

git --no-optional-locks status --porcelain=v2 --branch -z \
    --untracked-files=normal --ignored=no
FlagWhy
--no-optional-locksgit status refreshes and rewrites the index by default, taking index.lock. Ferret polls on a watcher event; taking that lock from a background thread can lose a race with the user's own terminal in the panel below. This makes the read genuinely read-only.
--porcelain=v2Stable across versions and independent of user config, and it carries branch, upstream and ahead/behind in the same output — D-45's single invocation.
--branchEmits the branch.* headers. Without it there is no branch name and no ahead/behind.
-zNUL-terminated records. Without it, paths containing a space, a tab, a newline or a non-UTF-8 byte are C-quoted and have to be unescaped — a parser bug waiting to happen, on exactly the filenames a file manager must handle.
--untracked-files=normalCollapses a wholly-untracked directory to a single entry with a trailing slash. On a fresh clone with a node_modules this is the difference between five entries and fifty thousand.
--ignored=noThe default, stated. Ignored files get no badge: the plan lists them, but a listing where every build artefact is greyed is noise, and the cost of enumerating them is unbounded.

The grammar, as actually emitted

# headers, each NUL-terminated
# branch.oid <sha> | (initial)
# branch.head <branch> | (detached)
# branch.upstream <upstream>      // absent when there is no upstream
# branch.ab +<ahead> -<behind>    // absent when there is no upstream

// entries, each NUL-terminated
1 <XY> <sub> <mH> <mI> <mW> <hH> <hI> <path>
2 <XY> <sub> <mH> <mI> <mW> <hH> <hI> <X><score> <path>NUL<origPath>
u <XY> <sub> <m1> <m2> <m3> <mW> <h1> <h2> <h3> <path>
? <path>

Real output, from a tree with a staged rename, an unstaged edit, an untracked file with a space in its name and an untracked directory (NUL shown as @):

# branch.oid 585a06d2…@# branch.head main@2 R. N... 100644 100644 100644 6178079… 6178079… R100 renamed name.txt@b.txt@1 .M N... 100644 100644 100644 7898192… 7898192… sub/deep/a.txt@? space file.txt@? untracked_dir/@

The five things that make a naïve parser wrong

  1. 1 A 2 record consumes two NUL fields. The rename's original path is a separate record, not a tab-separated suffix as it is without -z. A parser that splits on NUL and treats every field as a record reads b.txt as a status line and desynchronises for the rest of the output.
  2. 2 branch.ab is optional. No upstream, no header. Ahead/behind must be Option-shaped, not zero-shaped, or a branch with no upstream claims to be perfectly in sync.
  3. 3 (detached) and (initial) are literal values in the branch.head and branch.oid fields. A detached HEAD shows the short OID; an unborn branch on a fresh git init shows the branch name with no ahead/behind and no OID.
  4. 4 An untracked directory ends in /. It is one entry standing for an unbounded number of files. §7 says what the listing does about it.
  5. 5 Paths are bytes, not str. On Unix a filename is arbitrary non-NUL bytes. The parser works in &[u8] and builds a PathBuf through OsStr::from_bytes on Unix; on Windows git emits UTF-8 and the lossy conversion is correct there.

XY, reduced to what the listing draws

X is the index against HEAD, Y is the work tree against the index, and . means unmodified. Ferret keeps both — the badge shows the more urgent of the two, and the tooltip explains both — collapsed into:

FileStatusFromMeaning
Conflictedu recordsUnmerged. Outranks everything.
StagedX ≠ ., Y = .Ready to commit.
StagedAndModifiedboth ≠ .Staged, then edited again — the state people lose work in.
ModifiedY ≠ .Changed, not staged. Includes deletions and type changes.
Untracked? recordsNot in the index.
§7

Status in the listing (F-51)

The part of this feature that can ruin the application, and the four rules that stop it.

Gate 7 in AGENTS.md is absolute: no per-frame work may be O(the directory). A git badge is drawn in a cell that renders forty times a frame while scrolling, in a listing that may hold two hundred thousand rows. The design below is shaped entirely by that.

  1. 1 The snapshot holds only what changed. A clean repository's map is empty; a busy one holds hundreds of entries. Nothing proportional to the directory is ever stored, iterated or hashed.
  2. 2 Lookup is one hash of a borrowed path. FastMap<PathBuf, FileStatus> is queried with &Path through Borrow — no join, no format, no allocation, and nothing added to the just budget count.
  3. 3 The directory roll-up is precomputed. While the snapshot is being built, every ancestor of every changed file, up to the work tree root, is inserted into a FastSet<PathBuf>. A directory row is one set lookup. The set is bounded by changed files × depth, off-thread, once per refresh.
  4. 4 The collapsed-untracked case is answered once, not per row. When the browsed directory is itself inside an untracked directory git reported with a trailing slash, git says nothing about its children — correctly, and uselessly for the listing. The snapshot therefore carries a single browsed_dir_untracked flag, resolved against the browsed directory when the snapshot is built. Every row in that folder is untracked; no per-row ancestor walk happens.
D-49 Past a cut-off, the counts survive and the badges stop.

A repository with a hundred thousand changed files — a first git add on a huge import, a botched line-ending conversion — would otherwise build a map of a hundred thousand PathBufs on every refresh. Past MAX_BADGED_FILES the map and the roll-up set are left empty and a flag records why: the status bar still shows the true count and the buttons still work, the listing simply draws no badges. The tooltip says so. This is a bounded, explained degradation rather than a stall.

What a badge looks like

A 6 px filled dot in the Name cell, at the right of the row's icon-and-name group, before the symlink target if there is one. Not a letter and not a coloured filename: colour on the name would fight the folder tint that already carries meaning (§7 of ui-base.html), and a letter at 11 px in a 30 px row is a smudge. A directory carries the same dot at 5 px and 70% opacity — present enough to follow down a tree, quiet enough not to compete with its children.

The Name column is the only column that changes

A separate Git column was considered and rejected. It would be a fourth sortable column for a value four of five rows do not have, it would take width from the name in the view where width is already contested, and hiding it would put the feature behind a menu most people never open.

§8

Commit, pull, push (F-52, F-53)

Four operations, one queue, and a rule about what the user is told.

ActionCommandNotes
Stage allgit add -A --Scoped to the work tree root, never to the browsed folder — "stage all" that staged some would be a trap.
Commitgit commit -F - The message arrives on stdin, so a message containing quotes, newlines or a leading - cannot be misread as arguments. Hooks run; GIT_EDITOR=true stops a hook that wants an editor from hanging.
Pullgit pull --ff-onlyFast-forward only, on purpose. A pull that starts a merge — or worse, leaves conflict markers — in a file manager with no conflict UI is a trap. When it refuses, git's own message says exactly why, and the terminal is right there.
Pushgit pushNo --force, ever, from any surface in this feature. Sets upstream on a branch that has none only via git's own push.autoSetupRemote, never by Ferret adding -u behind the user's back.
D-50 One git mutation at a time, per window.

Two concurrent operations on one index is how a repository ends up with a stale index.lock and a user who has to delete a file to get their tool working again. GitPanel holds at most one in-flight action; while it runs, every action button is disabled and the branch chip shows a spinner. Status reads are unaffected — they take no locks (§6).

D-51 git's output is shown unedited, and failure is never silent.

plan.html is explicit about this under F-53: the reference product shows a real fatal: unable to access … when a pull fails, and Ferret should be equally honest. Success produces a short toast built from git's own summary line ("Fast-forwarded to a1b2c3d"). Failure produces a warning notification carrying git's stderr verbatim, trimmed only of trailing whitespace and capped at MAX_MESSAGE_CHARS. Ferret never invents a friendlier message for a git error, because the friendly version is the one that cannot be searched for.

Timeouts

A status read is capped at STATUS_TIMEOUT (5 s) — long enough for a cold cache on a large repository over a network mount, short enough that a wedged git does not leave the segment permanently spinning. Network operations are capped at NETWORK_TIMEOUT (120 s), because a real push of a real repository over a real connection takes minutes and killing it at thirty seconds would be worse than useless. A timeout kills the child and reports the timeout as itself.

§9

Theme tokens

Five colours, both themes, none of them a literal at a call site.

theme.rs already exists for exactly this: "the colours that encode file and git state in the browser". The tokens join BrowserPalette, which resolves against the active mode, so light and dark are one code path and Gate 3 cannot be failed by forgetting one.

TokenLightDarkDraws
git_modified#b8860b#e0af68Changed, not staged. Amber.
git_staged#2e7d32#9ece6aStaged. Green.
git_untracked#6b7280#8b93a3Not in the index. Grey — new is not an alarm.
git_conflicted#c62828#f7768eUnmerged. Red, and the only red in the listing.
git_branch#4a5568#a0aec0The branch chip's glyph and text.

Both dark values for modified and staged are the Groknight terminal palette's yellow and green, deliberately: the terminal panel six pixels below is printing git status in those exact colours, and two different greens for one meaning in one window is the kind of detail that reads as sloppiness without being consciously noticed.

StagedAndModified gets no sixth colour. It draws the staged green with the modified amber as a ring, which is the one state where both facts matter.

§11

Build order

Each step leaves the application runnable, which is what makes a long run recoverable.

  1. 1 ferret-git, parser first. errors.rs, config.rs, status.rs with the porcelain v2 parser and its tests over byte literals. No process spawning yet, no UI. The whole of §6's sharp edges are covered here, where they are cheap to cover.
  2. 2 command.rs and discover.rs. D-44's environment, the timeout, the output cap. Discovery against a temp repository built by the test itself.
  3. 3 GitPanel and the status-bar segment (F-50). Discovery on navigation, one refresh, the branch chip and the counts. The app now shows a branch. No actions, no badges.
  4. 4 The refresh triggers (D-48). Watchers, debounce, generations. Verified by editing a file in the terminal panel and watching the count change without touching Ferret.
  5. 5 Badges in the listing (F-51). The snapshot handle into FilePane, the Name cell's dot, the directory roll-up. just budget immediately afterwards — this is the step that can fail Gate 7.
  6. 6 ops.rs, then the commit dialog (F-52). Stage-all and commit, with the dialog as its own entity (D-46).
  7. 7 Pull and push (F-53). The single-flight guard (D-50), the notifications (D-51), the timeouts.
  8. 8 Windows pass. Path separators through the parser, git.exe discovery, the CREATE_NO_WINDOW flag so no console flashes on every status read.
§12

Gates & budgets

Gates

  • Gate 7 (no per-frame O(directory) work). Point the pane at the fixture's flat/ inside a repository and scroll. just budget must be unchanged by this feature — the badge lookup allocates nothing.
  • Gate 3 (both themes). Five new tokens, each defined for light and dark, in one resolve function so there is no path that defines one and not the other.
  • Gate 4 (both platforms). Two keybindings, both bound. No console window on Windows. Paths through the parser tested for both separators.
  • Gate 6 (run it). Every visible state — clean, dirty, detached, unborn, no upstream, conflicted, not a repository, git missing — checked in the running app.

Budgets

MeasureBudgetWhy
Badge lookup, per row per frame0 allocationsGate 7. Enforced by just budget.
Status refreshes for one git add -A1D-48's debounce. A dozen watcher events, one process.
Concurrent git processes per window1 read + 1 writeD-50.
Idle CPU in a repository0No timer. Watchers only.

Acceptance

plan.html's phase 5 line: browsing a large repository shows correct per-file status with no measurable scroll cost, and a failed push surfaces git's actual message. Both halves are checkable, and the second one is the one that is usually quietly dropped.

§13

Risks & questions

RiskMitigation
git status is slow on a very large repository, so the badges lag the listing by a second.The listing never waits for it. Badges appear when they appear, exactly as size and date already do. The user's own core.fsmonitor and untracked cache — which an embedded library could not use — make this fast for the people it would otherwise be slowest for.
A submodule or a linked worktree makes .git a file, not a directory, and the watcher watches nothing.Discovery uses rev-parse --absolute-git-dir, which resolves the indirection. The watch is on the resolved directory.
The .git watcher on a busy repository (a rebase, a large fetch) produces a burst.Same debounce and single-flight as everything else. The worst case is one extra status read after the burst settles.
A user has a pre-commit hook that takes thirty seconds.The commit runs on the background executor with the network timeout, not the status timeout, and the dialog stays up with its button disabled. Hooks are a feature of using the real binary, not a bug.

Questions

  • Q-09. Should the change count include untracked files? The reference product's number appears to. Ferret's does, because "41 changed" that ignores forty new files is a number that has to be explained. Revisit if it proves noisy on repositories with weak .gitignore files.
  • Q-10. Should a directory's roll-up dot distinguish which status it is rolling up when its children disagree? Currently it shows the most urgent. The alternative — a neutral "has changes" tint — is calmer and less informative. Decide with real use.
