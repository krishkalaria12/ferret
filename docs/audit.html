Audit · rev 2 · 29 Aug 2026

What the first audit did not look at

Rev 1 is finished — twenty-six findings and six decisions, landed. This is the pass over what that left behind, and over the parts of the workspace the first audit passed through without auditing: the settings schema, the sidebar and title bar, the binary, and the asset and theme layers. The headline is not performance this time. It is that the app quietly does the wrong thing in four places, and one of them is wrong for almost every user on earth.

§1

What this is

The second read of the workspace, after the first one was acted on in full.

Rev 1 asked one question — where is this slow? — and answered it well enough that the answers are now in the code: shared handles in Entry, stable EntryIds, one watcher registry, metadata resolved during the walk, three budgets in CI. The reindex that took 17.8 ms takes 1.8 ms. The listing that filled itself in for half a second arrives complete.

That success is what makes this pass different. The obvious hot paths have been walked twice; what is left is not more of the same. It is work the first audit never looked at — ferret-settings, ferret-platform, ferret itself, and the sidebar, title bar and menus that make up most of the shell — plus the handful of places where rev 1's own fixes stopped one step short.

Read this first

Rev 1 said plainly that nothing in it was profiled. That is no longer true, and the distinction matters: this document mixes measured figures with structural claims and labels every one. A measured figure names the command that produced it. A structural claim says what the code does and what that costs in kind, and is not accompanied by a wall-clock number it did not earn.

The shape of it

Rev 1's findings were nearly all one thing: work that is O(the directory) running per row or per frame. This one splits three ways, and the biggest group is the one a performance audit does not usually produce.

  • Four correctness bugs (§3, §4). Every date in the app is in the wrong time zone. The default theme setting does not do what it says. Twelve settings do nothing at all. Copy and paste does not reach Finder. None of these is slow; all of them are wrong.
  • Six pieces of waste (§5, §6) that rev 1 walked past because they are not in the file list — including one syscall-per-frame that is the exact bug rev 1 fixed as A-25, left standing in the function next to it.
  • One regression rev 1 introduced (§7), documented at the time and still open.

How the findings are numbered

Continuing from rev 1 rather than restarting: A-27 onward and D-39 onward. This is not tidiness. Twenty-six of the old identifiers are cited in code comments — A-05 in folder/mod.rs, D-35 in entry.rs, A-24 in listing.rs — and reusing a number would point a future reader at the wrong finding.

  • critical — wrong rather than slow, or a stall on a path a person uses constantly.
  • major — a real cost, or a promise the app does not keep.
  • minor — waste worth removing while you are already in the file.

§3

What the app gets wrong

Four findings that are not about speed. A file manager's job is to tell you the truth about your files; these are the places it does not.

A-27 Every date the app displays is UTC critical

crates/ferret-ui/src/format.rs:53–75 — format_date

format_date takes a SystemTime, converts it to seconds since the epoch, and runs Howard Hinnant's civil_from_days on it. That algorithm is correct and the implementation is correct. It computes a UTC civil date, and nothing anywhere in the workspace ever applies a local offset:

let secs = t.duration_since(UNIX_EPOCH).map(|d| d.as_secs() as i64).unwrap_or(0);
let days = secs.div_euclid(86_400);          // UTC days
let rem  = secs.rem_euclid(86_400);          // UTC seconds past midnight
let (h, m) = (rem / 3600, (rem % 3600) / 60);

Grepping the whole workspace for any timezone handling returns one hit, and it is a comment in this function's own test asserting the UTC value. There is no offset, no localtime_r, no tz database, nothing.

So for a user in IST (+05:30), a file saved at 00:30 on the 4th displays as 19:00 on the 3rd — wrong time, wrong day, wrong date. In PST (−08:00) it runs the other way. Only users on UTC see the truth, and they see it only outside British Summer Time. This is on the Date Modified column, the column view's metadata panel, and anywhere else a date appears.

Fix — This is the one place in the workspace where writing it by hand is the wrong instinct. The offset is not a constant: it depends on the date being formatted (DST), on the user's zone, and on a tz database that ships updates several times a year. plan.html's "no date library — civil-from-days is thirty lines" note was written when formatting was the whole job; it is not any more. See D-39.

A-31 theme: "system" does not follow the system major

crates/ferret/src/main.rs:249–254 · crates/ferret-settings/src/schema.rs:22–29

The schema documents the default as "Follow the OS appearance, and change with it while running". apply_startup_theme calls Theme::sync_system_appearance exactly once, during startup, and nothing in the workspace observes an appearance change afterwards — grepping for observe_window_appearance or WindowAppearance outside that one line returns nothing.

So Ferret reads whether the Mac is in dark mode at launch and then holds that opinion forever. Every user on the macOS "Auto" appearance — which is the OS default — gets a window that is the wrong colour for half of every day, and the setting that promises otherwise is itself the default.

Fix — Window::observe_window_appearance exists in the pinned GPUI revision (gpui/src/window.rs:1958). Register it when the window opens and re-run the same three-way match already in apply_startup_theme. The subscription belongs with the window, so it lives or dies with it.

A-32 The clipboard never leaves the process major

crates/ferret-ui/src/browser/mod.rs:172 · browser/mutations.rs:280–335

Copy and cut write to a private field:

// Browser
clipboard: Option<(Vec<VfsPath>, bool)>,

Two consequences, and the second is the one nobody will report as a bug because it looks like the app is broken rather than incomplete:

  • No interop. Cmd-C in Ferret puts nothing on the system pasteboard, so Cmd-V in Finder, in a Save dialog, or in a terminal does nothing. The reverse also fails: copying in Finder and pasting in Ferret pastes whatever Ferret last copied, or nothing.
  • No interop with itself. The field is on Browser, and every window has its own. Copying in one Ferret window and pasting in another is a no-op — silently, because paste_clipboard takes None and returns.

Fix — No new dependency. GPUI already models exactly this: ClipboardEntry::ExternalPaths (gpui/src/platform.rs:2355) with App::write_to_clipboard and read_from_clipboard. The cut/copy distinction has no pasteboard representation on macOS, so it stays a local flag beside the system write — which is also how Finder behaves. See D-42.

§4

The file that lies

One finding, but it is the largest single thing in this audit and it undermines a decision the project has already made.

A-30 Twelve settings are declared, shipped as documentation, and read by nothing critical

crates/ferret-settings/src/schema.rs · default-settings.json · consumers in ferret-ui

D-12 says the settings file is the source of truth and the settings UI is a view over it, and schema.rs's header adds that "a hand-edited file must never be able to brick the app". Both hold. What nobody checked is the other direction: that a key the file offers actually does something. Twelve do not.

A thirteenth, keymap, is worse than unread: it is a BTreeMap<String, Option<String>> with a documented null-unbinds convention and a passing test proving the convention parses, while every binding in the app is hard-coded in main.rs. The test asserts that a feature which does not exist is parsed correctly.

Why this is critical and not cosmetic

These are not internal constants. They are serialised into default-settings.json, which the crate ships, which a test asserts is accurate, and which the module header calls "documentation the user reads and copies from". A user who sets confirm_permanent_delete: false has been told by the project's own documentation that the confirmation is gone. It is not. That is a worse failure than the setting not existing — and for that particular key, it is a failure in the direction of destroying data the user thought they had guarded.

Fix — Each one either works or goes, and the split is not close: six are a handful of lines each (directories_first, confirm_permanent_delete, enter_opens, show_places, show_volumes, ui_font_size), and six are features that have not been built (restore_session, default_directory, keymap, row_density, alternate_row_colors, columns). Wire the first six; delete the second six until the feature lands. See D-41, which also proposes the test that stops this recurring.

§5

The render path, again

Rev 1 cleared the file list and stopped there. The shell around it was never read, and the same three mistakes are in it.

A-28 The sidebar does seven syscalls per frame critical

crates/ferret-ui/src/browser/sidebar.rs:168 · browser/mutations.rs:422–437 · platform/macos.rs:41–51, :84–128

This is A-25, which rev 1 fixed, sitting untouched in the function immediately above the one that was fixed. volumes() was moved to a background timer so render only reads a cached value. places() — one line away, called from the same render_sidebar — was not:

// browser/sidebar.rs, inside render_sidebar
let places  = self.places(cx);      // → platform.places(), every frame
let favorites = self.favorites(cx); // → clones the Vec<PathBuf>, every frame
let volumes = self.volumes();       // → cached (A-25)

And places() is not a lookup. Each call walks the well-known folders and asks the filesystem whether each one exists, because a folder the user deleted should not appear:

fn place(kind: PlaceKind, name: &str, path: PathBuf) -> Option<Place> {
    if path.is_dir() {                       // ← a stat, per call
        Some(Place { name: name.to_string(), kind, path })   // ← an allocation, per call
    } else { None }
}

Seven of those — Desktop, Documents, Downloads, Music, Pictures, Movies, Applications — plus dirs::home_dir(), plus seven Strings and eight PathBufs, every time the sidebar draws. On a warm cache that is cheap enough to have gone unnoticed. On a Mac where ~/Documents is in iCloud Drive and has been evicted, or on a machine where the home directory is an SMB mount that has gone away, is_dir() is the call that blocks — and it blocks the window, at frame rate.

The audit that fixed volumes() said the reason in one line: "a stale network mount stalls that call, and stalls the window with it". Exactly the same sentence applies here, and places() is the one called unconditionally on every frame rather than once per fifteen seconds.

Fix — The same one, and the machinery already exists. Browser::start_volume_refresh is a background loop that probes and stores; give places the same treatment, or better, fold both into one probe task since they are the same kind of work on the same schedule. Render reads the last known list. Favourites do not need a probe at all — they come from settings — but they should stop being cloned per frame.

A-29 The selection summary is rebuilt in O(the directory), per selection change critical

crates/ferret-ui/src/folder/mod.rs:610–629 — refresh_selection_summary

Rev 1's A-07 made the status bar O(1) per frame by caching the selected paths and their byte total. The cache is correct and the status bar is fast. What was never examined is how often the cache is rebuilt, and the answer is: on every single mutation of the selection.

pub(super) fn refresh_selection_summary(&mut self) {
    // ...
    for (id, entry) in self.visible_entries() {   // ← every row in `order`
        if self.selection.contains(&id) { paths.push(entry.path.clone()); ... }
    }
    self.selected_visible_paths = paths.into();   // ← a fresh Arc<[VfsPath]>
}

Every one of select_only, toggle_select, extend_select, select_rows, select_all and clear_selection ends in that call. Two of them are not one-shot user actions:

  • A marquee drag calls select_rows from update_marquee, which runs on every mouse-move event — at display rate while the band is moving.
  • Shift + arrow calls extend_select once per key repeat, roughly thirty times a second once the repeat starts.

Measured, on a 200,000-entry listing, release build:

Cost of one selection change (selection_summary_cost, 200,000 rows)
SituationPer changeShare of a 120 Hz frame
A small band — 200 rows selected691 µs8%
Everything selected (Cmd-A, then any arrow key)1.37 ms16%

The scan dominates the small case; in the large one the Arc<[VfsPath]> is itself 200,000 elements — 4.8 MB allocated and thrown away per mouse-move.

Fix — Rev 1's A-02 proposed exactly this and only half of it was done: "keep an ordered selection vector on Folder, rebuilt by the selection mutators rather than derived by scanning". It is still derived by scanning; the change was only that it is scanned once per change rather than once per row per frame. The mutators know what they touched — select_only changes one row, extend_select knows its old and new bounds — so the summary can be maintained incrementally. select_all and clear_selection stay O(n) because they genuinely are.

A-33 IconKey::of allocates per row per frame major

crates/ferret-platform/src/icon.rs:61–79 · crates/ferret-ui/src/icons.rs:203–210 · called from pane/mod.rs

entry_icon runs once per visible row in all three views, and starts by building a cache key:

let key = ferret_platform::IconKey::of(local, entry.is_dir_like());
// → IconKey::Extension(ext.to_ascii_lowercase())   ← a String, per row, per frame

Two things are wrong with it. It allocates a String to look something up in a cache — the classic shape rev 1 spent eleven commits removing. And it re-derives the lowercased extension from the path when Entry has cached exactly that value since D-35, precisely so this would not have to happen. For .app bundles it is worse: IconKey::Application allocates the full path as a String.

And the budget cannot see it

This is the part worth dwelling on. just budget asserts two allocations per visible row per frame and passes. It passes because its harness deliberately skips os_icon — which needs a GPUI App the harness does not have — and the module says so. So the one number in the repository whose job is to catch a per-row allocation has a hole in it exactly where a per-row allocation is. See §10.

Fix — IconKey::Extension(SmolStr) and a constructor that takes an &Entry, so the key is built from the cached extension and a short extension never touches the heap at all. smol_str is already a dependency of both crates.

A-37 The sidebar allocates a row id and a label per row, per frame minor

crates/ferret-ui/src/browser/sidebar.rs:204, :227, :243, :345 · browser/title_bar.rs:215

SharedString::from(format!("place-{i}")) for every row, plus label.to_string() for every label, plus format!("Ferret — {title}") once for the window title. Fifteen-odd allocations a frame is not a stall and this is not urgent — but the ids are derived from a counter and could be ElementId::NamedInteger, which GPUI provides for this exact case and which does not allocate.

A-38 The delegate re-reads the model four times per cell minor

crates/ferret-ui/src/pane/list.rs:459–470, :517

render_td is called once per (row, column). Inside it, self.folder.read(cx) appears four times — for the entry, the selection state, the depth and the expansion — and self.palette(cx) re-resolves the browser palette, which is three Rgba-to-Hsla conversions and a theme lookup. At four columns and forty visible rows that is 640 entity reads and 160 palette resolutions per frame to answer questions that are constant for the row and for the frame.

Fix — Read once at the top of render_td, and hoist the palette to the frame. Neither is O(the directory), which is why this is minor; both are free.

§6

Memory & the listing

Three things the listing rework left slightly out of shape.

A-34 Metadata carries two fields nothing reads major

crates/ferret-vfs/src/entry.rs:46–55

Measured with size_of: Entry is 144 bytes, Option<Entry> is also 144 (the niche packs, which is the good news), and Metadata is 48 of those bytes. Two of its five fields are read by nothing in the workspace:

  • created: Option<SystemTime> — 16 bytes. No column shows it, no sort key uses it, no menu offers it.
  • readonly: bool — no row draws it, no operation checks it.

On flat/ the slab holds 200,000 × 144 = 28.8 MB, of which 3.2 MB is a creation time nothing will ever display. Dropping both takes Metadata from 48 bytes to 32 and Entry from 144 to 128 — an 11% cut to the resident size of a large listing, for deleting two fields.

Fix — Delete them, and take them out of to_metadata while you are there. The counter-argument is that a Date Created column is a plausible feature; the answer is that st_birthtime comes back in the same stat that is already being made, so re-adding the field later costs one line and no syscalls. Carrying 3.2 MB against that is not a trade.

A-35 LISTING_BATCH_SIZE now gates the first row on 4,096 stat calls minor

crates/ferret-vfs/src/config.rs:37 · vfs/local.rs — resolve

4,096 was chosen when a batch was names only, to amortise a channel send and a model update over enough rows to matter. D-33 changed what a batch is: every entry in it now carries a resolved stat, so the constant is doing a second job it was never sized for — bounding how long the first row waits.

Measured, cargo xtask bench on flat/: time to first row went from 2.0 ms before D-33 to 5.8 ms after. Both are far inside the 50 ms budget, which is why this is minor rather than a regression — but it is three times worse for no reason, and the same constant also sets the ceiling on how much work a cancelled walk leaves in flight.

Fix — Ramp it. A first batch of 128 puts the first row back under a millisecond; doubling to the existing 4,096 over the next few batches keeps the throughput the constant was chosen for. Roughly six lines, and it makes both jobs the constant is now doing explicit instead of coincidental.

A-36 Assets::list ignores the path it is given minor

crates/ferret-ui/src/assets.rs:27–31

fn list(&self, path: &str) -> gpui::Result<Vec<gpui::SharedString>> {
    let mut out = FerretAssets::iter().map(Into::into).collect::<Vec<_>>();
    //                          ^ every embedded asset, whatever `path` said
    out.extend(gpui_component_assets::Assets.list(path)?);
    Ok(out)
}

The contract is "list the assets under path". This lists all of Ferret's assets under every path, and only delegates the filter to the library half. Nothing currently depends on the answer being right, which is why it has gone unnoticed — but "nothing currently calls this correctly" is a poor thing to be relying on, and the fix is a filter.

A-39 The macOS icon conversion swizzles one pixel at a time minor

crates/ferret-platform/src/macos.rs — icon_for_path

Carried forward unchanged from rev 1, which called it "one free byte-level win" and was right to rank it last. AppKit hands back RGBA and GPUI wants BGRA, so the code walks chunks_exact(4) and pushes four bytes at a time — 4,096 iterations per icon at ICON_POINTS = 64. It runs once per file type, off the render path, so it is genuinely not urgent.

Fix — Rev 1 named the right one and it is still right: ask NSBitmapImageRep for the byte order you want via its bitmapFormat and do no conversion at all. Failing that, a u32 swizzle over bytemuck::cast_slice is four times fewer iterations and three lines.

§7

The gap rev 1 opened

Not a new finding — an open one, carried here because it is the only thing in the workspace that is worse than it was before the last audit, and because there is now a concrete way to close it.

D-37 replaced one notify watcher per Folder with a single shared backend and reference-counted subscriptions. That was right — ten tabs in column view was up to forty native streams — and it came with a cost that was documented in ferret_vfs::watch's module header at the time rather than discovered later:

The cost, restated

notify's FSEvents backend calls stop(), edits its path list, and calls run() again on every watch and unwatch. With one stream per folder that was invisible. With one shared stream, every registration change is a window in which every other watched directory loses events outright — and a lost event is a row that stays stale until something else happens, which is the failure A-06 exists to prevent.

Two things have been checked since, and both matter:

  • Upgrading does not fix it. notify 8.2.0 — two majors ahead of the pinned 7 — has byte-identical watch_inner and unwatch_inner, and still sets since_when to kFSEventStreamEventIdSinceNow once at construction and never advances it. So every rebuilt stream starts from "now" and the events during the rebuild are genuinely gone.
  • The fix needs no new package. fsevent-sys 4.1.0 is already in Cargo.lock, pulled by notify itself, and it exposes FSEventStreamGetLatestEventId (fsevent-sys-4.1.0/src/fsevent.rs:102) — which is precisely the value that would have to be threaded through for a rebuild to lose nothing.

The mitigation already in place — parking idle registrations so navigating away and back costs no rebuild — reduces how often the window opens. It does not close it. See D-40.

Libraries worth adopting

One that is not optional, two that are already paid for, and one that is a feature rather than a fix.

jiff — the only one that is not a choice

A-27 needs a tz database, and a tz database is not something to hand-roll. The offset for a given instant depends on the user's zone, on whether that instant was in daylight saving, and on a rules file that IANA updates several times a year as governments change their minds. Getting it wrong is exactly as bad as the bug being fixed.

jiff is the one to reach for over chrono or time: it is the newest of the three, it was written by the author of regex and ripgrep specifically to make the correct thing the easy thing, and it reads the system zoneinfo directly rather than needing a companion crate the way chrono + chrono-tz or time + time-tz do. It is also the only one whose API makes "this instant, in the user's zone, as a civil date" a single call.

What survives

civil_from_days and its tests do not need to be deleted. They are correct for what they compute; they were simply asked the wrong question. The smallest honest change is to keep the formatting and replace the input — resolve the SystemTime to a local civil date with jiff, then format that. plan.html's "no date library, civil-from-days is thirty lines" note should be amended rather than deleted: it was right about formatting and wrong about zones, and saying so is more useful to the next reader than quietly reversing it.

fsevent-sys — the registry is already the seam

D-37's own justification was that a registry is where a different change-detection mechanism plugs in when remote mounts arrive. That seam is what makes this cheap now: the local backend can own an FSEventStream directly, store FSEventStreamGetLatestEventId before every stop(), and pass it as since_when on the next run(). Nothing above ferret_vfs::watch changes, because nothing above it knows what a stream is.

The honest counter-argument is that this is unsafe FFI in exchange for closing a window measured in milliseconds, on macOS only, and that Windows' ReadDirectoryChangesW has no equivalent problem because notify registers each directory independently there. That is a real argument for deferring it. It is not an argument for leaving the module header's warning as the only mitigation forever.

nucleo — a feature, and it should be labelled as one

The filter is a substring match and type-ahead is a prefix match. Both are correct and both are now fast (A-13). nucleo — the matcher behind Helix and Zed's pickers — would make the filter fuzzy, which is a better filter and a different one. It belongs in plan.html as a feature with a decision behind it, not in an audit as an optimisation. Noted here only so the option is on record; the current implementation is not a finding.

§9

Decisions

Four, continuing from D-38. The first is a reversal of a decision plan.html made, and says so.

D-39 Dates are local, and a library owns the conversion.

Every displayed timestamp is resolved to the user's zone before it is formatted, using jiff and the system tz database. civil_from_days stays and keeps its tests; what changes is that it is handed a local civil datetime rather than a UTC one.

Because plan.html decided against a date library on the grounds that formatting is thirty lines. That was true and it is still true — but formatting was never the hard part, and the document did not notice that the easy part was the only part being done. A file manager that reports the wrong modification day is not usefully fast.

D-40 The macOS watcher resumes from its last event id rather than restarting.

The local backend owns an FSEventStream through fsevent-sys instead of going through notify on macOS. Before every rebuild it stores FSEventStreamGetLatestEventId; the next stream starts from there rather than from kFSEventStreamEventIdSinceNow. notify stays for Windows, where the problem does not exist.

Because the registry closed forty native streams and opened one delivery gap, and the gap is the kind of bug that is invisible until someone loses work to it. Doing this behind the registry is a change to one file; doing it after remote mounts have added a second mechanism is a change to a design.

Deferrable if the unsafe surface is judged too much for the size of the window. In that case the parked-registration mitigation stands and the module header stays the record — but that is a decision to take deliberately, not by default.

D-41 Every setting either works or is deleted, and a test enforces it.

The six cheap ones are wired up. The six that need a feature are removed from the schema and from default-settings.json until that feature lands, and keymap goes with them. A test asserts that every field the schema serialises is named somewhere outside ferret-settings.

Because D-12 made the file the source of truth, and a source of truth that is ignored is worse than no file at all — it is documentation that lies. The test is the part that matters: this class of drift is invisible to every other check in the repository, and it will recur the moment a setting is added ahead of the code that reads it.

The test is cheap and slightly unusual

It cannot be a compile-time check, because "is read" is not a property the type system sees. But Settings::default().to_json() already enumerates every shipped key, and a test can walk that list and grep the workspace source for each name. Crude, and it would have caught all twelve of these on the day each was written.

D-42 The clipboard is the system's, not the browser's.

Copy and cut write ClipboardEntry::ExternalPaths to the system pasteboard through GPUI. Paste reads it. The cut flag stays a process-local hint beside the system write, because macOS has no pasteboard representation for it.

Because a file manager whose copy does not reach Finder is not a file manager the user can adopt, and "Finished when" in AGENTS.md is explicitly "you can set Ferret as your default file manager and not miss the system one". Copy and paste between the two is table stakes for that sentence, and the fact that it also fails between two Ferret windows means the current design cannot be extended into working — it has to be replaced.

§10

What the budgets miss

Rev 1 added three budgets and a profiler. They work — and this audit found four things none of them can see, which is worth writing down while it is fresh.

The budgets caught something real on their first run: the allocation budget failed at 4.00 per row against a predicted floor of 2, and the cause was format! reallocating its buffer in both format_size and format_date. That is exactly the job. But three of this audit's four largest findings sailed past all of them.

Why each budget missed what it missed
FindingWhich budget should have caught itWhy it did not
A-33Allocations per frameThe harness skips os_icon because it needs a GPUI App. The gap is documented in the module — and a documented hole in the one check whose job is to have no holes is still a hole.
A-29Allocations per frameIt measures a scroll. Nothing in the harness changes the selection, so the one path that is O(the directory) is never exercised.
A-28NothingNo budget covers the shell. Every measurement in the repository points at the file list, because that is where rev 1 was looking.
A-27Nothing — correctlyA timezone bug is not a budget's job. It is a test's, and there was no test that formatted a known instant and asserted a local result, because the function has only ever been asked for a UTC one.

Three additions, in the same spirit as rev 1's

  • Close the icon hole. The allocation harness skips os_icon for a real reason, but gpui::TestAppContext can supply the App it needs. Moving the budget to a #[gpui::test] is a smaller change than the hole is a risk.
  • Script a selection, not just a scroll. One marquee-drag's worth of select_rows calls in the same budget would have put A-29 on the first run, and it is four lines.
  • A date test with a zone in it. Set TZ, format a known instant, assert the local result. It is the only way this class of bug is ever caught, and it is the test that should land in the same commit as D-39.
What is genuinely working

Worth saying, because an audit that only lists faults gives a false impression. The watcher burst budget is the strongest thing in the repository: 5,000 creates and 5,000 deletes, asserting the model matches the disk exactly, converging in 87.5 ms and 26.6 ms. It covers three findings at once and it would fail loudly if any of them regressed. Gate 7 — no per-frame work may be O(the directory) — is the right rule, and A-29 is a reminder that it needs to be applied to per-interaction work too.

§12

What this did not check

Stated plainly, so nothing here is mistaken for a clean bill of health it did not earn.

  • Windows was read, not run. Again. windows.rs was read for the places() shape (identical to macOS, so A-28 applies to both) and for the icon cache. The unsafe SHGetFileInfo path was not audited with the care the macOS one received, and no finding here has been reproduced on Windows.
  • No profiler was attached. The measured figures come from cargo xtask bench, just budget, and three #[ignore]d measurements run in release. Tracy is wired up (--features profile) and was not used; a flame graph might well disagree with the ordering of §5.
  • The correctness bugs were reasoned, not reproduced. A-27 and A-31 are read from the code and are not in doubt — there is no timezone conversion and no appearance observer to find. But neither was demonstrated by running the app in a non-UTC zone or toggling the system appearance, and doing so is the first step of fixing them.
  • The terminal phase was not considered. terminal.html is a plan, not code. Where a finding here interacts with it — the shared worker pool, the clipboard, the settings schema — this document assumes Phase 2 has not started.
  • Nothing was checked for security. The unsafe AppKit block, the path handling around symlinks, and the new fsevent-sys proposal in D-40 all deserve a pass that this is not.
  • Rev 1's own work was re-read, not re-derived. A-29, A-33 and A-35 are all places where rev 1's fixes stopped one step short, which suggests the same is true somewhere this pass did not look.
