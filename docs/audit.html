§1

What this is

Phase 1 is finished. This is the pass over it before Phase 2 starts adding to it.

The base shell works, and it works on the fixture — Gate 1 was satisfied by choosing a virtualised table and never collecting a listing into a Vec. What this audit found is a second layer of cost that virtualisation does not save you from: work that is O(the whole directory) but runs per visible row or per frame, and work that is correctly asynchronous but serialised one syscall at a time. Both are invisible in a home directory and both are quadratic in flat/.

Read this first

Every finding below comes from reading the code, not from a profiler. The complexity claims are structural and I stand behind them; the wall-clock numbers are arithmetic from the sizes involved and are illustrations, not measurements. §11 says what to add to xtask so the important ones become numbers the repository owns rather than assertions in a document.

How the findings are numbered

A-nn for audit findings, so nothing collides with plan.html's F-nn features, D-nn decisions or R-nn risks. Six new decisions are proposed as D-33 … D-38, continuing where terminal.html left off. Severity is a pill on each finding:

  • critical — breaks a stated gate, or is wrong rather than slow.
  • major — a real stall a user will feel on a large directory.
  • minor — waste worth removing while you are already in the file.

The shape of it

Nine of the top ten reduce to two root causes. One: Entry is expensive to clone (a heap PathBuf plus a heap String) and the render path clones it constantly. Two: the model keys everything — selection, cursor, row lookup, expansion — on a full VfsPath, so every index rebuild is n allocations and n long-string hashes. Fix those two representations (§8) and roughly two-thirds of this table stops being reachable rather than being fixed one call site at a time.

§3

The render path

Gate 1 says "point it at flat/ and scroll". It passes. These are the things that make it stop passing the moment something is selected.

A-01 The OS icon is rebuilt from raw bytes on every row, every frame critical

crates/ferret-ui/src/icons.rs:116–135 · crates/ferret-platform/src/macos.rs:213–217 · called from pane/mod.rs:497–515

D-18's whole design is that the OS is never touched on the render path. It isn't — but what replaced it is worse. os_icon() runs once per visible row, and each call:

  • takes the provider's Mutex;
  • clone()s the cached IconBitmap — at ICON_POINTS = 64 that is a 16 KB Vec<u8> memcpy (macos.rs:202, :216);
  • builds a brand-new image::Frame and a brand-new gpui::RenderImage around it (icons.rs:127–134).

A fresh RenderImage is a fresh identity, so GPUI cannot recognise it as the texture it uploaded last frame. Forty list rows is ~640 KB of memcpy and forty new image handles per frame; icon view with ~200 visible tiles is over 3 MB per frame. At 120 Hz that is hundreds of megabytes a second of pure copying to draw icons that never change.

Fix Cache the decoded, shared handle, not the bytes. Have IconProvider::lookup return something cheap to clone and stable in identity — an Arc<RenderImage> built once at resolve time, behind an ArcSwap so the read path takes no lock at all (§9). The is_well_formed guard (icon.rs:33–38) then runs once per type instead of once per row per frame, which is also where it belongs. This is a small, contained change with the largest single payoff in the document.

A-02 Drag payloads are built eagerly, and building one scans the whole listing critical

crates/ferret-ui/src/pane/list.rs:320–324 · icon_view.rs:119–124 · folder/mod.rs:254–264

render_tr decides the drag payload before knowing whether a drag will ever happen, and for a selected row that payload is folder.selected_paths(). That function walks every display row (visible_entries() is (0..order.len()).filter_map(entry_at)), tests each against the selection set, and clones the matching VfsPaths.

So the cost is rows on screen × rows in the directory. With Cmd-A on flat/ and forty visible rows that is 8,000,000 index-and-hash steps and 8,000,000 PathBuf heap allocations — per frame. Icon view is five times worse because five times as many tiles are visible.

Fix Two independent halves. (a) Move the payload construction inside the on_drag closure, which only runs when a drag actually begins — the closure already captures the folder entity in the external-drag path (list.rs:361–363), so this is a re-shuffle rather than new machinery. (b) Keep an ordered selection vector on Folder, rebuilt by the selection mutators rather than derived by scanning. Do both: (a) removes it from the frame, (b) makes it cheap even when a drag does start.

A-07 The status bar recounts the directory every frame major

crates/ferret-ui/src/browser/render.rs:42–71 · folder/mod.rs:271–290

render_status_bar calls selection_count() and selection_size(), and both are visible_entries() scans over the whole listing. The comment at folder/mod.rs:273–277 correctly explains why the count must be visible-only; it is the how that costs — two full passes over 200,000 entries to render one line of text, every frame, whether or not anything changed.

Fix Maintain selected_visible_count and selected_visible_bytes as fields, updated by select_only, toggle_select, extend_select, select_rows, select_all, clear_selection and rebuild_index_and_order. The invariant is small enough to hold in one place and worth a unit test that asserts the incremental value matches a full recount after a scripted sequence of selections and a filter change.

A-08 Every cell clones its Entry, every frame major

pane/list.rs:320, :390 · pane/icon_view.rs:87 · pane/column_view.rs:136, :182 · pane/rename.rs

The pattern is folder.read(cx).entry_at(row).cloned(), used because the borrow of the folder cannot outlive the element being built. Each clone is a PathBuf allocation, a String allocation and an Option<PathBuf> allocation. A list row costs four of them (one per render_tr, three per render_td); forty rows is 160 clones and ~480 allocations per frame, before icons.

Fix Structural, and it is D-35: make Entry.path an Arc<Path> and Entry.name a SharedString. The clone becomes two refcount bumps and every call site above stays exactly as written. The doc comment at vfs/entry.rs:61–63 already says the name is held separately "because deriving it from path on every frame shows up when 200,000 rows are in play" — the same reasoning applies one level further down.

A-16 The column view's metadata panel scans the listing twice per frame major

crates/ferret-ui/src/pane/column_view.rs:326–337

render_metadata_column calls selected_paths() (one O(n) scan, A-02) and then (0..folder.row_count()).find_map(...) to locate the row that path belongs to — a second O(n) scan, to find something the model can already answer in O(1).

Fix folder.row_of(&path) exists for exactly this (folder/mod.rs:309–311). Combined with A-02's ordered selection vector the whole block becomes two lookups.

A-19 tabular_numerals() allocates three times per call minor

crates/ferret-ui/src/theme.rs:189–191 · called from pane/list.rs:503, :526 · column_view.rs:385 · browser/render.rs:70

FontFeatures(Arc::new(vec![("tnum".to_string(), 1)])) — a String, a Vec and an Arc, constructed fresh for every Date cell and every Size cell on screen, every frame.

Fix static TNUM: OnceLock<FontFeatures>; return a clone, which is one refcount bump. Three lines.

A-20 The bundled icon path is formatted fresh per row minor

crates/ferret-ui/src/icons.rs:82–109

asset_path returns String and gets there through up to three clone()s of the mapped name plus a format!. It runs for every row that has no OS icon yet — which, for the first quarter-second of every listing and forever on a platform where the provider is unavailable, is every row.

Fix Store the finished asset path in the table (HashMap<Box<str>, SharedString>) so lookup returns a SharedString and the format! happens once at startup. The test at icons.rs:269–287 that proves every mapped icon exists keeps working unchanged, and gets faster.

A-21 The column list is rebuilt and locked on every delegate call minor

crates/ferret-ui/src/pane/list.rs:79–88, :122–124, :136–141

visible_columns() allocates a Vec; visible() takes the hidden_columns mutex to call it; column_at() calls visible(). Between columns_count, column, render_th, render_tr and render_td that is roughly five allocations and five lock acquisitions per row per frame, to answer a question with at most four possible answers.

Fix Cache the resolved order on the delegate — a SmallVec<[FileColumn; 4]> never allocates at all — and invalidate it in toggle_column, which already calls table.refresh for exactly this reason (pane/mod.rs:310–316). The unit tests at list.rs:704–736 test visible_columns as a pure function and stay valid.
§4

The listing pipeline

The name tier is fast and measured. The metadata tier is neither.

A-03 The metadata backfill is one blocking-pool round trip per entry, in series critical

crates/ferret-ui/src/folder/expansion.rs:236–278 · crates/ferret-vfs/src/local.rs:95–104

The loop is chunked into 256s, but the chunking only controls how often the UI is notified. Inside it:

for chunk in targets.chunks(CHUNK) {
    for path in chunk {
        // one smol::unblock — a task spawn onto the blocking pool,
        // one symlink_metadata, and a wake back — per entry.
        if let Ok(md) = fs.metadata(path).await { ... }
    }
    ...
}

On macOS metadata_in_listing is false (local.rs:42), so this runs for every entry of every listing. For flat/ that is 200,000 sequential round trips through the blocking pool: 200,000 task spawns, 200,000 thread wakeups, and a stat that never overlaps with the next one. One core busy, the rest idle, and the Size and Date columns stay blank the whole time.

It is also the one hot path xtask bench does not measure (§11), which is presumably why it survived.

Fix Two levels. Cheap and immediate: move the inner loop inside a single smol::unblock so one chunk is one round trip — 800 hops instead of 200,000, for about ten lines. Correct: resolve metadata during the walk itself with a parallel walker, which deletes this function on both platforms. That is D-33.

A-10 The listing channel carries one entry per message major

crates/ferret-vfs/src/local.rs:53, :83 · config.rs:17 · folder/listing.rs:64–86

The producer sends each Entry individually into a bounded(LISTING_BUFFER) channel; the consumer receives them one at a time and then re-buffers them into batches of BATCH_SIZE = 4_096 anyway. So the per-entry granularity buys nothing at all — 200,000 sends and 200,000 receives, each a potential park and wake when the consumer falls behind, to produce fifty model updates.

Fix Batch at the source: have the producer accumulate and send Vec<Entry>, and let the stream item become a batch. The consumer's buffering loop then collapses to "forward what arrived". LISTING_BUFFER's doc comment (vfs/config.rs:11–17) is still the right policy — it just needs to be denominated in batches. The cancel-by-drop contract is unaffected, and the test at local.rs:456–470 still proves it.

A-11 Resolving icons clones the whole listing to find a handful of keys major

crates/ferret-ui/src/folder/expansion.rs:219–234 · icons.rs:141–159

request_os_icons does entries.iter().chain(children…).cloned().collect() — a full copy of every Entry in the directory, 200,000 PathBuf and String allocations — and hands it to resolve_os_icons, whose first act is to reduce it to a deduplicated set of IconKeys bounded by the number of file types present. The doc comment two lines above is right that the OS calls are deduplicated; it is the transport that isn't.

It runs on every finish_loading and on every folder expansion (expansion.rs:104).

Fix Build the Vec<(IconKey, PathBuf)> inside the model update, where the entries are already borrowed, and move only that across. The moved payload goes from 200,000 entries to a few dozen.

A-14 Ancestor columns run the full listing lifecycle for a column that draws names major

crates/ferret-ui/src/pane/column_view.rs:42–77 · folder/listing.rs:125–145

build_ancestor_columns creates up to MAX_ANCESTOR_COLUMNS = 3 real Folders and calls start_loading on each. finish_loading then unconditionally runs attach_watch, reload_expanded_children, start_metadata_backfill and request_os_icons — for columns that render only an icon, a name and a chevron (column_view.rs:259–321).

So pressing Cmd-2 in ~/Downloads attaches three extra OS watchers, starts three extra full metadata backfills (A-03) and clones three more listings for icons (A-11). In a deep path under a large directory that is a visible stall on a keystroke that should be instant.

Fix Give Folder a listing profile — { metadata, watch, icons } — set to browse-only for ancestor columns and for the path bar's completion listing (A-15). It is one struct and four ifs, and it is the same seam Phase 2 will want when the terminal asks for a directory it is not displaying.

A-15 The path bar materialises the whole directory on every keystroke major

crates/ferret-ui/src/browser/path_bar.rs:93–129

refresh_completions re-lists on every InputEvent::Change — correct, and correctly generation-guarded. But it collects every entry into a Vec first and only then filters:

while let Some(Ok(entry)) = ...next(&mut stream).await {
    entries.push(entry);          // 200,000 Entry allocations…
}
let matches = matching_directories(&entries, &prefix);   // …to keep ~8

The module header says a popover taller than a handful of rows stops being a hint. The filter agrees; the collection does not.

Fix Filter inside the loop and break at the popover's cap. Dropping the stream cancels the walk, so a completion in a huge directory stops after a few entries instead of reading all of it.

A-22 convert() rebuilds the same path three times minor

crates/ferret-vfs/src/local.rs:257–301

entry.path() is called at :258, :269 and :291 — each one allocates a fresh PathBuf by joining the parent to the name. The symlink and broken-link branches are guarded, so the second and third only fire for links, but the first fires for everything. entry.file_name().to_string_lossy().into_owned() at :259 then allocates a second copy of a name the PathBuf already contains.

Fix Hoist let local = entry.path(); once. With D-35's Arc<Path> the name can be a SharedString built from the same buffer, removing the duplicate too.
§5

Model bookkeeping & correctness

Two of these are bugs, not slowness. Both are in the watcher path, which is the part a test suite is least likely to cover and a user is most likely to hit.

A-04 apply_probes uses indices it has already invalidated critical · correctness

crates/ferret-ui/src/folder/expansion.rs:114–172

Within one loop over a watcher burst, the function both inserts into and removes from self.entries:

for (path, result) in probed {
    match result {
        Ok(entry) => match self.top_index.get(&vp).copied() {
            Some(ix) => { *self.entries.get_mut(ix) = entry; }
            None     => { self.entries.insert(pos, entry); }   // shifts every index ≥ pos
        },
        Err(err) if err.is_gone() => {
            if let Some(ix) = self.top_index.get(&vp).copied() {
                self.entries.remove(ix);                        // shifts every index > ix
            }
        }
        ...
    }
}
self.rebuild_index_and_order();   // the index is only repaired here, after the loop

top_index maps path → index into entries. After the first insert or remove, every index above the edit point is off by one — but the loop keeps consulting the stale map. So a burst carrying two deletions removes the wrong entry the second time, and a burst mixing a create with a delete overwrites an unrelated row. The listing then disagrees with the disk until a manual refresh, silently.

Bursts carrying several paths are the normal case, not the edge case — the debounce and drain at folder/listing.rs:163–179 exists precisely to coalesce them.

Fix Resolve every probe against the pre-loop index first, then apply the mutations in one pass: collect the set of paths to drop and do a single entries.retain(...), collect the new entries and insert them in one merge, then reindex once. That also removes the O(n) Vec::remove memmove per deletion. Add a test: two files deleted in one probe batch, assert both are gone and nothing else moved. The existing folder/tests.rs already has the machinery to build one.

A-06 The watcher drops events when its channel fills, and nothing resyncs critical · correctness

crates/ferret-vfs/src/watch.rs:52, :74

The channel is bounded(64) and the callback is let _ = tx.try_send(kind);. The doc comment (watch.rs:47–50) reasons that dropping a new event costs freshness while blocking the watcher thread costs the backend — which is the right trade. But it is only right if someone is told that a drop happened. Nobody is.

Sixty-four events is very little. A git checkout, an npm install, an unarchive or a build all blow through it in milliseconds. The events past the sixty-fourth are gone, the consumer never learns that its picture is incomplete, and the listing stays wrong indefinitely — there is no periodic reconciliation to catch it.

The model already knows how to handle this shape: WATCH_RELOAD_THRESHOLD (folder/mod.rs:49–54) says a burst above 512 paths is answered with one clean walk. Overflow is the same situation arriving through a different door and deserves the same answer.

Fix On a failed try_send, set an overflowed flag; when the channel next has room, send a single WatchEvent::Desynced. The consumer turns that into reload_preserving_state. Roughly fifteen lines, and it converts a silent wrong-forever into a re-list.

A-05 Every watcher burst triggers a full O(n) reindex critical

crates/ferret-ui/src/folder/sort.rs:127–164

rebuild_index_and_order clears and refills three hash maps — row_of_path, top_index and known_paths — each keyed by a cloned VfsPath. That is roughly 3n PathBuf allocations plus 3n hashes of a full path string, and it is called from resort, rebuild_order, toggle_expanded, load_children and — the one that matters — apply_probes.

So saving one file in flat/ costs ~600,000 allocations and ~600,000 hashes of ~60-byte strings. That is not a frame; that is several.

Fix Three layers, each independently worthwhile. (1) Arc<Path> keys (D-35) turn every clone into a refcount bump. (2) Key the top-level maps by name, not by full path — every entry in entries shares one parent, so the name is already unique within the map and is an order of magnitude shorter to hash. Swap the hasher too: SipHash on 60-byte paths is ~36 MB hashed per rebuild, for a threat model Ferret does not have (§9). (3) Don't rebuild when nothing structural changed: a probe batch that only refreshed metadata in place needs no reindex at all, and apply_probes already tracks metadata_changed separately from changed (expansion.rs:118–169) — the information is there, it just isn't used to skip the work.

A-12 The Kind comparator allocates a String per comparison major

crates/ferret-ui/src/folder/sort.rs:268–272 · crates/ferret-vfs/src/path.rs:114–124

cmp_entries for SortKey::Kind calls a.path.extension(), and VfsPath::extension ends in to_ascii_lowercase() — a fresh String. Inside a comparator. Sorting 200,000 entries is ~3.4 million comparisons, so one click on the Kind header is roughly 6.8 million heap allocations.

The same call is on the render path via FileIcons::asset_path (icons.rs:96), once per row per frame.

Fix Cache the lowercased extension on Entry at listing time — it is needed by icon dispatch anyway, so it pays for itself twice. Failing that, decorate-sort-undecorate. While in the file: sort_by → sort_unstable_by; the comparator already ends in a total-order name tiebreak (sort.rs:281), so stability buys nothing and the scratch buffer is n/2 elements.

A-13 Filtering lowercases both sides into new Strings, per entry major

crates/ferret-ui/src/folder/sort.rs:223–231, :95–112

is_visible does e.name.to_lowercase().contains(&f.to_lowercase()). The needle is re-lowercased for every entry, and every name is lowercased into a fresh allocation. That is ~400,000 allocations per keystroke on flat/, and the filter field fires on every keystroke (browser/mod.rs:222–226). select_by_prefix has the same shape per row per type-ahead character.

Fix Build one case-insensitive matcher per keystroke and run it over the names without allocating either side — aho-corasick is already in the lock and does exactly this with SIMD (§9). Keep the behaviour identical; the existing filter tests should not change.

A-17 One OS watcher per Folder major

crates/ferret-vfs/src/watch.rs:51–86 · folder/listing.rs:147–204

Watch::start constructs a notify::recommended_watcher per call, and each one is its own FSEvents stream (macOS) or ReadDirectoryChangesW registration (Windows), plus its own thread and its own GPUI task draining it. Every tab has one; column view adds up to three more per tab. Ten tabs in column view is up to forty native watchers and forty tasks — for a handful of distinct directories, several of which are shared between tabs.

Fix A watcher registry in ferret-vfs: one backend watcher, a HashMap<PathBuf, Vec<Sender>> of subscribers, reference-counted so the last unsubscribe unregisters the path. This is what Zed's fs crate does, and it is dramatically easier to add now than after remote mounts introduce a second watching mechanism. See D-36.

A-23 entry_names() copies the directory for a membership test minor

crates/ferret-ui/src/folder/mod.rs:315–317 · browser/mutations.rs:32–34, :174–178, :236

It builds a HashSet<String> of every name in the directory — 200,000 allocations — and every caller uses it only to ask unique_name whether a candidate is taken (format.rs:136–155). It is called synchronously from new_folder, new_file, transfer and paste_clipboard, all on the UI thread, all right before a filesystem operation.

Fix Pass a predicate instead of a set — unique_name(|name| folder.contains_name(name), …) — and answer it from the existing index. With A-05's name-keyed map that is an O(1) lookup with no allocation at all.

A-24 Expanded subtrees are never refreshed, and the code reads as though they are minor

crates/ferret-ui/src/folder/listing.rs:216–221 · vfs/watch.rs:79

start_watch_apply drops any path whose parent is not self.dir. That filter is harmless but misleading — the watch is registered NonRecursive, so events for expanded children never arrive in the first place. A folder expanded in place (§8) shows a snapshot that never updates until it is collapsed and reopened.

Fix Decide and write it down. Either watch each expanded folder (natural once A-17's registry exists — subscribing to a second path becomes cheap), or keep the current behaviour and replace the filter's implicit claim with a comment saying expanded subtrees are a snapshot by design.
§6

Blocking the UI thread

The Vfs contract's first promise is "nothing blocks a frame" (vfs/vfs.rs:38–44). Four places break it, one of them on every folder you open.

A-09 Preferences are written synchronously on every navigation — and the debounce for it is dead code major

crates/ferret-ui/src/browser/tabs.rs:191–209 · state.rs:82–89, :118–139 · ferret-settings/src/config.rs:30

record_current_view ends in state.save_prefs(), which is write_atomically: a create_dir_all, a full serde_json::to_string_pretty of up to FOLDER_PREFS_CAPACITY = 4_000 records (~500 KB by the module's own estimate), a write and a rename. All on the UI thread.

It is called from PaneEvent::ViewChanged (tabs.rs:67) and from swap_active_tab (tabs.rs:94) — so every sort click, every column toggle, every view-mode change and every folder you enter serialises and writes half a megabyte before the next frame.

The machinery to avoid this already exists and is entirely unused:

  • ferret_settings::config::SAVE_DEBOUNCE is defined, documented with exactly this failure ("without this, dragging a column edge would write the file on every frame"), and referenced nowhere in the workspace.
  • FolderPrefs::is_dirty() (folder_prefs.rs:187) has a passing test proving an idle app can skip writing, and no caller.
Fix A debounced save task on FerretState: record_current_view marks dirty and (re)arms a SAVE_DEBOUNCE timer; the timer checks is_dirty() and writes on the background executor. Flush synchronously once, on window close. While there: to_json uses serde_json::to_string_pretty (folder_prefs.rs:118) on a file the module header explicitly says is "written by the app rather than by hand" — pretty-printing it is roughly double the bytes and a slower serialiser, for nobody. This is the finding with the best effort-to-relief ratio in the document — everything it needs is already written.

A-18 Creating a file or folder blocks the window major

crates/ferret-ui/src/browser/mutations.rs:36–67 · browser/mod.rs:368–370

smol_block_on(fs.create_dir(&path)). The comment argues a local mkdir is sub-millisecond and that blocking buys a live window to start the inline rename in. The first half is true on APFS and false on an SMB share, a sleeping external disk, or a network mount that has gone away — and the second half is solvable without blocking.

Fix Spawn, and start the rename from the completion. The pane already has a pending_rename slot (pane/mod.rs:126–127) with a render-time hand-off (pane/render.rs:10–12) built for precisely this "I need a &mut Window I don't have" situation — the slow-click rename uses it already.

A-25 The volume list can hit the filesystem during render minor

crates/ferret-ui/src/browser/mutations.rs:374–383 · browser/mod.rs:50 · platform/macos.rs:158–187

volumes() caches for VOLUMES_TTL = 15s, but it is called from the sidebar's render pass, so when the TTL expires the frame pays for a read_dir("/Volumes") plus a metadata() per entry. A stale network mount stalls that call, and stalls the window with it. PROBE_TIMEOUT_MS (platform/config.rs:25) was clearly written for this hazard and is never used.

Also blocking, lower stakes: save_settings is synchronous on the same thread and fires from toggle_hidden, toggle_sidebar, toggle_theme and add_current_to_favorites (mutations.rs:286, :307, :325, :357) — a much smaller file, but it rides the same fix as A-09. go_to_existing_parent (tabs.rs:157–168) walks up the tree with synchronous Path::is_dir calls; it only runs when a folder has vanished, but that is exactly when the parent may be an unresponsive mount.

§7

jwalk: where it belongs

Yes — but not where you would first reach for it, and not without deciding what it means for the search crate.

jwalk is a rayon-backed parallel directory walker. Its win is many stats and many directories. It is not a faster readdir: reading the names out of one directory is a serial syscall stream and no library changes that. Which is exactly why the obvious place to put it is the wrong one, and the unobvious place is worth several seconds.

Use it here

  • The metadata tier (A-03). The single biggest win in this document.
  • copy_tree — vfs/local.rs:317–355, single-threaded recursion, and it is what a cross-volume move runs.
  • Recursive delete — remove_dir_all at local.rs:245 and macos.rs:90 has the same shape.
  • Folder size on demand — the Size column deliberately shows nothing for directories (entry.rs:85–91); when "calculate size" arrives it is a parallel walk or it is a hang.
  • Trash pre-flight and conflict scanning for the future ferret-ops queue.

Do not use it here

  • The Phase-1 single-directory listing, as it stands. The name tier is already measured at ~0.3 ms to first row and ~143 ms for 200,000 entries (xtask/config.rs:52–64). It is not the bottleneck. Dropping jwalk in without also fixing A-10 just moves the queue.
  • Search (F-40s). plan.html already commits to ignore + grep-searcher, and ignore::WalkBuilder is a parallel walker with gitignore semantics. Adopting jwalk there too means two parallel walkers and two thread pools for one job.

D-33 Resolve metadata during the walk, with jwalk, and make metadata_in_listing true on both platforms.

Replace LocalFs::read_dir's std::fs::read_dir loop with jwalk::WalkDir::new(dir).max_depth(1).skip_hidden(false) over a Ferret-owned rayon pool, reading DirEntry::metadata() — which the walker has already resolved on its worker threads — and emitting Entry batches (A-10) with metadata: Some(_) filled in.

Folder::start_metadata_backfill then deletes itself: it already returns early when capabilities().metadata_in_listing is set (expansion.rs:237–240), which is the Windows path today. One code path on both platforms, and the Size and Date columns are populated the moment a row appears instead of minutes later.

Because The Capabilities doc comment (vfs/vfs.rs:18–25) already anticipates this — "assuming two would throw away the Windows win, and assuming one would stall macOS on a 200,000-entry directory". The right resolution is to stop having two tiers on the local backend at all, and keep the flag for remote mounts where a second round trip is genuinely expensive.

D-34 jwalk for bulk file work; ignore for search. One walker per job, never both for the same job.

jwalk owns metadata resolution, tree copy, tree delete and directory sizing — jobs with no ignore semantics, where the lower overhead matters. ignore owns filename and content search, where honouring .gitignore is the entire feature. Neither is used for the other's job.

Because Both crates are parallel walkers and it is very easy to end up with both doing the same job in different parts of the codebase, at which point nobody can reason about how many threads are walking the disk. Writing the split down now costs a paragraph; discovering it in Phase 5 costs a refactor.

What to price in before adopting it

jwalk adoption hazards

§8

Architectural changes

Three reshapes. The first two are the ones that make most of §3 and §5 unreachable rather than fixed; the third is the one that gets harder every phase you leave it.

D-35 Entry holds shared handles, not owned buffers.

pub struct Entry {
    pub path: VfsPath,          // PathBuf inside — heap alloc per clone
    pub name: String,           // second heap alloc per clone
    pub path: VfsPath,          // Arc<Path> inside
    pub name: SharedString,     // SmolStr: inline to 22 bytes, then Arc<str>
    pub kind: EntryKind,
    pub metadata: Option<Metadata>,
    pub link_target: Option<Arc<Path>>,
}

Mechanical, wide, and it does not change a single call site's shape — every .cloned() in the render path stays exactly as written and becomes a refcount bump and a short memcpy. It is the precondition for A-02, A-05, A-08, A-11 and A-22.

SharedString specifically, not Arc<str>: it is built on smol_str, which stores up to 22 bytes inline, so most filenames cost no allocation and no atomic at all. §9 has the detail and the even-cheaper variant that derives the name from an offset into the path.

Because Do it before Phase 2, not after. ferret-terminal will hold paths for cwd sync, and ferret-ops will hold them for the operation queue; converting two crates is cheaper than converting four. It is also the kind of change that is trivial while the tests are green and miserable in the middle of a feature.

D-36 Rows get a stable id. Selection, cursor, anchor and expansion key on it instead of on a path.

Introduce EntryId(u32) — an index into a per-Folder slab that is not invalidated by sorting or filtering. Then:

  • selection: HashSet<EntryId>, anchor/cursor: Option<EntryId>, expanded: HashSet<EntryId> — u32 hashing, zero allocation.
  • order: Vec<Row> stays; row_of_path becomes Vec<EntryId> plus one HashMap<SharedString, EntryId> built once per listing rather than once per watcher burst.
  • rebuild_index_and_order stops allocating entirely — it permutes u32s.

The module header's rule ("selection is stored as paths, never indices, because a watcher reload reshuffles rows") is right and is preserved: an EntryId is not a display row and not an index into entries. It is a stable identity that survives re-sorting, which is what the rule was actually protecting.

Because This collapses A-05, most of A-02 and all of A-23 into one change, and it is the single hardest thing in this document to retrofit — every one of the ~40 call sites that touches selection, cursor or row_of_path gets touched, and that number only grows.

D-37 One watcher registry in ferret-vfs, not one watcher per Folder.

A registry owning a single backend watcher per backend, with reference-counted subscriptions per path. Watch stays exactly what it is from the caller's point of view — a handle whose drop unsubscribes — so nothing above it changes. Add the overflow-and-resync signal from A-06 here, once, rather than per watcher.

Because Remote mounts (Phase 7) will need a completely different change-detection mechanism — polling for SFTP, notifications for nothing at all on S3 — and a registry is the seam where that plugs in. Adding it while there is exactly one backend is a refactor of one file.

Two structural things worth saying that are not decisions yet

The listing profile

A-14 and A-15 are the same problem: Folder has one lifecycle and every consumer pays for all of it. Ancestor columns want names and icons; the path bar wants directory names and nothing else; the browsed directory wants everything. A ListingProfile { metadata, watch, icons } passed to Folder::new is three fields and four branches, and Phase 2's terminal — which will want to know about a directory it is not rendering — is the third consumer that makes it obviously right.

The operations queue is load-bearing sooner than Phase 6

plan.html schedules ferret-ops late, which is defensible. But transfer and paste_clipboard (mutations.rs:180–221, :240–279) are today a detached task looping awaits, with no progress, no cancellation and no undo. Copying 40 GB is currently invisible and unstoppable — the only feedback is a toast if it fails. A-18's fix and jwalk's parallel copy_tree (D-34) both want somewhere to live, and that somewhere is the queue. Consider pulling a minimal version of it forward: a job list, progress, and cancel. Undo and conflict policy can stay in Phase 6.

On ferret-core

plan.html's rule — do not create a crate before there is code for it — is right and this audit does not propose breaking it. But note the trigger condition has nearly arrived: ferret-terminal will want VfsPath and nothing else from ferret-vfs. That is the second consumer the rule was waiting for. Extract ferret-core when Phase 2 starts, and fold D-35's representation change into the same commit — one wide mechanical change instead of two.

parking_lot — for correctness first, speed second

Ferret holds std::sync::Mutex in eleven places, every one of them guarding a critical section of a few nanoseconds: read a Vec of at most four columns (list.rs:123), read a Point (icon_view.rs:270), take an Option (pane/render.rs:15–22), look up an icon (macos.rs:216). Short critical sections are exactly where parking_lot's adaptive spin-then-park wins, and where its one-byte lock word matters against std's larger inner state.

But the better argument is that poisoning is doing active harm here:

// icons.rs:130 — a poisoned cache silently becomes "no icons, forever"
self.cache.lock().ok()?.get(key)?.clone()

// pane/list.rs:130 — same shape: a poisoned width map silently reverts to defaults
self.widths.lock().ok().and_then(|w| w.get(&column).copied())

Both swallow a poisoned lock into an indistinguishable "no value". parking_lot has no poisoning, so lock() returns the guard directly — the .ok()? disappears along with the failure mode it was hiding, and the twenty-odd .lock().unwrap() calls elsewhere lose their panic path.

Do not let this substitute for the real fix

parking_lot makes A-01's per-row lock cheaper. It does not make it correct to take a lock once per row per frame. Do the ArcSwap change below; adopt parking_lot for the locks that remain.

Hashing — the largest library-level win in the document

Rust's default hasher is SipHash-1-3, chosen to be HashDoS-resistant against attacker-supplied keys. Ferret's index keys are paths from the user's own local disk. It is paying a cryptographic-ish hash for a threat model it does not have.

The arithmetic on A-05: rebuild_index_and_order fills three maps of n entries keyed by full VfsPath. On flat/ with ~60-byte paths that is 3 × 200,000 × 60 ≈ 36 MB hashed per rebuild — and it rebuilds on every watcher burst. At SipHash's ~1.5 GB/s that is roughly 24 ms of pure hashing to react to one file being saved. Fx or foldhash on short keys runs several times faster, and A-05's name-keying (~15-byte keys) cuts the input by four again.

Two caveats, both real

Version split. The lock has rustc-hash 1.1.0 (via Zed's collections). Declaring rustc-hash = "2" compiles a second copy rather than unifying. That is a real duplicate but a trivial one — the crate is a few hundred lines with no dependencies — and 2.x's FxHasher is meaningfully better than 1.1's on longer keys. Take the duplicate; do not contort the version to avoid it. Adversarial keys. This is the caveat that actually matters. Local paths are the user's own, but Phase 7's S3 and WebDAV mounts return keys chosen by a remote server, and Fx is trivially collidable on purpose. Either use Fx for the local indices only and a seeded hasher for anything keyed on remote-derived names — or use foldhash everywhere and take a slightly smaller win with no caveat and no duplicate at all. That is still the option I would pick.

SharedString is better than the Arc<str> D-35 asked for

Worth stating precisely, because it upgrades D-35: gpui::SharedString is backed by gpui_shared_string, which is backed by smol_str. SmolStr stores strings of up to 22 bytes inline and falls back to Arc<str> above that.

Most filenames are under 22 bytes. So for the common case Entry.name becomes zero heap allocation and zero atomic refcount — a 24-byte memcpy on clone, which is strictly better than Arc<str>, and it degrades gracefully to shared ownership for the long ones. D-35 should say SharedString, not Arc<str>, and it costs nothing to say so.

The path still wants Arc<Path> — paths are long and genuinely shared. The best version stores only the path and derives the name from a byte offset into it:

pub struct Entry {
    path: Arc<Path>,
    name_at: u16,            // byte offset of the final component
    ...
}
impl Entry {
    // O(1) slice, no parse, no allocation — which is what the
    // comment at vfs/entry.rs:61–63 was actually asking for.
    pub fn name(&self) -> &str { &self.path_str()[self.name_at as usize..] }
}

That removes the duplicate storage A-22 notes without giving up the property the existing comment defends. If the borrow lifetimes make it awkward at the call sites, SharedString is the pragmatic answer and is still a large improvement.

arc-swap — the right shape for the icon cache

A-01's access pattern is read-mostly to an extreme degree: read once per row per frame, written a few dozen times in the life of a directory. That is what ArcSwap is for.

pub struct MacIcons {
    cache: Mutex<HashMap<IconKey, Option<IconBitmap>>>,
    cache: ArcSwap<FxHashMap<IconKey, Option<Arc<RenderImage>>>>,
}

The render path becomes a lock-free atomic load plus a map lookup plus an Arc clone — no mutex, no 16 KB memcpy, no RenderImage reconstruction, and a stable image identity so GPUI reuses the texture. The resolver clones the map, inserts, and swaps; with a few dozen entries that copy is irrelevant and happens off the render path.

One wrinkle worth planning for: RenderImage lives in gpui, and ferret-platform is a service crate. plan.html's layering rule permits service crates to depend on gpui itself (only gpui-component is restricted to ferret-ui), so this is allowed. If you would rather not, keep the provider returning bitmaps and put the ArcSwap<…, Arc<RenderImage>> cache in ferret-ui in front of it — the render path ends up identical.

aho-corasick for filtering

A-13's fix has an obvious hand-rolled form (lowercase the needle once, ASCII fast path). But aho-corasick is already in the tree and does it better:

// built once per keystroke, not once per entry
let matcher = AhoCorasick::builder()
    .ascii_case_insensitive(true)
    .build([needle])?;
// then, per entry: SIMD, no allocation, no lowercasing of either side
matcher.is_match(entry.name())

200,000 allocation-free SIMD searches instead of 400,000 String allocations, and it is the same engine that will do the work when search lands.

rayon — already here, and A-12 wants it

Sorting 200,000 entries on a Kind or Size header click is embarrassingly parallel. rayon::slice::ParallelSliceMut::par_sort_unstable_by is a one-line swap for sort_by once A-12's comparator stops allocating (a comparator that allocates is a comparator you must not run on eight threads). Use the same Ferret-owned pool D-33 constructs, so the sort and the walker share one set of workers rather than each sizing itself to the core count.

tracy-client is nearly free, because the instrumentation already exists

This is the find of the section. profiling 1.0.18 is in the lock, pulled directly by gpui (and by wgpu beneath it). The profiling crate is a facade: the scope! macros compile to nothing until a backend feature is turned on, and GPUI's render pipeline is already sprinkled with them.

So enabling profiling/profile-with-tracy and adding tracy-client gives you GPUI's own frame, layout and paint spans without writing a line of instrumentation — and Ferret's own profiling::scope! calls slot into the same timeline. For a document whose top three findings are all "this runs once per row per frame", that is exactly the instrument required, and it turns §3 from arithmetic into a flame graph.

Pick the backend deliberately

tracy-client needs the external Tracy profiler application, which is a superb tool and an extra thing to install. puffin is self-contained and renders in-process, which is friendlier for contributors but far less capable. Either is a one-line feature swap since both sit behind the same profiling facade — so this is not a decision that has to be got right first time, which is the best kind.

dhat turns §11's third budget from a number into a test

§11 proposes an allocations-per-frame measurement and suggests hand-rolling a counting global allocator. dhat already is one, with a better story:

// behind a feature, never in a release build
#[global_allocator]
static ALLOC: dhat::Alloc = dhat::Alloc;

let _p = dhat::Profiler::builder().testing().build();
scripted_scroll_of_flat_with_everything_selected();
let stats = dhat::HeapStats::get();
// the budget, as an assertion CI can fail on
assert!(stats.total_blocks < BUDGET, "{} allocations per frame", ...);

The difference between a printed number and a failing assertion is the difference between a regression someone notices and a regression someone ships. A-01, A-02 and A-08 all leave wall-clock timings on a fast machine essentially untouched; none of them survives an allocation assertion.

divan for the budgets themselves

xtask bench currently times one run and compares against a constant, which is honest but noisy — it is why FIRST_ROW_BUDGET had to be set at 50 ms to catch a 0.3 ms operation "in kind rather than machine-to-machine variation" (xtask/config.rs:47–52). A real harness gives distributions instead, which lets the budgets tighten enough to catch a 2× regression rather than only a 100× one. divan is the light option; criterion is the thorough one and costs noticeably more build time. Either is fine — divan is the one I would reach for on a workspace that already takes a long time to compile.

This is the one number that would have caught A-01 and A-02 the day they were written — and as a dhat assertion it fails CI instead of scrolling past in a log. And one thing to turn on before any of it

gpui is already instrumented with the profiling facade (§9). Enabling a backend costs one feature flag and gives frame, layout and paint spans through GPUI's own pipeline — so §3's findings stop being arithmetic and start being a flame graph you can point at. Do this first; it will change which of the twenty-six you care about most, and it may well disagree with my ordering.

Gate 7

Worth adding to AGENTS.md's gate list, in the same spirit as the six that are there: no per-frame work may be O(the directory). It is checkable by reading a diff, it is the single rule that would have prevented six of these findings, and unlike a timing budget it does not depend on how fast the reviewer's machine is.

§12

The order to do this in

Sequenced so each step is independently shippable and the app runs at the end of every one. Steps 1 and 2 are worth doing before Phase 2 starts; the rest can interleave with it.

Before step 1: turn on the profiling backend (§9) and stand up the dhat allocation budget (§11). Both are an afternoon, neither changes any behaviour, and together they mean every step below lands with a number attached instead of an argument. It is also the only honest way to check whether my ordering is right — see §13.

§13

What this did not check

Stated plainly, so nothing here is mistaken for a clean bill of health it did not earn.

  • Nothing was profiled. No build was run, no instrument was attached. Every complexity claim comes from reading the call graph; every wall-clock figure is arithmetic from the sizes involved. §11 exists to convert the important ones into measurements the repository owns.
  • Windows was read, not run. ferret-platform/src/windows.rs was read for shape and for the metadata_in_listing claim. The unsafe icon path there was not audited with the care the macOS one received.
  • GPUI's own behaviour is assumed, not verified. A-01 rests on GPUI keying its texture cache on RenderImage identity. That is the standard behaviour and the fix is correct either way, but the magnitude should be confirmed against the pinned revision before it is cited as the top finding in a commit message.
  • The theme, the icon assets and the settings schema were not reviewed beyond what the performance path touches. Gate 3 (both themes) was not re-checked.
  • No security review. The unsafe AppKit block in macos.rs has a well-written safety comment and a well-formedness guard at the boundary; it was read, not verified against the AppKit threading rules it claims.
  • The library claims were verified against Cargo.lock, not against a build. Every version and every "pulled by" in §9 was read out of the lockfile, so the crates are certainly present — but no benchmark compared SipHash to foldhash on Ferret's own keys, and the 36 MB figure is arithmetic. Do the swap behind the §11 counter, not on my say-so.
  • The tests were not run. terminal.html reports 122 passing; this audit takes that at face value. Several findings above propose new tests, and three of them (A-04, A-06, the §11 allocation counter) would likely fail today.
The overall read

This is a well-built Phase 1. The hard structural calls — streaming listings, cancel-by-drop, path-keyed selection surviving a re-sort, an icon provider that never touches the OS on the render path, capabilities declared rather than assumed — are all right, and every one of them is right for a reason written down beside it. What the audit found is almost entirely constant factors on top of correct structure: an icon cache that returns bytes where it should return a handle, a payload built eagerly where it should be built lazily, a metadata tier that is asynchronous but not concurrent. Those are the good kind of finding. The two watcher bugs are not, and they are step 1.
