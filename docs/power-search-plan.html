Detailed implementation plan · F-40–F-43 · 30 Aug 2026

Power Search, at filesystem speed.

An indexed, continuously refreshed filename and content search for Ferret, with a live-scan fallback for arbitrary regex and unindexed roots. It opens from a right-side top-bar toggle, preserves every control visible in the supplied reference, and adds the smallest set of high-value capabilities that improve latency without sacrificing correctness.

Decision summary

Executive verdict

Build the existing Phase 4 commitment as one modal Power Search surface backed by a GPUI-free service and a supervised background daemon. The daemon maintains a persistent path/content index; live filesystem scans cover new, stale, unindexed, remote, and arbitrary-regex cases. Bounded channels stream result batches into a virtualized table; generation IDs and cancel-by-drop prevent stale work from reaching the UI.

Recommended baselineTantivy for indexed content and fields; rusqlite for path metadata, crawl state, history and saved searches; notify plus reconciliation scans for freshness; nucleo for fuzzy path ranking; and ignore + grep-searcher + grep-regex for initial indexing, live fallback and arbitrary regex.
PS-D01

Use a hybrid persistent index. Indexed Home/current-folder queries should return in tens of milliseconds. The index is a performance layer, never the sole truth: watcher events update it, reconciliation repairs missed events, and opening a result re-stats the path. Unindexed or stale scopes transparently stream live results while indexing continues.

PS-D02

Literal by default; regex is explicit. Literal search enables the fastest prefilters. Regex compilation happens once per query with conservative pattern/compiled-size limits and inline errors.

PS-D03

Rank indexed results; stream live discovery. Indexed candidates may be relevance-ranked immediately. Live fallback never waits for a global sort, which would delay first results and disable traversal parallelism; it ranks only a bounded retained window before merging.

PS-D04

One query generation owns all work. Changing query, filters, or scope drops the old receiver and sets a shared cancellation flag. Every batch carries its generation; stale batches are ignored defensively.

PS-D05

The daemon is supervised and optional at runtime. Ferret starts one per-user helper on demand, negotiates a versioned local protocol, restarts it after failure, and falls back to in-process live search if it is unavailable. No network listener, elevated privilege, or always-required login item.

Included additions

  • Smart-case as the default, plus explicit case-sensitive mode; fixed-string/regex toggle; whole-word toggle for content.
  • Include hidden, respect ignore files, follow symlinks, and same-filesystem toggles under an expandable Options row.
  • Date and size ranges from F-42; exclusion globs; maximum depth; custom scope; recent searches stored as query settings only—never results or file content.
  • Content result context, highlighted match, file/line/column, copy path, reveal, open, Space preview, and keyboard navigation.
  • Clear disclosure when results are capped, files are skipped, access is denied, a remote backend is filename-only, or the query is still running.

Non-goals for first delivery

  • No OCR, semantic/vector search, archive decompression, PCRE2, or searching inside proprietary document formats. The persistent index covers supported text and metadata only.
  • No cloud-hosted index, network API, telemetry, cross-device synchronization, or system-wide privileged service. Index data stays per-user and local.
  • No attempt to provide regex backreferences/look-around; the Rust regex syntax is fast and bounded precisely because those are excluded.
  • No global result sort that waits for completion. No unlimited result retention. No UI-thread filesystem access.

New crate: ferret-search

This is the point at which a second service needs VfsPath/EntryKind. Prefer moving only truly shared domain types to ferret-core if necessary; do not make ferret-search depend on ferret-ui or gpui-component. The service library owns query planning and can run in-process for tests/fallback; a small ferret-searchd binary owns the persistent index lifecycle. Public request/result types must not assume slash paths.

SearchService::start(SearchRequest) -> SearchSession
SearchSession { events: Receiver<SearchEvent>, cancel-on-drop }
SearchEvent = Batch { generation, results } | Progress(...) | Warning(...) | Finished(...)
SearchResult = File { path, metadata } | Content { path, line, column, ranges, preview }

Daemon and index lifecycle

  • Process model: one unprivileged daemon per signed-in user, launched on demand by Ferret and kept alive while useful. A lock file or platform mutex prevents duplicates; idle shutdown is configurable.
  • Local protocol: versioned framed messages over a Unix-domain socket on macOS and named pipe on Windows. Authenticate through filesystem/pipe ACLs and a per-launch nonce; never bind TCP.
  • Stores: Tantivy segments hold tokenized content and searchable fields; SQLite holds canonical path identity, file fingerprint, crawl/index state, roots, exclusions, recent queries and saved filters.
  • Freshness: notify marks paths/roots dirty, a debounced queue applies incremental updates, and periodic plus startup reconciliation catches dropped/coalesced watcher events.
  • Recovery: writes are transactional or segment-atomic. Corrupt/incompatible indexes are quarantined and rebuilt from source; search falls back to live scanning during rebuild.
  • Privacy: index roots are explicit and inspectable; excluded paths never enter either store. The settings UI shows size, last refresh, paused/error state, rebuild and delete controls.

Hybrid query planner

  • Filename/path substring and metadata filters query SQLite/trigram fields; optional fuzzy ranking runs bounded candidates through Nucleo.
  • Token, phrase and prefix content queries use Tantivy. Candidate hits are filtered against current SQLite metadata and re-statted before destructive or open actions.
  • Arbitrary content regex, unindexed roots, stale dirty paths and unsupported remote backends use the ripgrep live path. Indexed and live streams deduplicate by stable file identity plus match location.
  • While initial indexing runs, return indexed hits immediately and stream live hits for uncovered portions. Progress distinguishes “search complete” from “index still building.”

Backpressure and scheduling

  • Use a bounded file-work queue and bounded UI-event channel. A slow frame must park search producers instead of materializing the tree.
  • Batch by count or a short deadline (for example 64 rows or 8 ms), whichever comes first. Notify GPUI once per batch, not once per match.
  • Reserve one CPU for the UI on machines with more than two logical cores; make thread count configurable and benchmark the heuristic.
  • Check cancellation before metadata work, before opening a file, after each file, and from the match sink. Dropping a session must stop observable output immediately.
  • Keep result data compact: shared root + relative paths where practical; bounded preview bytes; no entire file bodies; never load all results merely to sort.

UI integration points

  • Add TogglePowerSearch in ferret-ui/src/actions.rs; bind both platform shortcuts in the binary; add a bundled search icon.
  • Add the toolbar button in browser/title_bar.rs right action group. Mount a gpui-component dialog under the existing Root.
  • Keep the long-lived modal state in a focused search/ UI module, not in the already-busy browser render file. Results use Table/virtual_list.
  • Opening a result navigates the active tab by default. Modifier behavior opens a new tab. Content results carry a future preview/editor location without coupling the engine to preview UI.

Benchmark matrix

  • Flat 200,000-entry fixture; 2 million indexed paths; 10 GB text corpus; deep tree; many tiny files; few multi-GB files; binary-heavy tree; generated minified lines; inaccessible directories; symlink cycle; Unicode names.
  • Literal rare/common, regex anchored/unanchored, Unicode classes, case-insensitive, filename-only, content-only, combined filters, cap-hit, cancel after 1/10/100 ms.
  • Empty/new/current/stale/corrupt index; daemon cold start/restart/crash; watcher burst/drop simulation; rename across roots; removable volume disconnect; schema migration and full rebuild.
  • macOS APFS (case-sensitive and insensitive if available), Windows NTFS, removable/network volume. Report CPU count, storage, cache state, files/bytes scanned, ignored/skipped counts.

Important implementation corrections to the older product plan

  • Do not force mmap for “large files.” Ripgrep’s own documentation notes buffered reads usually win for directory searches; let the searcher choose and benchmark any threshold.
  • Do not make “sort results” the default. Ripgrep documents path sorting as disabling parallelism. Stream discovery order and offer post-completion sorting only when the retained set is bounded.
  • Do not send every hit to GPUI. Batch results and coalesce progress. The table must be virtualized from its first rendered row, satisfying the same gate as the base file pane.
  • Do not commit the index once per filesystem event. Debounce bursts, batch document changes and reload readers after commits; foreground queries always outrank indexing work.

Gated build order

Delivery sequence

Each stage leaves the workspace runnable. Do not advance when its gate fails.

PS-0

Lock semantics and fixtures

Write request/result/error types, query truth table, platform matrix, benchmark fixtures, and budgets before choosing UI details. Gate: tests cover smart case, globs, paths, cap, cancellation, and partial errors.

PS-1

Create the service and protocol skeleton

Add ferret-search, ferret-searchd, shared request/event types, versioned local IPC, supervised launch, in-process fallback, bounded channels and fake-engine tests. Gate: protocol mismatch/crash is recoverable and drop prevents every later generation event.

PS-2

Add SQLite schema/migrations, indexed roots, ignore crawler, fingerprints, kinds, hidden/ignore/symlink policy, extension/date/size/depth fields and FTS5 trigram path search. Gate: 2 million paths meet query, crawl, storage, restart and migration budgets.

PS-3

Incremental freshness

Connect notify, dirty queues, batched updates, periodic/startup reconciliation, volume disconnect handling and rebuild/quarantine flows. Gate: watcher storm/drop tests converge to filesystem truth without busy idle I/O.

PS-4

Modal shell and toolbar toggle

Add actions, icon, platform keybindings, Root-hosted dialog, focus trap/restore, fields, scope tabs, index status and virtual results. Gate: both themes/sizes pass; arrows follow focus; table stays smooth while indexing and streaming.

PS-5

Add Tantivy schema/writer/reader, token/phrase/prefix queries, snippets and ranking; add grep-searcher/grep-regex for arbitrary regex, dirty paths and unindexed scopes. Gate: indexed and live latency budgets pass and merged results deduplicate correctly.

PS-6

Complete filters and scopes (F-42/F-43)

Add range controls, exclusions, custom folder, volume roots, indexed-root management, history/saved filters and capability-aware remote surface. Gate: no local-path assumptions leak into public result identity.

PS-7

Actions, accessibility and resilience

Open/reveal/copy/preview hooks, result caps, partial warnings, screen-reader names, keyboard parity, IME-safe debouncing, stale-path behavior, daemon recovery and index controls. Gate: complete interaction/state checklist on both platforms.

PS-8

Profile and harden

Flamegraphs/allocations, cold start, initial crawl, long soak, cancellation storms, corruption/migration, regex limits, storage accounting and dependency/license audit. Gate: just lint, just test, search benchmarks, just build, and manual just dev verification all pass.

Honest uncertainty

Risks and open decisions

PS-Q01 · How should fuzzy filename matching appear?

Recommendation: ship explicit “Substring” and “Fuzzy” modes, defaulting to substring to match the reference. Nucleo reranks a bounded indexed candidate set; stable result IDs keep selection fixed while scores update.

PS-Q02 · What exactly is “Root” on Windows?

Recommendation: label it “Computer” and search selected mounted volumes, with all fixed local volumes as an explicit option. Avoid automatically scanning network/removable volumes.

PS-Q03 · How much context should content results retain?

Recommendation: one bounded display line plus match ranges and line/column. Read neighboring context lazily for preview; never retain whole file bodies.

PS-Q04 · Which roots are indexed by default?

Recommendation: index Home by default with standard cache/build/vendor exclusions, then let users add/remove roots and inspect estimated size. Do not automatically index network shares, removable volumes, system roots or remote mounts. Every root remains pausable, rebuildable and deletable.

PS-Q05 · Remote content search contract

F-43 leaves this genuinely backend-specific. Prefer a capability enum and explicit UI. An SSH backend may run remote rg/grep when available; S3/WebDAV are filename/metadata-only until a server-side search API exists. Never download an entire remote tree implicitly.

Primary risks

  • I/O saturation: unbounded parallel reads can make the whole machine feel slow. Bound content workers separately from traversal and preserve one CPU for UI.
  • Stale paths: the filesystem changes mid-query. Treat results as observations; re-stat on action and explain if the item moved or vanished.
  • Regex/resource abuse: linear matching is not free. Cap pattern length, compiled program size, file size, context, matches per file, total rows, and retained bytes.
  • Permission noise: whole-machine search can generate thousands of denials. Aggregate by category/root, keep useful results visible, and expose details on demand.
  • Index growth/privacy: a content index duplicates searchable information and reveals paths. Keep it per-user, access-controlled, capped, inspectable and completely deletable; exclude sensitive roots by default.
  • Daemon complexity: lifecycle, IPC, schema migration and crash recovery create new failure modes. Preserve the in-process live fallback and make every store rebuildable from source.
  • Scope creep: archives, OCR, semantic search and remote execution are separate capabilities. Do not block the indexed local core on them.
