The explorer shell

The window Ferret is before it is anything else: sidebar, tabs, path bar, file pane, status bar. Build this first; everything else plugs into it. Targets macOS and Windows.

§1

What this is

The missing reference — a design to build the base against.

Ferret's product plan (plan.html) catalogues 51 features but never shows what the window looks like. This document fills that gap for the base: an original mockup of the explorer shell, the region-by-region geometry, the gpui-component widget behind each region, the colour tokens, and the interaction contract.

It is not a screenshot of anything. Ferret's reference product, Iruka, is closed source and its screenshots are its own copyrighted assets, so nothing from them is reproduced here. What follows is Ferret's own design, converging — as Dolphin, Finder and Explorer all do — on the layout every file manager of this family uses.

How to use it

The mockup below follows this page's theme; hit theme in the sidebar to check the other one. Both are first-class — no token may be defined for only one. Every number in §4 is a logical pixel, matching what you pass to px() in GPUI.

§2

Base vs addon

The base is a complete, usable file manager on its own. Nothing in it is a placeholder.

The test for the base is simple: can you use Ferret instead of your system file manager for browsing, opening and organising files? If yes, the base is done. Everything that makes Ferret distinctive — the synced terminal above all — is an addon that lands on top of a finished shell.

Deliberately excluded from the base: the preview pane, the terminal panel, and the splitters and toggle buttons that drive them. They arrive with their features, so the base ships a full-width file pane rather than empty furniture.

File icons

Per D-18, icons come from the OS behind an IconProvider trait, because a Finder replacement whose icons do not match Finder looks wrong on sight. Both targets expose this, including application icons and custom folder icons:

Icon sources
PlatformAPIGives
macOSNSWorkspace.icon(forFile:)Real Finder icons, app bundles, custom folder icons, document badges.
WindowsSHGetFileInfo / IShellItemImageFactoryReal Explorer icons; the latter also yields thumbnails at arbitrary size.

Two rules make this safe at 200,000 rows:

  • Never call the OS on the render path. The provider answers instantly from a cache keyed by extension, or returns the bundled fallback and resolves the real icon in the background.
  • Ship the bundled set first. ~60 types covering the common extensions, so the list is never blank and never blocks. The OS providers land behind the same trait before the base closes — same interface, no rework.

Type

  • Interface: the platform UI face — -apple-system / Segoe UI / system default. 13 px rows, 11.5 px chrome, 10.5 px section labels.
  • Tabular numerals everywhere a number stacks — dates, sizes, counts. Without it the Size column visibly jitters.
  • No monospace in the base. It arrives with the terminal.

§9

States

The listing is not always a tidy list of files. Each of these needs a design before it needs code.

Every state the file pane can be in
StateWhat the user sees
LoadingRows stream in as the directory is read. No spinner-then-swap: show what has arrived. If nothing has arrived after ~200 ms, a subtle indeterminate bar in the column header.
Empty folderCentred, muted: "This folder is empty." Status bar reads 0 items.
Everything filtered out"No items match «query»" with a Clear filter action. Distinct from an empty folder — never conflate the two.
Permission deniedNamed and actionable: "Ferret can't read this folder. You don't have permission to open /private/var/root." Not a raw EACCES.
Folder deleted while openDetected by the watcher: banner offering to go to the nearest existing parent.
Broken symlinkRow shown with a struck-through or warning-tinted icon and the dead target in the Name column.
Very large directoryNo cap and no warning — virtualisation is the answer. 200,000 entries must scroll at full frame rate.
No selectionStatus bar shows the item count only, no selection clause.

Pane unfocusedSelection drops to --app-selected-idle; arrow keys go to whatever has focus.
§10

Build order

Inside the base, this is the sequence that keeps something runnable at every step.

  1. Filesystem layer. done ferret-vfs: the Vfs trait, the local backend with streaming read_dir, and the per-folder preference store. Testable with no window — 31 tests live there. Still to come: the change watcher.
  2. Window shell. Title bar, a static sidebar, and a file pane rendering one hard-coded directory as a virtualised Table. Point it at the fixture's flat/ and prove scrolling at 200,000 rows before going further.
  3. Navigation. Double-click to enter, up, back and forward with per-tab history, and the path bar.
  4. Selection and focus. Single, range and toggle selection; the focus model; the status bar.
  5. Sidebar for real. Places from the OS, Favorites with reorder and persistence, Volumes with mount and unmount watching.
  6. Tabs. Per-tab state, new, close, reorder.
  7. Sort, columns, filter. Header sorting, column resize and visibility, the inline name filter.
  8. The other two views. Icon and column, sharing the selection and navigation model already built.
  9. Mutation. Context menus, new file, new folder, inline rename, trash, copy/paste. Every path through a confirm-and-report flow.
  10. Watching. Live updates from notify, including the deleted-folder case.
  11. Settings and themes. Settings file, keymap, light and dark, per-folder view preferences.

Steps 1 and 2 are where the project's performance ceiling is set. If the table is not virtualised properly there, no later work recovers it.

Measuring it

cargo xtask fixture generates the tree every one of these steps is tested against — 200,000 flat entries, maximal nesting, 255-character and NFD and emoji names, broken and cyclic symlinks, an unreadable directory, a 4 GB sparse file, 59 extensions, and an ordinary project tree for eyeballing the UI on something realistic. cargo xtask bench measures the listing and fails past budget.

Budgets
MeasureBudgetActual
Time to first row, 200k entries50 ms0.3 ms
Full listing, 200k entries3 s143 ms
Frame time while scrolling< 8 msmeasured in the app, not the bench

The gap between 0.3 ms and 143 ms is the whole argument for streaming listings. If time-to-first-row ever approaches full-listing time, something has started collecting the directory before yielding it.

Done when

You can set Ferret as your default file manager and not miss the system one for browsing, opening, renaming, moving and deleting — on macOS and Windows.
