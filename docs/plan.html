§1

Summary

What we are building, and why it is worth building.

Ferret is a file manager for people who work in a shell. You browse folders in a graphical pane; an embedded terminal is already in that folder. No cd. Around that spine sit the things a developer actually needs from a file browser and never gets: git status in the listing, grep-and-regex search over file contents, real previews for Markdown and source code, SSH connections that mount as browsable folders, and a queue that shows what your copies are doing.

The idea is not ours. Iruka ships it today — a paid, closed-source, macOS-only app, itself an homage to KDE's Dolphin. Ferret's contribution is the two things Iruka is not: open source and cross-platform. Linux users lose Dolphin's terminal panel the moment they step outside KDE; Windows has no equivalent at all. That gap is the reason to build.

This document is the whole-product plan: the UI we are copying, every feature with an ID, the crate architecture, per-OS hazards, the decisions already made, and the order of work. Each feature will get its own detailed plan later; those plans should cite the IDs used here.

How to read this

Feature entries in §4 collapse and expand. Everything marked core is load-bearing for the product's identity — if it is cut, Ferret stops being Ferret. later means deliberately deferred past v1.0, not forgotten.

§2

Scope & non-goals

Drawing the line before any code is written.

In scope for v1.0

Feature parity with Iruka's five shipped roadmap phases — synced terminal, SSH, Markdown preview, git control, Power Search, syntax-highlighted previews, dual pane, in-place editing, cloud mounts, batch rename, operations queue, symlinks — running natively on macOS and Windows, with a light and a dark theme. Linux is deferred (D-19), not abandoned.

Explicit non-goals

Deliberately not building
Not buildingWhy
Licensing, activation, trial timers, paymentFerret is GPL-3.0. There is nothing to unlock.
Sparkle-style in-app auto-updateShip through the platforms people already use: GitHub Releases, Homebrew, Flatpak, AUR, winget, Scoop. Revisit only if release friction proves real.
Telemetry or analytics of any kindA file manager sees every path you touch. It should phone home never.
Iruka's name, icon, artwork, copy or brandFunctional layout is fair to reimplement; identity assets are not. Ferret gets its own name, icon and words. Do not copy strings from Iruka's site into the app.
A general-purpose text editorIn-place editing (F-36) means quick fixes to a config file, not an IDE. Anything larger opens in the user's editor.
Mobile, web or a plugin runtimeScope control. Revisit after v1.0.
On cloning a commercial product

Reimplementing a competitor's functionality and general window layout is ordinary and legitimate. Copying its assets, icon, name, marketing copy or code is not. Ferret should look like a native file manager of the same family — a three-pane browser over a terminal, which Dolphin, Finder and Explorer all converge on anyway — without lifting anything that identifies Iruka. Keep that line visible in code review.

Layout rules

  • Sidebar, preview pane and terminal panel are each independently collapsible, and each remembers its width or height across sessions.
  • Every divider is drag-resizable. Terminal is horizontal-split under the file pane; preview is vertical-split to the right of it.
  • Dual pane (F-05) splits the file pane itself, leaving one shared preview and one terminal per pane.
  • The window draws its own title bar on an opaque themed background. Blur and vibrancy are deliberately unused (D-15), so no surface may depend on translucency.
  • Minimum usable window is 760 × 480; below that, the preview pane collapses first, then the sidebar.
Build against the reference, not this section

This section frames the window. docs/ui-base.html is the buildable specification for the base shell: an original mockup in both themes, region geometry in logical pixels, the gpui-component widget behind each region, the token mapping, the full pointer and keyboard contract, and every state the file pane can be in.

Visual language

Ferret should read as native on each OS rather than as a macOS app ported twice. In practice that means one layout with per-platform details: title bar controls follow the host convention, the accent colour follows the system accent where one is exposed, and the default monospace font differs per platform. Light and dark are equal first-class themes — every token defined in both, no colour hard-coded for one.

4.2 Terminal

F-10Embedded terminal panel core

A real, xterm-compatible terminal docked beneath the file pane. One PTY session per tab. Full VT support: colours, mouse reporting, alternate screen, resize, scrollback, clickable URLs, copy and paste.

Behaviour: this is the feature that decides whether Ferret is credible. It has to be a genuine terminal — vim, htop, tmux and a TUI coding agent must all work — not a command runner with a log view. Plan for alacritty_terminal as the VT parser and grid model, with our own GPUI renderer on top.

F-11Directory sync between UI and terminal core

The signature feature. Navigate in the file pane and the terminal cds to match. A Sync toggle in the terminal header turns it off for when you are deliberately somewhere else.

Behaviour: sync must be safe. Never inject a cd while a foreground process is running or the shell is on the alternate screen — queue it and apply when the prompt returns. Paths must be shell-quoted. Crate architecture

Where the two-crate scaffold is heading, and the rule that keeps it from tangling.

Today

The repository holds two crates: ferret (the binary — GPUI bootstrap, window, menus, actions) and ferret-ui (views, components, theme). That is the correct starting point and should not be split before there is code to put in the new crates.

The layering rule

One direction only

ferret → ferret-ui → service crates → ferret-core. No service crate may depend on ferret-ui, and no crate other than ferret-ui may depend on gpui-component. Service crates may depend on gpui itself for its background executor and entity system — this is exactly how Zed structures project, terminal and fs, and fighting it costs more than it saves.

The payoff is that every service crate is testable without opening a window, and the parts most likely to be wrong — path handling, conflict policy, rename planning, search filtering — are exactly the parts that end up outside the UI.

The Vfs contract

One trait carries local disk, SFTP, S3 and WebDAV. Getting it right early is what makes remote mounts feel like folders rather than a bolted-on transfer client.

  • Async throughout. Even local calls, so a slow network mount can never block a frame.
  • Streaming listings. read_dir yields entries as they arrive, not a completed Vec.
  • Cheap metadata, expensive metadata. Name and kind come free with the listing; size, permissions and git status are separate, cancellable follow-ups.
  • Capabilities are declared. A backend advertises what it supports (symlinks, permissions, atomic rename, random-access write). The UI greys out what a mount cannot do instead of failing at the last step.
  • Paths are opaque. VfsPath, not std::path::PathBuf — remote paths are not local paths, and Windows path rules are not POSIX rules.

The honest read

Roughly a third of the total effort is in this table, not in the feature list. Iruka is a one-platform product; the moment Ferret commits to three, the terminal, paths, shell integration and packaging each triple. Plan Phase 9 as real work, and get a Windows runner into CI from Phase 0 so drift is caught the week it happens rather than the month before release.

§7

Decisions

Settled choices with their reasoning. Assumptions and unknowns are in §9, kept separate on purpose.

Accepted decisions
IDDecisionReasoning
D-01 GPUI from Zed's Git repository, not a crates.io release. gpui_platform is not published, and gpui-component resolves gpui from the same Git source. Using both from Git lets Cargo unify them into one crate instance. Reproducibility comes from Cargo.lock. Consequence: never add a rev to one without pinning the other to match.
D-02 Adopt gpui-component rather than hand-rolling widgets. It already provides the exact set this product needs — virtualised table, tree, dock, resizable, Rope-backed input, highlighter, Markdown text, command — is Apache-2.0, and targets both platforms. Rebuilding that is a year of work with no product in it.
D-03 Rust edition 2024, MSRV 1.90. gpui-component is edition 2024; matching avoids friction at the boundary.
D-04 Git via the git binary, not libgit2 or gitoxide. Credential helpers, SSH agents, 2FA, signing, hooks and includeIf configs all work for free. No C toolchain, no vendored build, no divergence from what the user sees in their own terminal. Cost: a runtime dependency on git being installed, and parsing porcelain output. Accepted — the reference product visibly does the same thing.
D-05 ripgrep's crates in-process, not a bundled rg subprocess. Structured results, real cancellation, no binary to ship or find on PATH. Same engine either way.
D-06 SFTP through russh, in-process — no FUSE, WinFsp or macFUSE. A kernel-level mount would need a driver install, elevated privileges and three separate implementations. An in-process VFS backend is the same experience inside Ferret with none of that. Cost: other applications cannot see the mount.
D-07 Interactive SSH shells out to the system ssh; only file browsing uses russh. Same reasoning as D-04 — the user's existing SSH configuration is not something we should try to reimplement.
D-08 Heavy backends behind default-off cargo features (s3, webdav). The AWS SDK alone would dominate build time for a feature most users never touch.
D-09 All bulk mutation goes through the operations queue (F-60). One code path for correctness, cancellation, conflict handling and progress. No feature gets its own private copy loop.
D-10 [profile.dev.package."*"] opt-level = 2. GPUI is unusably slow with unoptimised dependencies. First build is long; incremental builds of our own crates stay fast.
D-11 GPL-3.0-or-later. Copyleft is the point: the reason Ferret exists is that the reference product is closed. Check: compatible with GPUI (Apache-2.0) and gpui-component (Apache-2.0) as dependencies.
D-12 Settings are a human-editable JSON file; the settings UI is a view over it. Matches the audience. Anything the UI can set must be expressible in the file, and external edits reload live.
D-13 Enable gpui_platform's runtime_shaders feature explicitly. Without it, gpui_macos's build script calls xcrun metal, which exists only inside full Xcode — Command Line Tools alone fail with unable to find utility "metal". runtime_shaders stitches the shaders and compiles them at runtime, so contributors need only the Command Line Tools. gpui-base already enables it transitively; declaring it ourselves means the macOS build does not silently depend on a feature another crate happens to turn on. Cost: shader compilation moves to first launch.
D-14 Interface colours come from gpui-component's theme; ferret-ui defines only what it lacks. Resolves Q-07. Adopting cx.theme() wholesale gives light and dark, semantic tokens and component consistency for free, and keeping a parallel palette would guarantee drift. ferret-ui keeps only the terminal's sixteen ANSI slots and the file- and git-state colours, which the component theme has no concept of.
D-19 Target macOS and Windows. Linux is deferred, not abandoned. Three platforms tripled the work in the terminal, paths, shell integration and packaging (§6) before a single user existed. Two well-supported targets ship sooner. Consequence: ferret-platform's trait boundary stays intact so Linux is a re-add rather than a rewrite, and no POSIX-only assumption may leak into feature code. Note that gpui-base still enables gpui_platform's wayland and x11 features transitively, and Cargo unions features — removing them from our manifest states intent, it does not exclude the code.
D-16 Per-folder view preferences are a bounded LRU in one JSON file, capped at 4,000 folders. Resolves Q-03. The whole map loads at startup, so lookup is synchronous and O(1) — anything that awaits here shows the wrong view mode for a frame before correcting itself. The cap bounds the file by construction (~500 KB) however long Ferret runs, and writes are debounced so a whole-file rewrite costs nothing. Windows Explorer already caps its equivalent store and evicts old entries; the real requirement is "remember the folders I use", not "remember every folder forever". Sidecar files (.DS_Store, .directory) were rejected outright: they need write permission the user may not have, fail on read-only volumes and network shares, and litter the user's own repositories. Revisit an embedded store when the thumbnail cache (F-33) gives a second reason for one.
D-17 One Vfs trait: async throughout, streaming listings, capability-declared, cancel-by-drop. A thin wrapper over the platform, not a filesystem reimplementation. Async even for local disk, so the first remote mount is a slow call rather than a frozen window — retrofitting that later would touch every call site. Listings stream, so a large directory paints immediately: measured at 301 µs to the first row against 143 ms for the full 200,000-entry listing. Backends declare metadata_in_listing because Windows' FindFirstFileEx returns size and times with the name while macOS's readdir does not — hard-coding either shape wastes one platform. VfsPath rather than PathBuf, so remote and Windows path semantics cannot leak into each other.
D-18 File icons come from the OS, behind an IconProvider trait, with a bundled set shipping first. A Finder replacement whose icons do not match Finder looks wrong on sight, and both targets expose this — NSWorkspace.icon(forFile:) and SHGetFileInfo — including application icons and custom folder icons. A small bundled set (~60 types) ships first behind the same trait so the list never blocks or flickers on an icon lookup; the OS providers land behind it before the base closes. Same interface either way, so no rework.
D-20 Performance is measured against a generated fixture, with budgets that fail the build. "It scrolls fine on my repo" proves nothing. cargo xtask fixture generates one tree covering every cliff — 200,000 flat entries, maximal nesting, 255-character and NFD and emoji names, broken and cyclic symlinks, an unreadable directory, a 4 GB sparse file, 59 extensions. cargo xtask bench measures time-to-first-row and full-listing time and exits non-zero past budget: 50 ms to first row, 3 s for the full 200,000-entry listing. It lives outside the repository so Cargo and editor watchers do not crawl it.
D-15 No window blur or vibrancy. The starter scaffold forced WindowBackgroundAppearance::Blurred with a transparent root fill. That constrains every surface to translucency for an effect that is version-gated on Windows and compositor-dependent on Linux whenever that returns. Ferret draws on an opaque themed background; blur can return later as a macOS-only enhancement.
§8

Delivery phases

Ten phases in dependency order. Each names what must exist before it starts and what proves it is done.

The ordering is not Iruka's release history. It is what a fresh build needs: the filesystem layer first, then the browser, then the terminal — because the terminal is the feature that makes the product worth using and everything after it is easier to judge once it exists.

Base, then addons

Phase 1 is the base: the explorer shell, specified in full by the base UI reference. It is a complete, usable file manager on its own. Phases 2–9 are addons — each plugs into the finished shell and each is independently shippable. The preview pane, the terminal panel and the splitters that drive them are deliberately not in the base; they arrive with their features rather than as empty furniture.

§9

Risks

Ranked by expected cost
IDRiskImpactMitigation
R-01 The terminal is far harder than it looks. A credible VT implementation with correct resize, alternate screen, mouse reporting and ConPTY behaviour is months of work, and it is the feature the product is named after. critical Start from alacritty_terminal for the grid and parser. Read Zed's terminal crate closely — it solves this exact problem on this exact framework. Prototype ConPTY in Phase 0 or 1, before committing to the Phase 2 schedule.
R-02 GPUI is unstable and undocumented. It tracks Zed's main branch, has no stability guarantee, and its documentation is thin. high Cargo.lock pins the commit, so updates are deliberate. Budget time for breakage at each bump. Zed's own source is the real documentation.
R-03 Two-platform scope. Every system-touching feature is written twice; see §6. Reduced from three by D-19, but not eliminated. high Get both into CI in Phase 0. Push platform differences behind ferret-platform traits so they cannot leak into feature code.
R-04 Scope. This is a two-person-year feature list at commercial pace. high Phases 1 and 2 alone are a usable, differentiated product. Ship them and get users before building phases 7 and 8. Treat anything marked later as genuinely optional.
R-05 Performance in large directories and large repositories. Naïve per-row metadata or git status will make scrolling unusable, and it will not show up in a small test folder. medium Virtualise from the first commit. Keep a fixture directory of 200,000 entries and a large repository in the test set from Phase 1.
R-06 Data loss. A file manager that mishandles a move or an in-place save destroys the user's work — the single worst failure this product can have. critical All mutation through ferret-ops (D-09). Atomic saves. Trash by default. Heavy unit testing of ferret-ops and ferret-vfs against temp directories. Never a destructive default.
R-07 Build friction discourages contributors: a Git GPUI dependency and a long first build. medium The worst of it — full Xcode on macOS — is removed by D-13. Document the rest precisely in the README. Provide a devcontainer or Nix flake. Cache the Cargo registry and Git checkouts in CI.
R-08 gpui-component is a single-vendor dependency at version 0.5 with publish = false at the workspace root. medium It is Apache-2.0 and forkable. Keep usage inside ferret-ui (§5) so a fork or replacement stays a contained change.
